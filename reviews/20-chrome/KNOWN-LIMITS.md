An ordinary network send adds no authority: that page could call `fetch('/delete')` autonomously. The hidden step itself is not held or reported as `unknown`; the result reports the original click as dispatched, with delivery unproven and only untrusted page observations. It does not establish that no other action happened. Rejected fixes: native entry breakpoints do not see the borrowed call through the controlled tab; DOM breakpoints expose raw attributes and violate the password rule; attaching the outside donor violates “only Claude's tabs”. Accepted as “a page sends on its own” by the lead; the activation capability added by every click is stated separately below.
- Every Claude click grants the page's handlers user activation, as an owner's click does; withholding it would break ordinary clicks. Popups can open and join Claude's record, the opener's badge and the first-input reload rule; clipboard writes are accepted as on the owner's own clicks. The Linux probes measured a popup blocked autonomously but opened on Claude's click, a clipboard write pending permission autonomously but accepted on the click, downloads in both cases, and the synthetic unsupported payment probe rejected in both cases (no claim about real payment sheets). The activation claim rests on those popup and clipboard probes, not on Web Audio: in a tab fresh from `chrome_open`, Claude's click on a fixture's "Play media" button did not start an `AudioContext` within 15 s (run 43575571819), and neither did the owner's Tab+Return there (run 43580466542), while his Return on the same page loaded through the address bar started it at once; the guard passes a free click through untouched (`guard.js`, the capture handler stops only asking controls), so the extension's code does not explain it and it stays an observation (REPORT.md, step 8).
- Navigation and GET searches can carry data in addresses; text can leave without a send question; accepted as ordinary browser navigation under decision 25.
- The English/German word list is a rule of thumb; disguised/unlabelled actions can stay free and harmless controls can ask unnecessarily; accepted under decision 25 as a recognition heuristic rather than a proof of page intent.
- Credential detection is a word heuristic (English and German names, API-key names, the `cc-csc`, password and one-time-code autocomplete tokens, label text split by markup); a revealed secret with no recognised signal, such as an image label, nearby text that isn't a label, another language or an unknown abbreviation, is read in a watched tab, and after an approved asking read in an unwatched one; the harm is one owner-typed secret exposed; accepted because the word list is a heuristic by design: masked and `type=password` history always protect, and the asking read shows the labels. The reverse also happens: a control named only by a short credential word (a "PIN" button, a colour called "Tan") is withheld and left to the owner. There is no bare `token` on the list: hidden CSRF fields are commonly named `*_token`, and withholding them would make ordinary forms refuse; so a field named only by a token word (an API or access token) is read like any other field (fixes b, G4.3).
- The browsing target of a link or form is resolved by the reader in script, following Chromium's rules: the first HTML `<base>` with a target, an empty target treated like a missing one, HTML's sanitising rule (a tab or newline together with `<` means `_blank`) for HTML links and forms, and an SVG link's own target with `xlink:show="new"`. Only Chrome decides where the input actually goes, so a Chrome version that resolves a target differently would make the question name another window or frame than the one used; the harm is that an approved request runs in a different window or frame than the question said; accepted because the address, method and body stay bound and are checked again before input, and the browser rows compare these rules with the installed Chrome: Chrome 157.0.8103.78 agreed on all 96 destination rows, including an empty `target` falling back to the base target (run 43566651314).
- A page can change between the final binding check and input; the page can act on a last-instant change; accepted under decision 25 because the local check narrows but cannot eliminate that interval.
- Changed visible compose text adds one new question showing the before/after text; a second change stops the send and asks the owner to send it himself. This is the bounded cost of binding read-only previews without an ask loop; accepted by `20-recheck-fixes-2.md`.
- When the smallest compose area is the whole body, all its visible text is bound. Live text anywhere in that body can exhaust the one re-ask and end in “send it yourself”. The lead accepted this cost in `20-recheck-fixes-2b.md`; revisit it after the owner's live-site tests if it occurs often.
- `done` proves one dispatch, not delivery; a site may reject or fail the action despite that status; accepted because page observations are labelled as such and the tool does not observe the network.
- An owner's delayed page step inside Claude's hold window is held and asked, including after an immediate submission; this adds a question to his own work; accepted by the owner's board #138 decision when task ownership is unclear.
- A native dialog already open before take is handed back to the owner; automation waits for his answer; accepted by the lead's bounded handoff/recovery rule because Chrome cannot establish that dialog's opener and guarded continuation.
- A borrowed-realm native dialog always asks with its continuation explicitly unguarded; the answered page can continue outside that dialog's hold; accepted by the lead's exact-answer, one-use approval rule with any prior hold preserved.
- A pristine-realm stringifier can detect wrappers in a controlled tab; a page may change behaviour or reject automation; accepted as limited compatibility exposure inside Claude's group, with no MAIN wrappers in ordinary tabs.
- Marking page text untrusted does not make its claims trustworthy; a model can still misunderstand page content; accepted at the normal MCP bar, with all approval content independently bound by the tool.
- Fixture compatibility does not establish every live-site layout or bot check; real sites may require adapter updates or owner intervention; accepted as the explicitly staged after-boot owner check, not a claim of live-account verification.
- Storage-fault and crash evidence covers synthetic scenarios; an unmodelled platform failure may behave differently; accepted as bounded test evidence, with unknown outcomes never automatically replayed.
- Another program running as the owner's user can disturb or imitate the native host or start Chrome differently; it can bypass this tool through the user's existing capabilities; accepted by decision 24 rather than treated as a tool-created authority. It gets no standing permission from the service: a "don't ask again" entry or read-only off through `chrome.sock` needs the owner's admin password in a polkit dialog, once for each change (final fixes F7).
- A process posing as the native host can open that password dialog for a change the owner didn't start; the harm is a nuisance dialog, or the named change if he confirms it anyway; accepted because the dialog names the change and needs his password every time, and the details page tells him to confirm only a dialog he started there.
- A process posing as the native host that connects to `chrome.sock` first, while Chrome is closed, makes the service refuse the real host (one live host at a time) until it disconnects; the harm is availability only: Chrome's tools and the details page don't work for the owner until that process disconnects, and nothing is loosened, sent or written for it; accepted as the same class as the host-imitation residual above (decision 24), since that process already runs as the owner's user and could stop his Chrome or the tools in other ways.
- The unsaved-typing report tells the owner's typing from Claude's by when it happened: trusted input in the field Claude aimed at, during Claude's own dispatch (from arming the page until the dispatch's finish), is marked as Claude's once that finish arrives; the harm is that owner typing into that same field within that span can be discarded without his OK; accepted because it needs his keystroke to land inside Claude's dispatch in the very field Claude is filling, and any other typing, including a change nobody was seen making, is marked as his. A dispatch whose finish is lost (a page dialog's pause failing, or the finish message failing on an unchanged document) is never confirmed: its marks count as the owner's in the report while it stays open, and become owner marks when Claude's next dispatch starts (fixes b, G2).
- The playing-media part of the unsaved-typing report is Chrome's tab `audible` flag, which stays on for about two seconds after sound stops; a report just after playback ends can still name media that is playing; the harm is one extra question to the owner; accepted because it errs toward asking and Web Audio and detached media are visible only through that flag. `chrome_tabs` rows show the same flag as `audible`, with `muted`, so Claude can see sound before closing or navigating a tab (final fixes step 8).
- After a release and a retake of the same document without a reload, every plain text field holding text counts as unsaved (final fixes step 7, the stricter rule), and a release voids Claude's earlier typing marks: a field Claude typed before the release is marked as the owner's, since he may have edited it while no guard listened (fixes b, G1). Claude can't type in a retaken document before its guarded reload, which gives this report first, so no mark made after a retake sits on unseen typing. What remains is the cost: one extra question when Claude takes back a tab holding only its own untouched draft; accepted because it errs toward asking, as the rest of the report does.
- The discard report runs before the first act after every take and retake (input in a taken or retaken document waits for its guarded reload, which gives the report; navigate and close_tab give it themselves) and before every reload, navigate, back, forward and close_tab. It does not run when a page action of Claude's, while he holds the tab (a click on a link, a submit, or another input of his that the page answers by navigating), makes the page navigate: typing the owner did in that tab while Claude held and drove it can be lost with the document. The narrower case is Claude's `fill` of a field the owner typed into while Claude held the tab, which replaces his text without a report. The harm is one owner draft; accepted because a click is what navigates, and cancelling the page's own navigation on every Claude click would break normal clicks; the owner is at the keyboard and sees the tab he typed in (fixes b, G3).
