## Findings reported immediately to the builder

1. **P1: popup admission can resurrect control after Stop.** `preloadEvent(Target.attachedToTarget)` validates its parent epoch before awaiting target lookup, tab lookup and grouping, then unconditionally adds the popup to `controlled`. **Run:** a plain Node VM loaded the actual background source, suspended `getTargets()`, awaited actual `stop()`, and then resolved the popup target. Output was `controlled:[8]`, followed by `Page.enable`, `Runtime.enable`, `Debugger.enable`, `Debugger.setBreakpointByUrl`, `Target.setAutoAttach`, and `Runtime.runIfWaitingForDebugger`. The popup became controlled after Stop completed. Initial `take()` has the same pre-admission gap: its first `controlled.set()` follows several awaits, so Stop cannot discover its pending attachment. Reserve/cancel admission from the first await, and check the captured Stop generation/control identity before every later mutation.

2. **P1: a document can become POST-loaded between inspection and automatic reload.** `prepare_control` checks GET/document metadata once, then awaits the frame `reload_state` queries and finally calls `Page.reload` without checking the current native document again. **Run:** an actual-dispatch VM started with GET top/child documents; during the child's state query the mock updated the actual `documentMethods` top entry to a replacement POST document. The dispatcher still reached reload, printing `reloadedMethods:["POST"]`. This is a source/Node counterexample, not a real receiver resubmission. A final method/document check alone leaves a further native boundary race; a browser-enforced loader identity condition is preferable. **Read:** explicit `navigate` with `direction:'reload'` also bypasses all method checks. The prohibition on resubmitting a form-loaded document must cover that path as well.

3. **P1: private release cleanup can block Stop indefinitely.** `release()` removes acting authority but awaits MAIN `Runtime.callFunctionOn` and isolated `Runtime.evaluate` cleanup before debugger detachment or the existing bounded content clear. A modal or unresponsive renderer can prevent those Runtime replies. **Run:** an actual-release VM with one registered cleanup handle and a pending `Runtime.callFunctionOn` printed `settled:false, controlled:[], calls:["Runtime.callFunctionOn"]` after 20 ms; detach was never reached. The existing bounded-release test had no installed documents and therefore missed this new await. The builder is considering a truthful bounded `cleanup_pending` response that revokes input immediately but retains private handles and visible group membership until restoration can finish. That design needs tests for modal close, unresponsive cleanup, reconnection/retake, popup descendants and manual group removal; it must not claim full release while wrappers remain.

4. **P1: installation can race release and leave wrappers in an owner tab.** **Read:** the paused-bootstrap handler captures a target state, then awaits the bundle and Runtime evaluation without rechecking its epoch. Release can inspect an empty `documents` map and detach while an outstanding install completes; its private cleanup handle may be recorded only after release has passed it. Track in-progress installs as part of release and check the captured target/control identity at asynchronous boundaries. This finding is source-derived; no native-browser race was run.

5. **P2: popup enrollment has two competing implementations.** **Read:** the new autoattach handler enrolls a popup directly, while `webNavigation.onCreatedNavigationTarget` still queues `take()` for it. Both can pass the uncontrolled check before either records admission, causing a second attachment attempt followed by `release()`, or replacement of the correct child-session debuggee with an independent attachment. Consolidate admission and test both notification orderings. This was reported alongside finding 1; no real Chrome ordering was assumed.

Three additional concerns were sent immediately to the builder:

1. **Owner-default attribution remains too broad.** The uncommitted predicate allows a phase-zero, trusted `submit` while the private MessageChannel mark remains, provided form/submitter match and the old owner input was not cancelled. For Enter without a submitter, it treats almost every input type as having a submission default, without checking whether implicit submission would actually happen. A form with multiple fields blocking implicit submission and no submit button has no such default. **Run:** actual-guard VM after trusted Enter on one of two modeled text fields, followed by phase-zero same-form `requestSubmit()` before the private channel cleared, printed `arrivals:1,holds:0`. This confirms the broad source predicate, not native task ordering or a real receiver arrival. Native `requestSubmit()` also produces a trusted submit event; that trust is insufficient to establish owner-task causation. A temporarily disabled/removed submitter can suppress a native default without `preventDefault` as well. The strict runner should exercise a suppressed/no-default owner input plus a Claude timer. If the exact native default cannot be established, the brief requires holding and recording the PLAN-GAP.

2. **Failed cleanup can still be reported as complete.** Release ignores CDP `exceptionDetails` from both cleanup calls and swallows protocol failures before restoring group membership. **Run:** in the actual private-relay factory fixture, making the installed `HTMLElement.prototype.click` descriptor nonconfigurable caused `cleanup()` to throw `TypeError: Cannot redefine property: click`, leaving `EventTarget.prototype.dispatchEvent` wrapped. The shared enabled flag was already false, so those retained wrappers forward native calls; this is a full-restoration/normal-browsing claim issue, not demonstrated unapproved delivery. Cleanup should attempt every remaining restoration/disposal step and distinguish destroyed contexts from live cleanup failures. It must not claim that every prototype was restored when a live page prevented restoration.

3. **Preload bookkeeping has no lifecycle bound under script/iframe churn.** `Debugger.scriptParsed` retains every script ID although only the bootstrap URL is needed. `Runtime.executionContextDestroyed` removes the context but not its script/document entries; removed iframe factories and bookkeeping can accumulate until a full execution-context clear. Filter bootstrap scripts and retire document/script state and remote handles when their execution context is destroyed. This is source-derived; no native memory stress measurement was run.
