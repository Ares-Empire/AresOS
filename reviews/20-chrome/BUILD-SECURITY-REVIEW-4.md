# Interim security review: document-start injection and native event relay

Reviewed the changing worktree based on `11b396f779473f91070af1caf975fac7f0f2e433` on 2026-11-09. This review is limited to the core extension injection and native-event relay. Implementation files and side-build files were not changed. No local browser or browser profile was accessed. The builder is repairing findings concurrently; this records the source snapshot where they were found, not a verdict on later changes.

## Findings reported immediately

1. **P0 — a held original Event exposes the relay and its cleanup capability.** **Read:** `page.js` dispatches the original event onto its detached relay before the isolated guard decides whether to deliver it. When the guard holds an asking click, it does not redispatch that event onto the intended target. The original event's native `target` consequently remains the relay after the wrapper returns. Page code retains the original Event, so it can obtain `event.target.firstElementChild` and dispatch `aresos-relay-cleanup`. The MAIN cleanup listener sets `enabled=false` and restores the saved native functions. A subsequent form submission bypasses the hold. This contradicts the claim that the relay and cleanup capability are unreachable. The same exposure occurs on unsuccessful transfer/delivery paths. Required regression: hold an asking `dispatchEvent(event)`, attempt cleanup through every retained native event reference, then attempt an unapproved submission; the independent receiver must still show zero arrivals.

2. **P0 — scrubbing the Event only in the report's final cleanup leaves a callback window.** **Read:** after relay transfer, `new Event('aresos-relay-deliver', {cancelable:true})` reads missing WebIDL dictionary members such as `bubbles` and `composed` through the page's `Object.prototype`. A hostile inherited getter can inspect the retained Event's `target` and invoke the cleanup capability before a final target reset runs. The other constructors use ordinary option objects too, and `targetRanges` is an ordinary Array whose iterator can be replaced by page code. Capturing the constructors does not capture these conversion operations. Reset the native target immediately after relay transfer, before constructing another event; eliminate inherited getters and page-controlled iteration during staging. Remove the DOM cleanup capability as defense in depth, keeping restoration on the private CDP path. An immediate reset must preserve native type/bubbles/cancelable and prior cancellation, and must cover failures. The builder's proposed `Event.prototype.initEvent` reset needs native regression evidence for both held and failed delivery, including hostile dictionary getters.

3. **P2 — abort cleanup is not associated with its own stack entry.** **Read:** an inherited getter during the outer request's `InputEvent` construction can invoke a nested wrapped operation. The nested delivery pops its record before invoking page handlers, but the nested MAIN `finally` then sends `aresos-relay-drop`. That listener pops the still-pending outer record. The outer target transfer or original-event transfer is subsequently lost or assigned to a different record. The observed source path tends toward dropped/held input rather than an unapproved send, but violates native compatibility and makes record ownership unreliable. Bind cleanup to a per-request record, and test nested success, nested hold and nested throw. Eliminating all page callbacks during staging reduces the reachable cases but does not itself make the existing unscoped stack operation correct.

**Read:** the new global registration contains only the inert ISOLATED context script. Controlled sessions install an exact extension-script breakpoint, identify the real extension world and matching MAIN context, and initialize guard/reader/wrappers before resuming. ## Follow-up on the private-verdict redesign

The builder subsequently replaced original-Event transfer with a private request/verdict channel. **Read:** the original Event no longer visits the relay; native click/dispatch is performed in MAIN only after the isolated guard cancels a signal on the detached private control. Form submission remains isolated. A missing guard leaves the signal uncancelled and denies dispatch. Request-number matching scopes abort cleanup. This design removes the direct Event-target disclosure and can satisfy continuation 2: its prohibition covers signals the page can reach, whereas this channel must remain genuinely unreachable. Its permission signal must never also be accepted on the legacy public bridge.

**Additional blocking implementation finding, reported immediately:** the first `options()` helper in that redesign called the page's live `Object.keys(values)` and iterated the returned Array with `for...of`. Page code could replace either function and obtain or modify the actual request/detail and StaticRange initializer objects. Furthermore, assigning a new `detail.request` property on an ordinary object could invoke an inherited page setter with the actual detail object as `this`; ordinary descriptors passed to captured `Object.defineProperty` could invoke inherited `get`/`set` getters. Null-prototype constructor output alone therefore did not remove callbacks or protect target identity. The suggested repair was a captured `Object.setPrototypeOf` applied directly to fresh literal dictionaries, including detail before assignment and property descriptors, plus private iterable/iterator/result objects without page-controlled enumeration. This follow-up requires rereading the actual repaired helper and native hostile-prototype tests before closure.

**Final source reread of this review turn:** the builder chose another valid repair: capture `Object.keys` before page scripts and index its dense result directly; populate null-prototype options and property descriptors; use a private iterable, iterator and iterator-result objects; define the request-number property through the captured native function; and match the request number on target, delivery and abort signals. MAIN also rechecks the native event type and composed document before native dispatch. No original Event is dispatched on the private relay. These changes address the specific source paths described above. I found no remaining relay-specific page-reachable relaxing path in this snapshot. The cleanup event is not independently a violation if the private node remains unreachable; removing it would be defense in depth rather than a condition imposed by continuation 2.

The result is **source findings addressed, native verification pending**, not a green acceptance verdict. Required native cases include held and failed dispatch; forged public relay/cleanup event names; poisoned Object/Array prototypes and inherited dictionary members; nested success/hold/throw; original Event and payload identity; cancellation/return values; and receiver counts before approval, after approval and after replay. No automated test or native browser was run by this reviewer during this review turn.

## Focused source recheck at `93851f223dc7d9b63da4c43c104b959851722dcc`

Read `guard.js`, `page.js`, the reader's implicit-submitter selection, the relevant background release code and the owner-attribution test cases. No browser, browser profile or side-build file was accessed. No test was run for this recheck.

**Blocking causation gap in this commit:** the private MessageChannel mark plus exact form/submitter matching does not distinguish a native default submission from a later page `requestSubmit()` while the mark is still pending. `requestSubmit()` itself generates a trusted submit event. A concrete source counterexample is an owner pressing Enter while a required field is empty or a custom-validity error is set: validation suppresses the native submission, leaving `owner.consumed` false. If an already-scheduled page timer runs before the private message, it can set the input's `.value` or clear `setCustomValidity()` and call `requestSubmit()` with the same submitter. Those value/validity changes need not generate MutationObserver records. The resulting trusted submit satisfies the phase-zero tests and receives an owner exemption even though it is delayed and changed. This is a reachable-source argument conditional on timer/message task ordering, not a claimed native receiver reproduction.

The builder proposed private call-depth tracking around every page-origin native `requestSubmit()` path in `onCall`, using `try/finally`. At phase zero, an event generated while that depth is nonzero must not use the owner exemption; a synchronous owner callback with a nonzero input event phase can still use it. The actual browser default does not enter that wrapper. Private capture of `invalid` events that invalidates the owner mark provides an additional conservative defense. These proposed changes address the identified distinction; this commit predates them, so they are not marked verified here.

**Other native-default routes examined, source only:** the wrapped `click()` and synthetic click paths are classified before native delivery. Chromium's label activation forwards a trusted click only when its underlying input is trusted; script-driven label activation does not manufacture an owner click. DOM `execCommand` insertion routes examined use typing commands rather than the keyboard TextEvent route that invokes implicit submission. No additional ordinary-page route to borrow this phase-zero exemption was identified in this focused review. The separately documented fresh-realm borrowed-native residual remains outside this conclusion. Sources: [simulated-event trust](https://chromium.googlesource.com/chromium/src/+/HEAD/third_party/blink/renderer/core/events/simulated_event_util.cc), [DOM insertion commands](https://chromium.googlesource.com/chromium/src/+/HEAD/third_party/blink/renderer/core/editing/commands/insert_commands.cc). These HEAD sources support the analysis but do not replace testing the pinned browser builds.

**Cleanup, source only:** `cleanup()` closes activation and disables captured wrappers before attempting restoration. A sealed but writable prototype property can restore its native function through the value-only fallback. A frozen, nonwritable wrapper cannot be restored; cleanup returns false, and release retains a pending result until that context is gone rather than claiming restoration succeeded. Retained wrapper references forward to the saved natives after authorized cleanup. Freezing a wrapper or prototype does not itself invoke the private cleanup path. No new page-reachable cleanup authority was found. Native frozen/sealed-prototype cases and pending-release behavior still require their own runtime evidence.

## Popup startup architecture blocker, 2026-11-10

**Conclusion:** no supported mechanism was established that guarantees MAIN installation before the first script of arbitrary native popups, while preserving normal outside tabs, using this ordinary extension's debugger authority and no browser debugging endpoint. This is an architecture blocker under `20-continue-3.md`'s explicit stop-and-report instruction, not a passing popup result. The builder reports both external install modes at 39/42 with the popup uncontrolled and no page `Target.attachedToTarget`; this reviewer did not independently run or inspect those browser jobs.

The primary-source investigation examined Chromium HEAD, resolved during this review to `15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0`. That is a source snapshot, not a claim that the external test binary was built from this exact revision.

- `RenderFrameHostImpl` obtains the new window's debugger-wait flag from `ShouldWaitForDebuggerInWindowOpen()`. That function enumerates **browser** DevTools agent hosts only. An opener's page-level auto-attach handler is not consulted. The frame auto-attacher enumerates descendant frames/workers, so adding a page-type filter does not make ordinary popup WebContents its children. See [new-window creation](https://chromium.googlesource.com/chromium/src/+/15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0/content/browser/renderer_host/render_frame_host_impl.cc), [popup wait selection](https://chromium.googlesource.com/chromium/src/+/15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0/content/browser/devtools/devtools_instrumentation.cc), and [frame auto-attacher](https://chromium.googlesource.com/chromium/src/+/15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0/content/browser/devtools/frame_auto_attacher.cc).
- `Target.autoAttachRelated` requires browser access mode; `attachToBrowserTarget` likewise requires browser mode. More decisively, the browser agent itself refuses sessions whose client is not trusted. The extension debugger client grants that trust only to the hard-coded Perfetto extension, with an additional restriction for unpacked Perfetto. Ordinary policy installation does not grant it. Discovering an existing browser target ID therefore does not bypass the session check. See [Target restrictions](https://chromium.googlesource.com/chromium/src/+/15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0/content/browser/devtools/protocol/target_handler.cc), [browser session admission](https://chromium.googlesource.com/chromium/src/+/15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0/content/browser/devtools/browser_devtools_agent_host.cc), and [extension trust/attachment](https://chromium.googlesource.com/chromium/src/+/15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0/chrome/browser/extensions/api/debugger/debugger_api.cc).
- `Page.windowOpen` sends and flushes a notification without waiting for client acknowledgement. `webNavigation.onCreatedNavigationTarget` similarly broadcasts an extension event; it supplies no navigation suspension or continuation handle. Responding with attach/pause/injection is therefore a race, even when it succeeds in ordinary cases. See [Page notification implementation](https://chromium.googlesource.com/chromium/src/+/15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0/third_party/blink/renderer/core/inspector/inspector_page_agent.cc) and [navigation notification implementation](https://chromium.googlesource.com/chromium/src/+/15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0/chrome/browser/extensions/api/web_navigation/web_navigation_api_helpers.cc).
- Pre-registered content scripts select URLs/origins, not private controlled-tab membership. `RegisteredContentScript` has no tab/group target; only immediate `ScriptInjection` has an injection target, and `injectImmediately` explicitly provides no prior-page-load guarantee. Registering MAIN for a controlled popup's URL also registers it for ordinary tabs at that URL. The global inert isolated bootstrap does not create a debugger session for a newly created page. See the [actual scripting API schema](https://chromium.googlesource.com/chromium/src/+/15bbbb7f9dcc96d89ada6f0c2c131edd2ad1b2f0/extensions/common/api/scripting.webidl) and [injection timing contract](https://developer.chrome.com/docs/extensions/reference/api/scripting#property-ScriptInjection-injectImmediately).

**Rejected alternatives, by inference from those boundaries:** late attach followed by reload cannot undo the popup's first scripts and is not the accepted already-open-tab flow. Network interception alone cannot cover an initial `about:blank` popup and synchronous opener `document.write()` execution. Deferring/replacing `window.open()` changes synchronous WindowProxy behavior and still requires a solution for native link/form-created windows; it is not a verified transparent popup mechanism. A broader registered MAIN bootstrap, page-readable identity marker, global JavaScript blocking, or external browser debugger authority would relax an explicit constraint. An extension-created blank tab can be attached before the extension navigates it, but replacing arbitrary page-created popups with that flow has different observable behavior and does not satisfy the present requirement. No such workaround was implemented or represented as a fix.

Only primary public documentation/source and the brief were read for this investigation. No local browser, browser profile, implementation edit, test execution or sub-agent was used. The supported next disposition is to retain the popup failure and report the blocker, rather than declare the before-first-script guarantee complete.
