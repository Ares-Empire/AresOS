## FIX

**`control/aresos_control/engine.py:159`, storage-failure fallback of `Engine.pending`.** Under the lock, a Mail notice taken from the pre-restore database is still listed as current.

- Scenario: service starts on an older database (lock). `Store.__init__` runs `recover_intents(persist=False)`, which synthesises recovery notices from the working DB's `submitting`/`partial` operations and defers them; `flush_notices` returns early under the lock (`storage.py:788`), so they stay in `store.deferred_notices` for the whole lock. Then `control_pending` hits a storage error inside `_pending` (I raised `ENOSPC` from `chrome.committed.sync`). The fallback at line 159 loops over `deferred_notices` and emits `("mail", "recovery-<id>:stale-send")` with "An approved operation or local repair is unfinished. Delivery … may already have happened …" in both `data.notices` and the `pending` envelope of every reply. `restore_required: true` is kept, but `unavailable` is the storage text ("snapshot only. Restart recovery…") with no restore wording. Reproduced in the copy; output above in my log. The normal path hides exactly these deferred notices (the early return in `notice_page`), so the two paths disagree, and the brief's R1 ("no row or notice from an app other than Chrome") does not hold on this path. R2's oracle capture runs exhausted phases under `crash-locked`, so this would likely surface as C3-class gaps there.
- Smallest fix: skip the loop while locked, `for changes,_,_ in ([] if self.store.locked else self.store.deferred_notices.values()):`, and optionally append the restore wording to `result['unavailable']` in that branch. Add one test (lock + injected storage error → no non-Chrome notice in reply or envelope) and one `restorelock-` probe.
- Severity: low. The leaked notice is a conservative warning, every action is still refused, and it needs a second fault. It is a FIX only because it is the brief's stated guarantee and the lead asked for this path.
