# Review 1: the test bench's design note

**Verdict:** NOT READY

## Blocking

1. **The laptop execution boundary has a host-side bypass.** `docs/design/TEST-BENCH.md:29,88–90` directs the agent to run the changed program’s test module on the laptop. The fixed read-command list at lines 265–273 covers only `bench laptop`. The brief’s ban on `test_owner_*` applies to the entire bench, and `os/tests/power-events.py:68–79,107–115` shows why a test selected from the checkout cannot be assumed safe on the host. It opens `/dev/uinput` and issues real sleep requests. Restrict native tests to individually reviewed modules, refuse `test_owner_*` and guest entry points before invocation, and route all other changed code to the container or hosted VM. Keep `exec` and input verbs unavailable to the laptop recorder. The one-step approval language at line 229 should preserve the unconditional bans on host owner tools, `rpm-ostree`, `bootc`, `ostree`, input injection, and portal changes.

2. **The laptop resource limits leave a path to swap, OOM, or a full SSD.** At `docs/design/TEST-BENCH.md:83–86,156–162,285–288`, tier 1 has only a startup floor, and tier 2 uses a lock beside the existing client-test lock. `mod/dev/env.sh:12–17,59–88,500–508` shows that the existing lock is file-specific and the memory reading is a snapshot. A Gradle build, hidden desk, or image build can start after both VM checks. A 5 GiB QEMU cap limits that scope’s charges but cannot guarantee that the owner’s game survives system-wide pressure. Coordinate laptop-heavy work across worktrees, bound the entire bench process tree, and have a watchdog stop it promptly when headroom drops. Gate disk writes on actual free space and enforce a run budget covering image builds, overlays, and evidence. Exercise refusal and cleanup under induced pressure on a disposable system before enabling laptop runs.

3. **The proposed bench source directory can enter a shipped image layer.** `docs/design/TEST-BENCH.md:142–146,263,282` puts code under `os/bench/` and cites the release checks for the existing CI service. `os/Containerfile:34–43` copies the full OS context into an ancestor of the release image. `os/.containerignore:1–5` excludes `ci/` but has no exclusion for `bench/`. The cleanup at `os/build.sh:787` hides those files in the final filesystem while leaving their bytes in the earlier layer. The checks at `.github/workflows/os-image.yml:470–484` inspect the final filesystem and specific CI paths. Place bench sources under an excluded tree or explicitly exclude `bench/`, use a separate build context for the guest layer, and test the release’s layer contents with a planted bench file. Also make the package 13 publish job reject `check_build=bench` when both inputs are supplied. Its condition at `.github/workflows/os-image.yml:263–269` omits the `check_build` exclusion used at line 421.

4. **The real-laptop recorder needs an evidence boundary.** `docs/design/TEST-BENCH.md:223–224,240,261–274` combines a broad journal read and supervisor status with a shared evidence model, and only explicitly excludes real screenshots from the repository. The status request is read-only, but its JSON includes app-window names and leftover world names (`os/config/usr/libexec/aresos-desktop:2626–2645,2875–2878,4370–4371,4810–4823`). A journal cursor bounds time and can still collect unrelated app messages. Query only the required units and fields, project status to the few booleans and process identities the assertion needs, and keep raw real-laptop evidence out of bench artifacts, agent output, and the checkout. Report unavailable journal access as unverified, with no privilege escalation.

5. **The tier 1 open-app example cannot pass as written.** At `docs/design/TEST-BENCH.md:90–96`, the stock laptop-home executable selects only an `eDP` connector and exits if none exists (`os/config/usr/libexec/aresos-laptop-home:594–595,2565–2578`). The existing test supplies `HEADLESS-1` through `run(..., select_monitor=...)` (`os/tests/laptop_home_headless.py:535–540`). After a click, the second view also cannot receive the home’s `app_state`. The helper sends it only to the initiating client. Connecting under the home’s view name would replace the home connection (`os/config/usr/libexec/aresos-shell:3429–3434,3816–3821`, `os/tests/test_aresos_shell_views.py:296–308`). Reuse the monitor-selection seam inside the disposable target, and have the observing view wait for `apps_running` to gain and lose `notepad`. Assert the launch result on the initiating connection. Apply the same monitor fix to the future VM click case on `Virtual-1`.

6. **The hosted build fits the existing machinery, but step 1 leaves incompatible pieces and an untestable gate.** `docs/design/TEST-BENCH.md:133–145,172–185,204,282–284` proposes a fixture-free layer and a disk with no account password. The current Control layer extends the full CI overlay, and its action loader lives there (`os/ci/control/Containerfile:1–5`, `os/ci/overlay/checks.py:557–575,588–608`). `prepare-disk.py:8–24` creates a synthetic root password on that route. `desktop_jvm` starts a paused JVM, while the separate guardian fixture seeds a world and prepares its launch (`os/ci/overlay/checks.py:151–164`, `os/ci/overlay/guardian.py:215–246`). Give step 1 a bench-only disk config and minimal agent with the existing virtio handshake. Reuse the read-only build job and put the VM pass under its own timeout, as Control does at `.github/workflows/os-image.yml:182–241`. Make the first gate auto-login, a positive helper health check that fails with a deliberately broken helper, a QMP screenshot, and a fresh boot ID after reboot. Put the stand-in’s world and open-app assertions in step 2. Keep guest networking off for this pass, and make the evidence size and content check gate the upload. The current upload uses `always()` even after the bound check fails (`.github/workflows/os-image.yml:251–262`).

7. **The live VM plan lacks a usable first disk and an offline update path.** Step 6 requires a local boot before step 7 creates its disk, and the design rules out downloading the hosted disk (`docs/design/TEST-BENCH.md:199–204,287–290`). The cited stock share is writable. It formats `store.raw` and creates scratch files on the share (`os/ci/stock_image.py:175–186,196–209,227–244`). Put disk creation before the first local boot gate. Specify a read-only export containing only the bench OCI image and a guest-owned writable import store. Switch to another bench-layered image so the agent survives the deployment, and require a new boot ID, the expected image revision, and a working channel after the switch. Verify KVM by opening it inside the actual rootless container before accepting the local route.

## Should fix

- Make the tier 1 launch recipe concrete. The private bus and compositor are proven starting points. The harness setup writes into `/usr`, starts two outputs, and disables cgroups (`os/input-portal/harness/in-container.sh:49–75`, `os/input-portal/harness/driver.py:1049–1055`, `os/input-portal/harness/run.sh:66–75`). Stage image files before dropping to the mapped UID, verify the private Wayland globals and actual output geometry, and include KWrite with its Qt Wayland support and the home’s GTK, Pango, Cairo, and layer-shell dependencies. Pin the stand-in scope path as the baseline if delegation fails. Keep the host user-manager socket out of the desk. The older shell headless check explicitly links to it and is unsuitable as a launcher here (`os/tests/check_aresos_shell_headless.py:115–122,148–159`).
- Define the hosted script selector, how the runner ties the selected script and artifacts to the dispatched commit, and the job’s dispatch budget. `check_build` selects a mode only (`.github/workflows/os-image.yml:40–44`). `CHROME_STEPS` is a hard-coded test sequence (`os/ci/control/control_vm.py:63–89`). A hosted batch is a realistic first delivery. Keep the interactive acceptance gate on the later VM path, with an explicit dependency on permission to run it locally.
- Correct the lid example’s evidence. The guardian closes its virtual lid during a save and holds it closed. The guest power-events test actually sends both transitions (`os/ci/overlay/guardian.py:395–426`, `os/tests/power-events.py:83–94`). On the laptop, check the effective lid policy before the owner closes the lid, confirm the game is ready, and compare process start times along with PIDs. Treat missing records or unreadable state as unverified. Add a concrete split between recorder readings and the owner’s observations for Wi-Fi, Bluetooth, touchpad, and external displays, which section 5 currently only lists.
- Keep laptop container and VM permission, any KVM access change, storage and spending limits, and visible hardware actions under **Owner decides**. Excluding private-image artifacts from public CI, picking a VM RAM ceiling, and choosing a dispatch cap within an approved budget are technical decisions. State that KVM permission and any one-time privileged setup are for the owner to arrange, and that missing access leaves the hosted route available. Record the real-laptop consent policy separately from step 5’s fixture-only implementation.

## Known limits to add

- AT-SPI on the actual GTK and KDE clients still needs proof in each target, including accessibility-bus discovery and mapping reported bounds to the screenshot. The home’s Cairo-drawn controls need the layout model or image-based interaction.
- The 1280×800 Control screenshot is a measured precedent. The proposed 1920×1080 guest mode needs to be set and verified. Glyph matching in the existing code is specific to the KDE polkit title and crop (`os/ci/control/control_vm.py:377–414`).
- The recorded 26–68 minute range and 28–44 second boot-to-channel times are Control observations. The bench needs its own measurements of build time, desktop readiness, and peak memory and disk use (`reviews/18c-image-test/REPORT.md:540–547,775–777`).
