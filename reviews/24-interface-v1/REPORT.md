## Done

### OS helper `aresos-shell/1.0` (`os/config/usr/libexec/aresos-shell`)

Python 3, standard library only. The wire format and the registry format are documented at the top of the file.

- **Transport:** newline-delimited JSON on `$XDG_RUNTIME_DIR/aresos/shell.sock`. The socket is 0600 in a 0700 folder; a live helper on the same path is refused, a stale socket is replaced. Every connection is checked with `SO_PEERCRED` (same UID only, at most 8 connections). Lines are limited to 64 KiB both ways: an oversized line gets `message_too_large` and closes that connection; malformed input (bad UTF-8, not JSON, NaN, deep nesting, a bad `id`) gets `malformed` and the connection stays usable. A connection without hello after 10 s is closed.
- **Envelope:** every request carries `protocol` (`aresos-shell/1.x`, major checked on every message) and an `id`. Replies carry `protocol`, the request `id` and `ok`; events carry `protocol`, an event `id` and `event`.
- **Messages (B1):**
  - `hello`: major/minor, capabilities, required capabilities, desktop instance, launch nonce (constant-time compare). `incompatible_version` (with the `missing` list) and `not_authorized` close the connection. Unknown optional fields are ignored.
  - `list_apps`: registry revision and `{id, name, available, reason}`, never a command.
  - `open_app`: `{request_id, launch_id, app_id, state}` with `starting`, `focused`, `background`, `closed` or `failed`, and stable errors `unknown_app`, `unavailable` (+ `reason`), `launch_failed`, `no_window`, `launch_uncertain`, `request_id_reused`.
  - Events: `app_state` (same request and launch IDs) and `shell_focus` (`foreground`/`background`, a reason, the app ID). They go only to the authenticated desktop connection and only for capabilities the mod declared. A newer authenticated desktop connection replaces the old one.
  - `world_ready` and `heartbeat` re-check instance and nonce and record the desktop world (`{id, desktop: true}`) and readiness.
  - `request_power`, `prepare_stop`, `save_complete` and anything else: `unknown_operation` (the guardian is package 25).
- **Duplicate request IDs:** results live in a launch journal, `$XDG_RUNTIME_DIR/aresos/shell-journal.json` (0600, atomic writes, at most 256 entries, per desktop instance). Each entry is written as `launching` *before* the app starts. A duplicate ID returns the recorded launch. After a helper restart, a `launching` entry becomes `starting` if its systemd scope is still active and `failed`/`launch_uncertain` otherwise. Nothing is ever relaunched.
- **Registry** (`os/config/usr/share/aresos/apps/*.json`, reviewed, shipped in the image): stable `id`, `name`, an absolute `argv` **or** a `desktop_entry` (its `Exec` split per the Desktop Entry spec, file/URL field codes dropped, unquoted shell characters refused), `working_directory`, and `window`: the Wayland `app_ids` of its windows and `instance` (`multi`: one process per launch; `single`: a launch hands over to a running instance and exits). Strict: unknown keys, a shell-string or relative argv, a duplicate ID, two entries claiming one window identity, or an entry claiming the desktop window leave that entry visible but unavailable. Availability (the executable exists) is checked at every list and open.
  - `terminal`: `/usr/bin/foot --app-id=aresos.terminal`. Its own app_id keeps the session terminal from counting as a hub-opened terminal.
  - `notepad`: **KWrite** (`/usr/bin/kwrite`, app_id `org.kde.kwrite`), already in the base image (`kwrite-26.08.1`; a test reads the image package list). It keeps package 01's `notepad` ID, as B1 asks.
  - `browser`: `/usr/bin/google-chrome` (app_ids `google-chrome`, `Google-chrome`), `single`. Shown as `not_installed` until package 21 adds Chrome.
  - Any other ID: `unknown_app`; the mod keeps showing the item.
- **Launch:** `systemd-run --user --scope --quiet --collect --slice=app.slice --unit=app-aresos-<id>-<launch>.scope -- <argv>` in the entry's working directory, stdio to /dev/null. Each app gets its own scope, outside the game's and the helper's cgroups. Launched apps never inherit `ARESOS_LAUNCH_NONCE`, `ARESOS_DESKTOP_INSTANCE` or the helper's service plumbing (`NOTIFY_SOCKET`, `LISTEN_*`, `WATCHDOG_*`). No shell anywhere.
- **Windows and focus (B2):** a minimal Wayland client for `zwlr_foreign_toplevel_manager_v1` (labwc) binds the manager and the seat, tracks every toplevel's app_id, parent and activated state, and can activate one.
  - A launch succeeds when a *new* window with one of the entry's app_ids appears. Older windows are never claimed; a window that names its app late is still claimed, once. No window within 30 s: `failed`/`no_window`. A `multi` app that exits before showing a window fails at once; a `single` app that exits 0 keeps waiting (Chrome hands the window to its running process).
  - Dialogs belong to their parent's app.
  - When the foreground app's **last** window closes, the helper activates the desktop window (app_id `aresos-desktop`) and sends `shell_focus` `foreground` (`app_closed`). Closing a background app sends nothing. Activating an app or another window sends `background`; activating the desktop sends `foreground` (`desktop_activated`). Within one compositor batch, closes are judged before activations, so labwc focusing the next window before it reports the close still returns to the hub, once.
  - Without the protocol (or without `WAYLAND_DISPLAY`) window tracking is off and the hello capabilities say so (see PLAN-GAP 1). If the compositor connection drops later, the helper exits non-zero so its supervisor restarts it and the mod renegotiates.
- **Running it:** needs `XDG_RUNTIME_DIR`, `ARESOS_DESKTOP_INSTANCE` and `ARESOS_LAUNCH_NONCE` (16+ URL-safe characters) from the supervisor. `--registry`, `--socket` and `--list` (prints the registry with availability) help testing. It runs standalone for Linux development with those two variables, so no developer direct-launch adapter was added to the mod. Nothing starts the helper yet: package 23 does.
- `os/build.sh`: one word. `/usr/libexec/aresos-shell` joins the existing `chmod 0755` line. No package lock, session or labwc change.

### Mod, Linux side (Windows path unchanged)

- `dev.aresos.shell.ShellClient` (main source set; JDK Unix-domain `SocketChannel` and Gson only, no new dependency). One background thread connects, sends `hello` (its capabilities, requires `list_apps` + `open_app`, instance, nonce) and `list_apps`, then reads replies and events. It reconnects with backoff 0.5 s to 10 s (30 s when the helper is incompatible). An open request whose connection dropped is resent after reconnecting **under the same request ID**, so the helper answers from its journal instead of launching again. Writes never run on the render thread. Heartbeats every 5 s; a helper that stops answering them is reconnected. Instance, nonce and socket come from `ARESOS_DESKTOP_INSTANCE`, `ARESOS_LAUNCH_NONCE` and `ARESOS_SHELL_SOCKET` (default `$XDG_RUNTIME_DIR/aresos/shell.sock`).
- `LinuxAppCatalogue`: `list_apps` becomes helper-type `AppDefinition`s, no command, unpinned, with default looks `terminal` = command block, `notepad` = writable book, `browser` = compass, others = paper. Merged into `apps.json` like Windows discovery (the owner's names, looks and pins win), at startup and after every reconnect. App items and logo doors use these IDs as before.
- `LinuxAppLauncher`: `open_app` by ID only; there is no command path on Linux at all. Success is a confirmed window (`focused`/`background`), or `starting` when the helper doesn't track windows (then focus return uses the existing GLFW path, as on Windows). A failure shows its reason in the action bar: `Couldn't open Chrome: not installed`, `…: no window appeared`, `…: not an app on AresOS`, `…: app helper unavailable`, `…: app helper incompatible`, `…: no answer from the app helper` (45 s cap, so a launch never hangs). Windows keeps its plain `Couldn't open Notepad`.
- `ShellFocusClient` (client; registered only when a shell client exists, i.e. on Linux): on `background` it releases all held keys (`KeyMapping.releaseAll`, so walking into a logo doesn't keep walking behind the app), resets app-use input and releases the pointer. On `foreground` it does the same, grabs the pointer when no screen is open and the window is active, and finishes a pending logo visit (the teleport in front of the logo), which the GLFW focus path may already have done. It reports `world_ready` with the save folder name once the marked desktop world is loaded with no loading screen or overlay, and not-ready heartbeats after leaving it.
- `WindowIdentityMixin` (client): on **Linux only**, sets GLFW's Wayland app_id and X11 class to `aresos-desktop` just before the game window is created, so the helper can find the hub window (B2: titles are not an identity). It returns at once on Windows.
- `AresOs`: creates the shell client on Linux clients only (never on Windows or a dedicated server), waits up to 5 s for the first catalogue, and on joining the desktop world says `AresOS apps can't open right now: the app helper is unavailable (…)` or `AresOS apps can't open: the app helper is incompatible (…)` while it isn't connected. `savePins` and the helper merge are serialized.
- Config (brief B.5): `AppsConfig` already imports package 01 configs on Linux as helper-type entries without commands, so no schema-2 change was needed.

## JUDGMENT-CALL

1. **Notepad on AresOS is KWrite.** It is in the base image already (no package change), opens one plain window per launch like Windows Notepad, and has a stable Wayland app_id. Rejected: Kate (heavier, reuses one running instance and restores sessions), nano in a terminal (not a notepad window), any editor not in the image (would touch package 21's lock). Changing it later costs one registry file and its test line.
2. **The hub window gets the identity `aresos-desktop` on Linux** (a client mixin sets GLFW's Wayland app_id and X11 class before the window exists). Without a stable identity the helper cannot hand focus back to the hub when an app closes; titles are not an identity (B2), and guessing from activation timing is fragile. Rejected: no active return (labwc would focus whatever window is next, often another app), or title matching. Package 23 and labwc window rules can use the same name. Undoing it means removing the mixin and the helper constant; Windows never runs it.
3. **Every click launches, also for the browser.** A click on the browser logo while Chrome is open asks Chrome for a new window, like a Windows shortcut. Rejected: raising the existing window for single-instance apps (more like a phone home screen). A few lines in `open_app` if the owner prefers raising.
4. **Small feel choices, all easy to change:** default looks for new helper apps (terminal = command block, browser = compass, notepad = writable book; editable in `apps.json`); the hub terminal runs plain `foot` with its own app_id `aresos.terminal` instead of the session terminal's banner shell; a launch fails as `no window appeared` after 30 s (Chrome's first start on the laptop should be measured against this); the in-world message when the helper is missing appears on joining the desktop world.

## PLAN-GAP

1. **Window tracking is unproven on labwc.** The foreign-toplevel client follows the protocol and is tested against a scripted fake compositor; no labwc runs here (the WSL distro has no labwc, and installing it is out of bounds). If labwc does not offer the protocol to the helper, tracking switches off: launches then count as opened when the process starts, focus return falls back to GLFW focus as on Windows, and B2's "show a failure if no matching window appears" does not hold in that mode. That fallback is the safest approximation available without the protocol.
2. **What package 23 must provide:** start `aresos-shell` inside the labwc session (it needs `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`), give it and the game the same `ARESOS_DESKTOP_INSTANCE` and a fresh `ARESOS_LAUNCH_NONCE` in their environment (Prism must pass them to the Java process; `ARESOS_SHELL_SOCKET` only if the socket moves), and restart the helper on exit. `systemd-run --user` needs the user's systemd manager; greetd with pam_systemd should provide it even though labwc runs under `dbus-run-session` (systemd-run talks to the manager's private socket), but this is unverified.
3. **Readiness has no consumer yet.** The helper records `world_ready` and heartbeats and logs transitions, but nothing reads them; B2's STARTING/IN_WORLD states and the guardian (packages 23/25) decide where readiness lives. No action is taken on missing heartbeats (B2: no automatic destructive repair).
4. **Websites and Windows commands are unavailable on AresOS.** `apps.json` entries of type `url`, and Windows-only IDs, stay visible but the helper answers `unknown_app`. Opening a website on Linux needs a reviewed design (for example a `browser` launch with a URL argument), which B1 does not specify.
5. **Registry columns not used yet:** B1's GPU/environment policy and lifecycle class. Apps inherit the helper's environment minus the launch secrets; all v1 entries are ordinary apps. The `minecraft` (`exclusive_game`) entry is P5.
6. **Apps that appear after a reconnect** are merged into `apps.json` at once but reach the inventory on the next world join (items are filled on join, unchanged).
7. **B1 calls the journal the "supervisor journal".** It lives with the helper in `$XDG_RUNTIME_DIR/aresos/` for now; package 23 may move ownership.
8. Error replies to lines whose `id` cannot be read carry `"id": null` (the request ID is unknown).
