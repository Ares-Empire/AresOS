**Blocking findings**

1. **The GET/HEAD exception weakens the tested recovery boundary.** [CONTROL.md:398](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:398), [CONTROL.md:412](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:412).

   17e held these requests when attribution was uncertain. The replacement depends on recognising Claude’s previously entered text, but restart ordering restores only guards—not the matching text and classification state—before accepting connections. A restored page could retry a GET carrying that text before protection is reconstructed. This does not require a hostile page.

   Keep 17e’s full fallback until all required classification state is restored and acknowledged. Narrow it only through qualified reading rules and receiver tests covering checkpoint/service/browser restarts and extension loss. “An uncertain GET can carry nothing different” does not establish that the checkpoint still knows enough to classify it.

2. **Local deletion is explicitly allowed without approval.** [CONTROL.md:854](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:854).

   “Without [an adapter], Claude’s click there acts at once” contradicts the owner’s deletion rule. An ordinary offline application can delete its only draft without making any network request. Re-check 7 identified this limitation and required approval **before** the local action.

   Require a qualified adapter and advance approval for such destructive actions; otherwise refuse them. Naming this as a residual does not authorise silently deleting local data.

3. **“Recognised action” is insufficiently defined for unattended release.** [CONTROL.md:785](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:785), [CONTROL.md:818](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:818), [CONTROL.md:824](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:824).

   The owner-only creation/revocation channels are appropriate. However, WhatsApp classification using timing, size and page state cannot prove that captured ciphertext represents the displayed message, recipient or action. These hints must not qualify traffic for “don’t ask again”.

   Define recognition as validation of the complete operation against a qualified adapter contract: account, stable target/conversation identity, action, permitted parameters and every constituent request/message. Unknown fields, mixed batches and unsupported protocol versions must ask or refuse. Earlier WebSocket messages must not inherit a later message’s exemption merely because order requires sending them first. Adapter changes must not silently widen existing permissions.

   Likewise, a syntactic GraphQL `query` at line 628 is not independently sufficient evidence of harmless server behaviour.

4. **Coding separation does not explicitly close the shared-file route.** [CONTROL.md:76](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:76), [CONTROL.md:1076](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1076).

   Refusing the machine-wide MCP servers for other users is correct. But the assistant may write owner-shared folders, while the design does not explicitly prohibit coding sessions from reading those same files.

   A mail’s contents can be written into an ordinary document or project file, read by a coding session, then transmitted using its network access—without the proposed messaging tool. Blocking session messaging does not close this.

   Require disjoint assistant-writable and coding-readable storage, including downloads, work files and session records. Transfers across that boundary must use the approved-send channel. Test this with a content marker, alongside real/effective-UID checks and rogue MCP configurations.

5. **Root removal covers only one of the two trust locations.** [CONTROL.md:479](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:479), [CONTROL.md:510](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:510).

   The start step installs the root into both policy and another trust store; stopping removes it only from policy. Consequently, the promised test that no old certificate remains accepted is not supported by the lifecycle as written.

   The `CACertificates` claim is **correct for 157.0.8103.38**: both flags are true, and the profile service observes certificate-policy changes. However, the system network context explicitly lacks the corresponding runtime verifier updater. [Policy definition](https://raw.githubusercontent.com/chromium/chromium/157.0.8103.38/components/policy/resources/templates/policy_definitions/CertificateManagement/CACertificates.yaml), [profile implementation](https://raw.githubusercontent.com/chromium/chromium/157.0.8103.38/chrome/browser/net/profile_network_context_service.cc), [system context](https://raw.githubusercontent.com/chromium/chromium/157.0.8103.38/chrome/browser/net/system_network_context_manager.cc).

   Specify removal from **every** installed trust location, crash/startup reconciliation, and invalidation of cached trust/connections where necessary. Test profile and service contexts after stop, crash, rotation and pass-through. The browser user’s NSS database is a plausible candidate, not yet a demonstrated service-context solution. [Chromium’s Linux certificate documentation](https://chromium.googlesource.com/chromium/src/+/main/docs/linux/cert_management.md).

6. **“Full upstream TLS checks” remains an unresolved security contract.** [CONTROL.md:466](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:466).

   Chain, hostname, validity and protocol checks are specified and testable. Revocation is merely added “where the core supports” it; the tests contain no revoked-certificate case. Meanwhile, saying Chrome’s extra checks “move” suggests replacements that are not actually promised.

   Specify the exact upstream verification policy, including revocation handling and unavailable/stale revocation evidence. State which Chrome protections are lost rather than replaced, and obtain the owner’s acceptance of any reduced guarantee before everyday use. Chrome documents private-root exemptions for pinning and CT, while separately describing CRLSets and stapled OCSP; those are not one blanket exemption. [Chrome 157 security FAQ](https://raw.githubusercontent.com/chromium/chromium/157.0.8103.38/docs/security/faq.md).

**Should-fix**

- **Tighten the privacy requirements and their tests.** [CONTROL.md:449](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:449). “Guarded sites” may include the owner’s unrelated tabs, so allowing their captured descriptions to reach Claude conflicts with the following sentence. Guard membership must not grant disclosure permission. Require affirmative attribution to a Claude-authorised operation; uncertainty goes only to the owner. Redact authentication material from descriptions and the tool-service approval log, not merely checkpoint logs. Clarify that “nothing leaves” means no additional checkpoint telemetry or exports: authorised tool results and the proposed phone descriptions are explicit data flows. The separate-user requirement is otherwise sound and testable.

- **The remaining judgment calls are generally right, with conditions.** [CONTROL.md:390](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:390), [CONTROL.md:404](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:404), [CONTROL.md:926](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:926). Holding foreign-frame workers is conservative and necessary; count its usability cost. A privileged port is reasonable with the stated low-port check and minimal binding privilege. Refusing action during calls is appropriate, but resumption must require an enforceable owner decision, not Claude asserting that permission was given. Always asking for Gmail sends is consistent with the mail rule. Service-protocol adapters are preferable to hostname exemptions, but recognising a protocol shape does not prove service provenance or harmless contents: test page-generated imitations. Exercise service health **while guards are active**, including attribution loss.

- **The Aresus direction is sound, but its brief needs a complete approval protocol.** [CONTROL.md:1117](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1117). Encryption, service-signed questions, phone-signed decisions and a local alternative form a reasonable design. Bind the signature/hash to one canonical description containing the operation generation, account, targets, complete capture bundle, expiry and any exact future “don’t ask again” scope. Prove authenticated enrolment against relay substitution; immediate revocation; rejection of altered, replayed, expired and restored-generation questions; and durable, atomic first-answer handling across phone/laptop races and crashes.

  Render untrusted descriptions inertly, with no remote resources or executable markup. Test the complete readable mail on-device. For the passcode-resistant claim, require a key bound to the current biometric enrolment with no passcode fallback; changing Face ID must invalidate it. Apple documents this distinction through [`biometryCurrentSet`](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/biometrycurrentset). The owner’s approval of this new surface remains open.

- **Brief 20’s list is broad, but incomplete.** [CONTROL.md:940](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:940). Add explicit tests for the blockers above; payload-bearing WebSocket **ping and pong**, not just messages/closes; actual web-push delivery with an independent publisher; trusted-action batch/preceding-message substitution; revocation racing release; and the full 15-minute approval lifecycle with HTTP/2 cancellation. Service tests must include fresh downloads and working positive controls under active guards. Preserve the twice-run, version-recorded receiver qualification and upgrade checks.

- **Correct the remaining overstatements.** [CONTROL.md:885](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:885) should promise **at-most-once forwarding**, not guaranteed once-only delivery: crashes can produce no delivery or partial delivery. The residuals otherwise explain the major limitations well. [STATE.md:100](/Users/pab/AresOS-council-control-layer/STATE.md:100) should reflect all three completed phone tests rather than describing the check as still in progress.
