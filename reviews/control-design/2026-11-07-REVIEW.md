The design needs changes before brief 18. It preserves sending and the owner’s signed-in tabs, but it does **not** yet deliver the full feature scope or the promised approval boundary.

This is a read-only review of [CONTROL.md](../../docs/design/CONTROL.md), including the 17c addition that appeared during review. I checked current Anthropic documentation; I ran no runtime tests. Tests below are proposed acceptance tests. I have not counted the known 17b work as new findings.

1. **Blocking — The two-socket boundary cannot be configured as described on Linux. (§§2, 7)**

   **Scenario:** The implementation allows `read.sock` through `sandbox.network.allowUnixSockets`. Linux ignores that list. Enabling `allowAllUnixSockets` to make the CLI work also permits connections to other reachable Unix sockets. Without the optional seccomp filter, Unix-socket blocking is absent even though the sandbox can start. These are documented behaviors. [Anthropic’s socket settings](https://code.claude.com/docs/en/settings-reference#sandboxnetworkallowunixsockets), [Linux sandbox dependencies](https://code.claude.com/docs/en/sandboxing#set-up-linux-and-wsl2).

   **Impact:** Either terminal reads fail, or Claude can potentially reach `act.sock` and perform sends, deletion and owner-only configuration without an MCP prompt.

   **Fix:** Prove a Linux-specific boundary first: a protected namespace/relay arrangement exposing only the read service, with action sockets, desktop buses and alternate socket paths inaccessible. Do not solve this by enabling every socket.

   **Test:** On the intended Linux image, run hostile programs that connect directly to both sockets, the native host and session buses. Reads must work; every action route must fail. Repeat with missing seccomp support and require startup refusal.

2. **Blocking — Managed configuration does not yet close every route to unsandboxed execution or self-approval. (§7)**

   **Scenario:** A managed MCP or hook definition invokes a script, interpreter or dependency inside a writable work folder. Claude edits it; reconnecting runs the replacement outside the sandbox, where `act.sock` is available. Separately, trusting `claude.ai` for ordinary browser use could expose the signed-in Remote Control approval surface to Claude.

   **Impact:** The agent gains the same authority as the owner without the intended prompt.

   **Fix:** Protect executable dependencies, imports, launch environment and configuration—not just the managed JSON. Inventory LSP servers, helpers and plugins alongside MCP and hooks; Anthropic documents that these processes can run outside the shell sandbox. Protect Claude authentication/session files and exclude approval/admin surfaces from browser automation. [Sandbox scope](https://code.claude.com/docs/en/sandboxing#what-runs-outside-the-sandbox).

   Correct two settings claims: `allowManagedMcpServersOnly` restricts the **allowlist**, whereas the already-proposed `managed-mcp.json` establishes the fixed server set; `allowManagedHooksOnly` also admits SDK hooks and hooks from force-enabled plugins. [Managed MCP](https://code.claude.com/docs/en/managed-mcp), [Hook settings](https://code.claude.com/docs/en/settings-reference#allowmanagedhooksonly). The proposed file-write choice also omits the current `blockWritesOutsideWorkingDirectories` control; it still needs protection for executable/configuration paths inside those directories. [File-tool restrictions](https://code.claude.com/docs/en/permissions#block-file-tool-reads-and-writes-outside-the-working-directories).

   **Test:** Attempt executable substitution, dependency shadowing, helper/plugin activation, restart-based escape and browser-based approval of a pending operation. Use deterministic hostile clients as well as model tests.

3. **Blocking — “Known sites” and sandbox host allowances do not enforce approval before disclosure. (§§6, 7, 10)**

   **Scenario:** An injected mail induces navigation to an already-known site with another mail’s contents in the URL. Alternatively, it uses `WebFetch`, `WebSearch` or a shell request. In bypass-permissions mode, the sandbox permits unlisted hosts unless the additional strict/managed allowlist control is enabled; its domain list does not constrain the built-in web tools. [Anthropic’s network behavior](https://code.claude.com/docs/en/sandboxing#hosts-outside-your-allowed-domains).

   **Impact:** A site receives private data without a send prompt. First-visit approval does not prevent subsequent disclosures, and a familiar hostname can host attacker-controlled content.

   **Fix:** Keep “known” separate from permission to transmit. Define permitted destinations and operations, including URLs, queries, redirects, subresources and local-network destinations. Lock shell egress and separately govern built-in web tools. Ordinary access to a domain must not authorize arbitrary payloads to it.

   **Test:** Send a synthetic secret through a known-site URL, search query, redirect, third-party resource, `WebFetch`, `WebSearch` and shell request. Each prohibited disclosure must produce zero receiver arrivals.

4. **Blocking — Chrome’s classifier releases delayed actions and loses responsibility when data changes context. (§6)**

   **Scenario:** Clicking Delete schedules `POST /delete?id=42` twelve seconds later. It contains no typed text, so both action-window and typed-text rules miss it. A checkbox can similarly autosave a boolean; an uploaded file can leave later as binary data. After `chrome_drop`, the page can retain and retry the operation. A popup or another same-origin tab can receive the data and transmit outside the controlled tab.

   **Impact:** Sending or deletion occurs without approval, including after the tool reported completion or cancellation. The proposed 17c message wrappers do not repair this HTTP classification rule.

   **Fix:** Track the complete operation across its lifetime and execution contexts. Do not infer harmlessness from method, timing or absence of typed text. Unknown mutations need a qualified adapter or refusal. Dropping a request must revoke its operation; releasing a tab must address retained drafts, queues and retries. Child targets need protection before execution—Chrome’s target attachment is not automatically recursive. [Chrome debugger documentation](https://developer.chrome.com/docs/extensions/reference/api/debugger#attach-to-related-targets).

   **Test:** Delayed deletion, checkbox autosave, binary uploads, retries after drop/release/restart, nested frames, popup submissions and cross-tab message relays. Inspect receiver state after the original action has finished.

5. **Blocking — Deletion can bypass its gate, and folder deletion does not identify the approved set. (§§3, 5, 6)**

   **Scenario:** Claude calls free `mail_move(..., Trash)` instead of asking `mail_delete`. On a trusted website, `chrome_submit_trusted` can release a deletion because Chrome has no separate deletion classification. For `mail_folder_delete`, ten newsletters can be replaced by ten important messages while approval waits; the displayed count still matches.

   **Impact:** Unprompted deletion or deletion of messages the owner never reviewed.

   **Fix:** Reject Trash/destructive destinations in the free move operation. Submission trust must not silently exempt deletion. Bind bulk deletion to an explicit message set. A count check followed by IMAP `DELETE` is insufficient: that command removes the mailbox’s current contents, and ordinary IMAP supplies no conditional deletion matching the proposed snapshot. Use exact UID deletion and a separately justified folder-removal strategy. [IMAP deletion semantics](https://www.rfc-editor.org/rfc/rfc9051.html#section-6.3.5).

   Also prohibit cleanup through writable-mailbox `CLOSE`, which can expunge unrelated messages already marked deleted. [Python’s `close()` behavior](https://docs.python.org/3/library/imaplib.html#imaplib.IMAP4.close).

   **Test:** Free move-to-Trash; deletion on a submission-trusted site; same-count mailbox replacement; delivery between validation and deletion; unrelated `\Deleted` messages surviving normal cleanup.

6. **Blocking — File transfer turns the protected service into an unrestricted file-access intermediary. (§§4–6)**

   **Scenario:** An attachment path is a symlink to a service-readable credential file. `mail_compose` supplies its hash and a later upload/send consumes it. Conversely, attachment saving accepts an arbitrary destination folder and could overwrite service state or executable configuration if writable. Hashing a file and reopening it later also permits replacement between validation and transmission.

   **Impact:** Credential disclosure, corrupted service state, or execution outside the agent sandbox. Separating credentials by Unix user does not protect them from the service’s own unrestricted operations.

   **Fix:** Define the cross-user file boundary explicitly. Import only authorized regular files into immutable service-owned blobs; send those exact bytes. Export into designated user directories with safe filename handling, no traversal, no symlink following and no silent overwrite. Establish ownership and access without granting the service broad access to the owner’s home.

   **Test:** Credential-path inputs, symlink/hard-link cases, traversal filenames, destination collisions, source replacement during hashing/transmission, and attempted writes into service/configuration directories.

7. **Blocking — A gesture or opaque network payload is not a truthful preview of the resulting action. (§§4, 6)**

   **Scenario:** `chrome_submit_input` shows “type this text and press Enter,” but the page sends to a different conversation or sends additional existing fields. A held request contains an opaque object ID while the owner sees no trustworthy identification of the item being deleted. During a phone approval, the same DOM element remains but its account or target changes.

   **Impact:** The owner approves different—or materially less specific—information than the operation that executes. Matching a raw hash proves byte equality, not that the owner understood the effect.

   **Fix:** Use a service-validated operation description containing the action, authenticated account, destination/target, material data and attachment identities. Bind it to relevant page state and reject changes. Where a generic browser gesture cannot establish those facts, use a qualified site adapter or refuse the guarantee.

   The S1 finding is valid: explicit ask/deny rules survive bypass mode. But that does not prove complete rendering on every approval surface. [Permission-mode rules](https://code.claude.com/docs/en/permission-modes#actions-no-mode-auto-approves). Remote Control forwards permissions, but its documentation does not establish this design’s full-payload display contract. [Remote Control](https://code.claude.com/docs/en/remote-control).

   **Test:** Changed recipients/accounts/targets during approval, opaque and multipart payloads, large nested inputs, control/bidirectional characters, and full desktop/phone rendering. Unreviewable inputs must fail before execution.

8. **Blocking — The outcome and recovery model cannot represent partial effects safely. (§§4–6)**

   **Scenario:** SMTP accepts recipient A but rejects B; `smtplib.sendmail()` can return normally in that case. SMTP then succeeds but saving Sent or setting `\Answered` fails. Alternatively, the process crashes after acceptance but before recording completion. [SMTP client behavior](https://docs.python.org/3/library/smtplib.html#smtplib.SMTP.sendmail).

   **Impact:** Neither `done` nor “failed, nothing happened” describes the result. Recovery can misreport delivery or repeat an irreversible action. In this design, absence from Sent is particularly weak evidence: the client creates that copy only after observing SMTP success.

   **Fix:** Define a durable operation state machine before the adapters: reserve the operation before irreversible I/O, bind its ID to immutable input, record per-recipient and per-stage outcomes, and return existing status on retry. Separate submission, Sent-copy and flag repairs. Add status/reconciliation tools, expiry, cancellation boundaries and restore-generation rules. A lost HTTP response or closed tab after release must not become “nothing sent”; an HTTP response alone must not mean the business operation succeeded.

   **Test:** Partial recipient rejection, failure at every post-send stage, concurrent duplicate calls, crashes at each persistence boundary, cancellation after acceptance, expired approvals and restoration of older state. Repairs must never resubmit mail.

9. **Should-fix — Mail compatibility is chosen before the provider is known, and the Sent-copy assumption is false. (§5)**

   **Scenario:** The actual account requires an authentication flow absent from the password-only adapter, or the provider already saves submitted messages in Sent. Gmail explicitly does the latter. [Gmail’s client guidance](https://support.google.com/mail/answer/78892?hl=en-GB).

   **Impact:** A passing GreenMail build cannot serve the owner, or creates duplicate Sent copies. Provider-specific Trash/label behavior can also differ from the assumed folder model.

   **Fix:** Identify provider, supported authentication, identities, special folders and submission behavior privately before committing to the production adapter. Configure Sent handling explicitly; discover special-use folders instead of relying on English names. Capabilities must be exposed to Claude, not discovered only by failed actions.

   **Test:** Provider-specific synthetic profiles covering authentication renewal/revocation, automatic versus client-created Sent copies, localized folders, label semantics and unsupported operations.

10. **Should-fix — Reply/thread correctness is underspecified and excludes archived conversation members. (§5)**

   **Scenario:** An invoice is moved to Archive, then `mail_thread` searches only Inbox and Sent. Replying to a list message uses From instead of Reply-To, or replying to the owner’s own sent message addresses the owner. The compose contract lists In-Reply-To but does not specify building the References chain.

   **Impact:** Incomplete conversations, wrong recipients, broken threading and incorrect “needs an answer” results.

   **Fix:** Thread across the relevant account folders; retain physical UID references separately from conversation identity and handle missing/duplicate Message-IDs. Specify Reply-To, own aliases, reply-all/Bcc behavior, References construction, quotation and forwarded-attachment rules. [Message and reply semantics](https://www.rfc-editor.org/rfc/rfc5322.html#section-3.6.4).

   Define wire encoding as well: MIME structure, transfer encoding, encoded headers, international addresses, line endings and decoded attachment hashes. “Plain UTF-8” alone is insufficient. Make verified TLS contexts explicit in the chosen Python implementation; `IMAP4_SSL`’s default context does not verify certificates. [Python TLS warning](https://docs.python.org/3/library/imaplib.html#imaplib.IMAP4_SSL).

   **Test:** Archived threads, duplicate/missing IDs, aliases, mailing-list Reply-To, replies to sent mail, Bcc privacy, nested forwarded mail, non-UTF-8 input, non-ASCII filenames/addresses, unsupported SMTPUTF8, and certificate/downgrade failures before authentication.

11. **Should-fix — Stable element identity does not protect concurrent owner edits or page-view consistency. (§6)**

   **Scenario:** The owner corrects a field after `chrome_read`; `chrome_fill` overwrites it because the element still exists. A single-page application changes rows while a cursor remains valid because the document did not navigate.

   **Impact:** Lost manual work and snapshots assembled from different page states. Tab switching tests do not establish protection against these cases.

   **Fix:** Bind actions to expected relevant values/state, and bind pagination to a view revision. Include browser-session/profile identity and invalidate references across restarts. Specify tab-group ownership independently of its editable display name, plus restoration of the tab’s previous grouping when released.

   **Test:** Concurrent field edits, reused row nodes, same-document route changes, pagination during mutations, duplicate group names, multiple windows/profiles and restart with old references.

12. **Should-fix — The tool workflow lacks a usable contract for late holds, multi-request actions and large content. (§§4–6)**

   **Scenario:** Autosave becomes held after `chrome_fill` has returned and Claude has finished its turn; no subsequent `chrome_submit` call exists to trigger the owner’s prompt. A form upload produces several requests, requiring several approvals despite PLAN’s “one asking step.” A large forward exceeds the bounded result size, but `mail_send` requires Claude to reproduce the complete message.

   **Impact:** Silent pending work, excessive calls/prompts, or accidental truncation and reconstruction errors.

   **Fix:** Add operation status and notifications for late holds; define completion independently of network quiet. Group qualified multi-request operations into reviewable approval units. Provide form-scoped reads, option discovery and safe batch filling. Define how complete large messages reach the approval input without silently truncating or relying on Claude to reconstruct them.

   **Test:** Fresh tool-user rounds with delayed autosave, multipart/multi-request forms, a long quoted thread and a large invoice batch. Record calls, approvals, latency and corrections; set acceptance budgets before judging usability.

13. **Should-fix — “Every app, every feature” has been narrowed without an explicit coverage plan. (§§5–6)**

   **Scenario:** The owner requests a formatted mail, updates an existing draft, manages Chrome downloads/bookmarks, closes a tab, handles a JavaScript dialog or works in an editor without a sufficient accessibility representation. The action list provides no complete route.

   **Impact:** The design delivers a useful subset while claiming the owner’s complete picture. The concrete narrowing includes plain-text outgoing mail, password-based mail access, Inbox/Sent-only threads, and a Chrome surface centered on ordinary page controls. The tab group itself preserves real signed-in tabs; it does not solve the missing features.

   **Fix:** Create a feature inventory for Mail and Chrome with an explicit tool, qualification test or acknowledged unsupported state for each feature. Preserve the owner’s completeness requirement; do not turn unsupported workflows into silent omissions or universal screenshot fallback.

   **Test:** Derive acceptance tasks from that inventory, including browser-level functions and representative complex web applications, beyond PLAN’s fourteen examples.

14. **Should-fix — The two-week schedule depends on unresolved architecture, and qualification comes too late. (PLAN order)**

   **Scenario:** Core is built around the proposed sockets, Mail around password IMAP, and Chrome around request replay. Linux isolation, provider behavior or 17b/17c then forces a redesign after both adapters depend on the core.

   **Impact:** There is no defensible commitment to complete, secure feature coverage by November 21. Containers can validate a prototype, but cannot establish the missing production boundaries.

   **Fix:** Before core, settle the Linux boundary, operation/approval contract, provider requirements and browser feasibility gates. Prove managed settings and desktop/phone approval using the fake app; final tool-name lists can still wait. Bring a minimal nonpublishing image test and registry-access solution forward. Core followed by Mail and Chrome in parallel is sensible **after those contracts stabilize**. Avoid an unnecessary port of the browser prototype before its behavior is qualified.

   **Test:** Require an early end-to-end fake send in the actual image, including hostile bypass attempts and phone approval. Re-estimate from passing gates and the feature inventory, with time reserved for tool-user fixes and the final security review.

The questions only the owner can settle are:

- **When free navigation/search/typing conflicts with guaranteed approval before disclosure, which wins?** Recommendation: preserve the approval guarantee; “known” must not imply permission to transmit arbitrary data.
- **Exactly what does a trusted-site exception authorize?** Recommendation: explicit origins and operations; deletion and approval/admin interfaces remain excluded.
- **Which mail provider, authentication method, aliases and special-folder behavior must work?** Recommendation: provide this privately before the Mail brief; credentials can wait until onboarding.
- **What constitutes complete first-release Mail and Chrome coverage?** Recommendation: approve a feature inventory, retain sending and real tabs from the start, and resolve HTML mail and browser-level functions explicitly.
- **How much general coding/network authority must the central session retain?** Recommendation: keep its app authority constrained; place broader recovery/development execution behind a separately confined or owner-operated route.
- **If completeness and the November 21 deadline conflict, which moves?** Recommendation: move the deadline, consistent with “do it completely right, or leave it.”
