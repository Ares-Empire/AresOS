# Design re-check 29: draft 26 (decision 25, Chrome as the light tool)

Reviewer: Codex `gpt-6-astra`, fresh context, 2026-11-08. Reviewed draft 26 on `control/chrome-light`.

Blocking findings:

- [CONTROL §6, asking rules](/Users/pab/AresOS-design-chrome/docs/design/CONTROL.md:406) miss activation paths. Enter or Space on a focused “Send” or “Delete” button is neither the specified click nor Enter in an editable field. Script submissions cover click/key handlers but omit input/change handlers triggered by filling, selecting or checking. Apply classification across those paths. For intercepted submissions, define how approval resumes the blocked submission without replaying the originating input.

- [Approval binding](/Users/pab/AresOS-design-chrome/docs/design/CONTROL.md:442) is incomplete. The comparison lists element identity/label and form values, but omits generic compose text outside forms, displayed account, effective submission destination, and confirmation-dialog identity/text. Those can change while the listed checks still pass. Include all described state in the question and comparison. “Belongs to an action he just approved” also needs an exact scope; a newly displayed confirmation must not inherit approval merely because it followed that action.

- [Navigation](/Users/pab/AresOS-design-chrome/docs/design/CONTROL.md:402) permits “any address” without a scheme restriction. A fixed DevTools method list alone does not establish the promised absence of script access: [`javascript:` navigation executes script](https://html.spec.whatwg.org/multipage/browsing-the-web.html#javascript-protocol). Explicitly restrict navigation schemes. Specify approval/settings-page exclusion across taking existing tabs, redirects, popups, history navigation and embedded frames, with checks before reading or acting.

Should-fix:

- [Brief 20’s password test](/Users/pab/AresOS-design-chrome/docs/design/CONTROL.md:556) checks only that passwords disappear from results. That does not prove they were never read. Brief 17’s referenced reader uses bulk DOM snapshots; [Chromium includes input values in those snapshots](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/inspector/inspector_dom_snapshot_agent.cc). Require an extraction path and tests that avoid collecting password values, including form serialization.

- Reconcile remaining contracts: [FEATURES’ Files table](/Users/pab/AresOS-design-chrome/docs/control/FEATURES.md:61) and rule 4.4 promise controlled download saving, while §6 makes downloads ordinary Chrome downloads and the tool read-only. Section 10 still says every send through the tools asks. Section 10 places classification/binding in Python, while §6 places the immediate checks in the extension. Section 4.3’s “release, site’s answer” needs outcomes appropriate to dispatched input without network inspection.

- Brief 20 should retain crash/restart, cancellation, adapter-update permission-scope and repeated qualification tests alongside the missing cases above.

Decisions 24 and 25 are faithful overall; the checkpoint removal is consistent across the main plan and STATE. The same-named user-host precedence claim is [correct](https://raw.githubusercontent.com/chromium/chromium/main/chrome/browser/extensions/api/messaging/launch_context_posix.cc) and fits the accepted same-user bypass. However, §2 should not describe Chrome’s control channel as unreachable when §6 expressly permits host impersonation.
