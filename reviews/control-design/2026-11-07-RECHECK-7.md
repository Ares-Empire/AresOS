# Design re-check 7: what brief 17d means for Chrome, and the options for a send boundary that fails closed

Reviewer: Codex `gpt-6-astra`, xhigh, read-only, fresh context, 2026-11-07. Reviewed draft 9 (`46ef611..00d205f`), brief 17d's report and code (`origin/pkg/17d-chrome-floor`, PR #8) and Chromium 157.0.8103.38 source. Asked as an options review: B1 a local intercepting proxy owned by the tool service, B2 a narrower design inside Chrome, B3 anything else.

**A. 17d’s conclusions stand; draft 9 is not a fail-closed send boundary.**

I reviewed the report, relevant harness code, draft-9 changes and Chromium source; I did not rerun Chrome. Versioned source links below target **157.0.8103.38**. API documentation was checked today.

- **False:** the floor covers every worker’s live connections. Chromium explicitly declines extension interception when a WebSocket has no frame. This supports 17d’s receiver evidence; worker HTTP and WebTransport results do not repair it. [Chrome 157 source](https://github.com/chromium/chromium/blob/157.0.8103.38/chrome/browser/chrome_content_browser_client.cc#L6526)
- **False:** an allowance authorizes exactly one request’s approved bytes. DNR has no body-hash condition or atomic consumption counter. Removing the rule cannot recall an admitted request. The 24/24 trials demonstrate a deterministic failure at the selected interruption point, **not a 100% probability during ordinary use**. Draft 9 acknowledges an instant of exposure, but that concession contradicts the owner’s required boundary. [DNR conditions](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest#type-RuleCondition)
- **False in the tested lifecycle:** allowances necessarily disappear on reload/update/crash. Interestingly, Chrome’s documentation says session rules clear on installation of a new extension version; 17d’s observed update survival conflicts with that description. Treat the observed behavior as controlling until explained; startup cleanup cannot protect an earlier request. [Ruleset lifetime](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest#dynamic-and-session-scoped-rulesets)
- **Still holds:** correctly scoped HTTP blocks precede Fetch in the tested cases; persistent blocks protect tested restored documents and worker HTTP; cooperative page holds survive tested interruptions; complete finite bodies can sometimes be frozen.
- **Unproven:** universal account binding, complete upload capture, authenticated-site usability and automatic guard retirement. Missing storage events cannot prove nothing was stored, especially with the demonstrated named-property escape. The debugger’s restricted domains confirm the observation limitations. [Debugger domains](https://developer.chrome.com/docs/extensions/reference/api/debugger#restricted-domains)

Administrative removal genuinely removes enforcement. Under this owner’s threat model, however, **Claude changing root-owned policy is excluded**. That result establishes the boundary’s dependency on administration; it is not independently a Claude escape.

**B. Options**

**B1 — Recommend investigating a strengthened version.** An external proxy can own the bytes and release decision independently of Chrome. Use managed [ProxySettings](https://github.com/chromium/chromium/blob/157.0.8103.38/components/policy/resources/templates/policy_definitions/Miscellaneous/ProxySettings.yaml), one fixed proxy, no DIRECT entry, and `<-loopback>` to remove implicit localhost/link-local bypasses; also require OS enforcement that Chrome can reach only the proxy. Chrome documents failure rather than direct fallback for a sole unavailable proxy. [Proxy behavior](https://github.com/chromium/chromium/blob/157.0.8103.38/net/docs/proxy.md) **Decrypt ordinary web traffic continuously from browser launch.** Activating interception later cannot decrypt existing opaque tunnels; HTTP/2 reuse and worker sockets make a tab reload insufficient. Selective decryption requires closing every potentially affected tunnel before input, with potentially profile-wide disruption. Reevaluate existing inspected connections when a guard starts, before acknowledging permission to act. Attribution needs strengthening: `Sec-Fetch-Site` supplies a relationship, not a source identity; Origin can be absent or opaque. [Fetch Metadata](https://web.dev/articles/fetch-metadata), [Origin rules](https://fetch.spec.whatwg.org/#origin-header) A DNR tab header is supporting evidence, not authorization: overwrite it, bind it to the current browser/document generation, strip it, and test forgery and stale reuse. Missing attribution must hold potentially guarded traffic **regardless of destination**; cross-context handoffs can require a broader guard, potentially the whole profile. Gate WebSocket handshakes, data and payload-bearing close frames. Refuse unsupported tunnels. WebRTC’s policy permits TCP proxying; its data channels remain DTLS encrypted, so an HTTPS interceptor cannot inspect them merely by installing a CA. [Policy](https://github.com/chromium/chromium/blob/157.0.8103.38/components/policy/resources/templates/policy_definitions/WebRtc/WebRtcIPHandling.yaml), [WebRTC transport](https://chromium.googlesource.com/external/webrtc/+/master/pc/g3doc/dtls_transport.md) Block those paths unless separately qualified. Chrome 157’s WebTransport client rejects a configured proxy but still contains a TODO for checking QUIC policy: do not credit `QuicAllowed=false` alone. [Source](https://github.com/chromium/chromium/blob/157.0.8103.38/net/quic/dedicated_web_transport_http3_client.cc#L721) Policy CA installation is supported from Chrome 132; valid locally trusted certificates are compatible with HSTS, and Chrome exempts private trust anchors from its pinning and CT checks. The proxy must independently validate upstream TLS. [CA policy](https://github.com/chromium/chromium/blob/157.0.8103.38/components/policy/resources/templates/policy_definitions/CertificateManagement/CACertificates.yaml), [Security FAQ](https://github.com/chromium/chromium/blob/157.0.8103.38/docs/security/faq.md)

**B2 — Reject as a fail-closed solution.** Dropping fail-then-repeat removes an awkward workflow, but ordinary approved releases still need the same unsafe allowance. A tab-specific URL/method match remains incapable of distinguishing competing bodies. Refusing existing workers also needs protection against subsequent registration, replacement and activation; an inventory check is insufficient. Adapters must establish an enforceable path, not merely recognize a message. Claude could still read, navigate and fill eligible conventional pages, but that does not qualify generic sends. Webmail requires individual qualification; chat applications whose essential sends use worker sockets are excluded. GraphQL applications need operation-aware classification: `/graphql` cannot be broadly allowed, and “query” is not independent proof of harmless server behavior. Persisted queues, existing sockets and incomplete storage observations remain.

**B3 — Useful additions, no cheaper complete replacement.** A network namespace supplies B1’s routing enforcement but cannot inspect encrypted operations. Policy-installed extensions can use `webRequestBlocking`, but this does not supply WebSocket-message interception or repair frameless interception. [Chrome API](https://developer.chrome.com/docs/extensions/reference/api/webRequest) Native service-side adapters are attractive for selected operations, provided browser-originated sends remain contained. Patched Chromium could implement an actual atomic network gate, including worker sockets, but becomes a maintained browser fork rather than branded stable Chrome: continual security rebasing, distribution and compatibility work. Its documented build requirements alone include 100 GB free space and recommend more than 16 GB RAM. [Build requirements](https://github.com/chromium/chromium/blob/157.0.8103.38/docs/linux/build_instructions.md)

**C. Recommendation, limits and brief 17e**

Recommend **B1 with OS-enforced routing**, as a qualification project before the Chrome build.

The defensible guarantee is narrow: **a supported operation already held by the proxy cannot escape because the extension detaches, reloads or disappears.** The proxy must hold request headers as well as bodies, persist the guard before input, and durably consume authorization before forwarding. Release the captured operation itself; never open a temporary URL allowance.

Promise **at-most-once forwarding**, not exactly-once business execution. A crash after dispatch can leave the result unknown; recovery must not replay it automatically.

Cancellation also needs honest wording. An observed abort, closed stream, expired lease or vanished document before dispatch cancels the operation. A JavaScript timeout may never cancel the network request, and cancellation can race dispatch. “Never send after the page internally gave up” is unachievable without a qualified page/adapter contract; a connected socket is insufficient evidence.

Owner-readable residuals:

- “A website can disguise sending as traffic we permit for reading.” Mutating GETs and opaque protocols require adapters or refusal; hostile-page confidentiality remains outside the generic guarantee.
- “The tool can preserve approved bytes without understanding what the server will do with them.” Account, target and operation descriptions still need qualification.
- “A network checkpoint cannot prevent deletion of data stored only in the browser.” Such deletion needs approval before the local action.
- “If the checkpoint breaks, online browsing stops.” Unsupported sites must fail visibly, without a direct fallback.

Day to day, the owner keeps the same profile and sign-ins, but autosaves and some owner clicks wait; live applications may disconnect or require adapters. Whole-profile uncertainty could affect unrelated tabs. The proxy sees passwords, cookies and page contents: keep payloads transient, bound buffers, protect temporary storage, omit secrets from logs, and never expose unrelated traffic to Claude. Its upstream TLS/HTTP2 implementation changes the observable connection fingerprint; additional bot challenges are plausible but **unverified**. Latency, CPU and memory costs are also unmeasured.

Chrome services need separate qualification. `CACertificates` is profile-scoped, while Chrome constructs a separate system network context; assuming every service accepts that root is unsafe. Test Sync, Safe Browsing, extension/component updates and push. Neither a Google hostname nor missing Origin establishes a safe exemption. [System context](https://github.com/chromium/chromium/blob/157.0.8103.38/chrome/browser/net/system_network_context_manager.cc#L1064)

**#67 still makes sense as a sufficient condition, not a generic automatic feature.** The proxy adds no proof about storage. Unknown observations must retain the guard; modern applications may therefore remain guarded until adapter evidence or explicit owner termination. Ending a guard authorizes possible future transmission of leftovers; that consequence must be visible.

**17e must answer these questions, with independent receiver logs and positive controls:**

1. **Can traffic bypass the proxy?** Exercise IPv4/IPv6, localhost/link-local, redirects, workers, QUIC and proxy failure. **Pass:** no direct application delivery; restored Chrome cannot transmit before persistent guards load.
2. **Does activation cover existing connections?** Preopen HTTP/2 connections and page/shared/service-worker sockets; activate during concurrent traffic. **Pass:** no post-activation unapproved operation escapes; input starts only after barrier acknowledgement.
3. **Is attribution conservative?** Test opaque/absent Origin, foreign frames, cross-origin handoffs, redirects, forged/stale/missing headers and extension removal. **Pass:** uncertainty broadens containment or refuses input; it never grants release.
4. **Are complete operations held?** Test multipart disk files, binary bodies, chunking, compression, WebSocket fragmentation and close reasons. **Pass:** zero upstream operation bytes before approval; approved payload hashes match; incomplete/oversized inputs fail closed.
5. **Can another request consume approval?** Race identical and different bodies, headers, accounts and documents. **Pass:** authorization identifies one captured operation; competitors remain held; changed context requires renewed approval.
6. **What happens at every crash point?** Kill extension, host, proxy and browser before/after durable consumption and during transmission. **Pass:** zero unapproved arrivals, no recovery replay, and uncertain dispatched results remain unknown.
7. **Does cancellation work?** Exercise AbortSignal, HTTP/2 reset, tab closure, wrapper timeout and late approval. **Pass:** acknowledged cancellation before dispatch prevents delivery; unobservable timeouts are refused or explicitly unsupported.
8. **Are alternate transports contained?** Use working WebTransport and WebRTC peers, including TURN/TCP/TLS. **Pass:** unapproved payloads never arrive; blocked protocols are reported as unavailable.
9. **Does TLS remain secure?** Test policy-root installation, HSTS, pinned destinations, invalid upstream certificates and browser services. **Pass:** supported traffic succeeds without certificate-error flags; invalid upstream authentication fails; service exceptions cannot carry page sends.
10. **Can guards retire safely?** Replay offline outboxes, named-property storage, OPFS, handoffs and browser restart. **Pass:** positive or incomplete evidence retains guards; only independently qualified resolution retires them.
11. **Is it usable and private?** Measure representative signed-in test accounts, bot responses, prompt counts, latency and resource exhaustion. **Pass:** agreed budgets hold, logs contain no credentials, buffers stay bounded, and exhaustion never enables forwarding.

Run the complete qualification twice on the recorded branded-Chrome version. Passing synthetic fixtures must not be presented as qualification of arbitrary real sites.
