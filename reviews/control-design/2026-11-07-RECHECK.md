1. **FIXED — Linux socket boundary (§2).** Removing terminal access to every service socket eliminates the unsupported Linux socket allowlist; filesystem hiding, seccomp and missing-filter qualification now form a coherent design. Anthropic confirms the documented Linux limitation and optional-filter behavior. [Sandbox documentation](https://code.claude.com/docs/en/sandboxing#set-up-linux-and-wsl2)

2. **PARTLY — Unsandboxed execution and self-approval (§7), blocking.** The MCP executable/dependency protections and approval-page exclusions are substantial fixes, but hooks and helpers still lack the proxy’s explicit interpreter, import and environment protections. Apply those protections to every executable chain and constrain the launch integrations: Anthropic still permits SDK hooks and in-process MCP servers under the proposed managed controls. [Hook exceptions](https://code.claude.com/docs/en/settings-reference#allowmanagedhooksonly), [managed MCP exceptions](https://code.claude.com/docs/en/managed-mcp#exclusive-control-with-managed-mcp-json)

3. **PARTLY — Disclosure without approval (§§6–7), blocking.** The strict shell-domain policy and separate `WebFetch` rule fix those omissions, but `WebSearch` remains ungoverned, and GET/subresource traffic without recognizable typed text still receives an unjustified reading exemption. Apply the chosen disclosure policy to `WebSearch` separately and define enforceable destination/operation rules covering redirects, subresources and local-network targets; the sandbox does not govern built-in web tools. [Anthropic’s sandbox scope](https://code.claude.com/docs/en/sandboxing#what-runs-outside-the-sandbox)

4. **PARTLY — Delayed actions and execution contexts (§6), blocking.** Holding non-GET requests regardless of timing fixes delayed POSTs, checkbox autosaves and ordinary binary uploads, while controlling child targets before execution is the right requirement. However, warning about uncontrolled same-site tabs does not prevent their transmissions, and dropping currently held requests before releasing a tab does not revoke its retained drafts/retries; require confinement or refusal, plus safe release of the whole operation.

5. **PARTLY — Deletion gates and approved message sets (§§5–6), blocking.** Rejecting move-to-Trash, using exact UIDs and prohibiting writable-mailbox `CLOSE` are correct, but a private mailbox name is not a concurrency lock, and a trusted-site POST behind a button labelled “Confirm” still evades the deletion heuristic. Require exact-UID deletion plus a provider-proven exclusion strategy—or refuse folder removal—and qualify trusted operations semantically rather than through HTTP methods or button labels. [IMAP deletion and rename semantics](https://www.rfc-editor.org/rfc/rfc9051.html#section-6.3.5)

6. **PARTLY — File-access intermediary (§4.4), blocking.** Immutable blobs and restricted exports address important parts, but moving imports into the owner’s MCP proxy makes owner-readable credentials accessible through an otherwise free attachment/upload operation: only exports have explicit allowed directories. Restrict imports to authorized roots or file grants, exclude credentials/configuration, and enforce containment and link/race protections inside the proxy; Claude Code’s file-tool restrictions do not constrain MCP tools. [Permission-control scope](https://code.claude.com/docs/en/permissions#block-file-tool-reads-and-writes-outside-the-working-directories)

7. **PARTLY — Truthful approval (§§4.1, 6), blocking.** Service-generated descriptions, state binding, escaping and early phone qualification improve the contract, but `chrome_submit_input` still approves a gesture without establishing the resulting recipient, payload or authenticated account. Require a qualified adapter before that path executes, otherwise refuse; page-provided labels and a matching request hash do not establish those facts.

8. **PARTLY — Outcomes and recovery (§4.3), blocking.** Durable reservation, per-recipient/per-stage outcomes, status tools and repairs substantially fix partial delivery and retry handling. Restore protection still needs an independently retained generation/high-water mark—restoring the log and its own generation together defeats the stated check—and cancellation must have a defined boundary relative to reservation, release and acceptance.

9. **FIXED — Provider compatibility and Sent handling (§5).** The design now records the privately established provider requirements, exposes capabilities and aliases, discovers special folders, and explicitly configures server-created versus client-created Sent copies. Real-account onboarding remains a clearly identified verification step.

The changes introduce two additional consequences:

- **Should-fix — Folder quarantine renames unapproved descendants.** With the [new rename-before-delete strategy](../../docs/design/CONTROL.md:186), deleting an empty `Projects` folder can also rename `Projects/Invoices`, leaving it under the private prefix when the parent is deleted or removal fails. IMAP requires hierarchical descendants to follow a rename; reject such folders or explicitly include and journal all descendant effects and recovery, rather than treating the rename as invisible preparation. [IMAP RENAME](https://www.rfc-editor.org/rfc/rfc9051.html#section-6.3.6)

- **Should-fix — Background holds can repeatedly block unrelated tab actions.** Under the [revised hold rules](../../docs/design/CONTROL.md:287), a dashboard that retrieves data through periodic POST requests continually creates background holds, while any hold prohibits further filling or clicking. Qualify read-only background operations where possible and scope action blocking to conflicting operations; test sustained polling, rather than measuring only how many background requests appear.

Explain that separation needs an enforced boundary, and that asking only for `git push`/`gh` does not cover other transmissions to allowed hosts.

Explicit ask rules do survive bypass mode. [Remote Control](https://code.claude.com/docs/en/remote-control), [permission modes](https://code.claude.com/docs/en/permission-modes#actions-no-mode-auto-approves)

- **Readable/writable folders: fairly framed.** Recommend narrow named directories, with credentials and executable configuration excluded.
