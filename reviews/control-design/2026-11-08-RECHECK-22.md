At [CONTROL.md:1575](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1575), first arrival still does not authenticate the intended relay. The startup premise is unsafe: Anthropic documents background MCP connections by default, and even blocking startup has a deadline after which pending connections continue in the background. A delayed or killed **not-yet-registered** relay leaves its slot available for the hostile direct child. Require registration bound to the trusted launch and channel, with unfilled slots closed before other work starts; test delays, failures and timeouts. Killing an **already registered** relay only disables the app under the stated rule—that replacement attack is closed. [Claude Code startup settings](https://code.claude.com/docs/en/env-vars)

The [pipe-holder scan](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1584) does not rescue registration. A feeder can send its descriptor through SCM_RIGHTS, close its local copy, and leave the descriptor queued in the kernel during inspection. It can retrieve it afterwards. Alternatively, it can write a request and close before inspection; queued bytes retain no writer identity. Even requiring Claude Code to hold the pipes is insufficient when the hostile child reuses its ordinary subprocess pipes. These are concrete gaps in treating a momentary descriptor scan as proof of request origin. Prevent unauthorized possession by construction; add queued-descriptor, write-then-close and check/use race tests. Non-dumpability does not revoke existing descriptors. [Linux descriptor-passing semantics](https://man7.org/linux/man-pages/man7/unix.7.html)

The credential disclosure statement is accurate: Linux stores Claude Code credentials in a file readable by that same user. “Unknown” is appropriately cautious about using those credentials to answer an existing Remote Control prompt; it establishes neither exploitability nor safety. This may remain a qualification task **only with an explicit blocking gate and a closed fallback**. Currently, simply recording the unknown does not support (c)’s unconditional containment claim. Self-approval is outside the accepted developer-site risk and five choices. [Credential storage](https://code.claude.com/docs/en/authentication), [Remote Control authentication](https://code.claude.com/docs/en/remote-control)

The TIOCSTI setting closes that particular injection mechanism. [Linux TIOCSTI requirements](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html)
