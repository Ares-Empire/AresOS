The six previous blocking points:

1. **GET/HEAD recovery — partly closed.** [CONTROL.md:429](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:429) now requires restoration before readiness. However, [CONTROL.md:413](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:413) never requires each entered text to be durably recorded and acknowledged **before input reaches Chrome**; the barrier explicitly acknowledges only the guard. A crash between typing and recording can restore an incomplete classification record and free a retrying GET. Extend the barrier to every input’s classification state and test that crash window.

2. **Local deletion — partly closed, still blocking.** [CONTROL.md:758](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:758). Labelled controls and Delete/Backspace outside text fields now ask first. But an ordinary offline app’s unnamed trash icon, “Reset” control, or confirmation can still delete through a free action. Calling this a gap does not enforce the owner’s rule. Require qualified knowledge of potentially destructive actions, otherwise refuse unsupported interactions. Tests must cover alternative activation paths and confirmations, while proving ordinary text editing—including supported contenteditable fields—remains free. Expanding the word list alone cannot close this.

3. **Recognised actions — closed.** [CONTROL.md:913](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:913), [CONTROL.md:879](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:879). Complete-operation validation, stable targets, account binding, versioned contracts, unknown-field rejection and suspension on widening address the finding. WhatsApp hints no longer authorise unattended release; GraphQL syntax no longer establishes reading. Earlier messages cannot inherit a later message’s exemption. The new advance-approval exception needs the separate correction below.

4. **Shared-file escape — closed.** [CONTROL.md:1219](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1219). The three users, disjoint writable/readable storage, read-only owner folders, private temporary/session files and marker tests address the original route. The additional firewall rule is sensible, but its verification must exercise actual connections to coding services over IPv4, IPv6 and container addresses, including firewall reloads; the listed file-marker test does not establish that boundary.

5. **Root removal — closed.** [CONTROL.md:540](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:540). Both trust locations, crash reconciliation and mandatory browser restarts now have explicit requirements and tests. Chrome 157’s [policy definition](https://raw.githubusercontent.com/chromium/chromium/157.0.8103.38/components/policy/resources/templates/policy_definitions/CertificateManagement/CACertificates.yaml) and [system-context implementation](https://raw.githubusercontent.com/chromium/chromium/157.0.8103.38/chrome/browser/net/system_network_context_manager.cc) support the refresh distinction. The service-context trust location remains honestly unproven. Tighten “removes every root” to **roots installed by this checkpoint**, identified explicitly; do not erase unrelated owner trust entries.

6. **Upstream TLS — partly closed, still blocking.** [CONTROL.md:501](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:501) now specifies checks and a deployment gate, but the owner question materially understates the loss. [CONTROL.md:527](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:527) calls CRLSets a small set of rare emergencies involving stolen site keys. Chrome’s [157 security FAQ](https://raw.githubusercontent.com/chromium/chromium/157.0.8103.38/docs/security/faq.md) says they enforce most security-relevant revocations visible through CCADB CRLs, plus proactively blocked misissued or compromised certificates. Correct that account before recommending acceptance. Likewise, “about once a year” is no assurance about emergency distrust; Chrome documents [aperiodic root-store updates](https://chromium.googlesource.com/chromium/src/+/main/net/data/ssl/chrome_root_store/faq.md).

   Using Chrome’s roots **with their constraints** is appropriate, but copying roots alone does not reproduce verification. Pin the complete CT policy, including log states and SCT delivery rules, and define stale-list handling. Chrome’s [CT policy](https://googlechrome.github.io/CertificateTransparency/ct_policy.html) requires more than timestamp counts.

One newly introduced blocking inconsistency:

7. **Advance destructive approval has no compatible signed representation.** [CONTROL.md:768](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:768) permits subsequent validated sends without another question, while [CONTROL.md:1288](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1288) requires the signed description to contain every Chrome capture’s ID and hash. Those captures do not exist before the approved click. Define a separate, bounded advance-operation description covering the contract version, account, exact targets, permitted effects, sequence limits and expiry, with durable consumption. Otherwise require approval of the resulting captures. Contract recognition alone must not become reusable permission for repeated deletions.
