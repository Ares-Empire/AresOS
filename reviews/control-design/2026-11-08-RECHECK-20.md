Two blocking findings remain:

1. **The registered MCP check does not establish that Claude Code approved the request.** At [CONTROL.md:1548](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1548), a same-UID process outside the sandbox can still act through the genuine relay. With ordinary dumpable processes and stdin pipes, it can reopen `/proc/<relay-pid>/fd/0` and inject requests. That access uses `PTRACE_MODE_READ_FSCREDS`; Yama’s attach restriction does not block it. The genuine relay then passes the executable and parent checks, although Claude Code never displayed an approval. This follows from the [proc descriptor permissions](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html) and [Yama implementation](https://raw.githubusercontent.com/torvalds/linux/master/security/yama/yama_lsm.c). Also, section 2 specifies a Python relay: `/proc/<pid>/exe` identifies the interpreter, not the approved script. Protect the relay’s input channels and establish its actual identity; qualification must attempt injection through the genuine relay, not merely direct socket calls from an impostor. The execution trace is useful evidence, but is not runtime enforcement.

2. **Unreviewed servers introduce an exception outside the four owner choices.** [CONTROL.md:1758](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1758) explicitly allows credentialed servers to post or delete autonomously. Neither asking before installation nor asking on tool calls governs those background operations. The installation question approves the displayed classes; it does not explicitly approve unrestricted background effects. The connector choice also does not cover this. Require independent review before credentialed execution, enforce actual outgoing operations, or present this additional exception explicitly for owner acceptance. “Stops it from sending his data anywhere else” is misleading: an allowed mail or collaboration API can deliver data to arbitrary recipients.
