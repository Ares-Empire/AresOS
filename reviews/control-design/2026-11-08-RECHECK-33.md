One blocking finding remains in the [held-event rule](/Users/pab/AresOS-design-chrome/docs/design/CONTROL.md:538): the specified checks cannot establish its preservation promise.

- While approval waits, `stopImmediatePropagation()` changes none of the listed recorded fields, yet resuming that event skips listeners while a link’s default action can still run. Cancellation and propagation state need explicit treatment. [DOM specification](https://dom.spec.whatwg.org/#dom-event-stopimmediatepropagation).
- A fresh frame’s unwrapped functions can dispatch the held event on a detached target, then call `initEvent()` with its original parameters. Initialisation resets `target` to null, so the recorded values can match without either wrapper observing the reuse. Native getters reveal current state, not dispatch history. [DOM specification](https://dom.spec.whatwg.org/#dom-event-initevent).

These are design counterexamples, not browser-tested results. The simplest light-tool resolution is to leave intercepted page-owned events stopped without resuming them; Claude can prepare fresh input. Otherwise, specify enforceable preservation, refuse where it cannot be established, and extend test 2 accordingly.
