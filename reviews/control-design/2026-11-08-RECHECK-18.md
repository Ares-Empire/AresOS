# Design re-check 18: draft 17 (decisions 22 and 23)

Reviewer: Codex `gpt-6-astra`, fresh context, 2026-11-08. Reviewed draft 17 at `27a6727`.

The decisions’ core intent is recorded faithfully, including the accepted developer-site exfiltration risk. Draft 17 nevertheless introduces powers beyond that acceptance.

The blocking findings are:

1. **Project deletion bypasses approval.** [CONTROL.md:1472](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1472) explicitly permits deleting project files without asking. Git protects neither uncommitted work nor history that Claude can also delete. This contradicts “delete asks” and the protected-version guarantee. Keep destructive changes behind an enforced approval boundary; calling them ordinary development does not establish owner acceptance.

2. **Writable projects can trigger execution outside the sandbox.** Planted hooks and configuration can execute during ordinary owner activity, without him deliberately launching Claude’s program. For example, Git’s `core.fsmonitor` can invoke a command during `git status`. Keeping projects off PATH does not prevent that. [Git documentation](https://git-scm.com/docs/git-config#Documentation/git-config.txt-corefsmonitor) supports this distinction. Prevent these automatic execution paths, and explicitly qualify Claude Code’s own unsandboxed Git operations against planted repositories. The blanket claim that project executables run as the owner only when he starts them is false.

3. **The GitHub token permits unapproved destruction.** [CONTROL.md:1485](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1485) excludes repository deletion and settings changes, but write access still permits deleting references and potentially rewriting history. GitHub’s [delete-reference endpoint](https://docs.github.com/en/rest/git/refs#delete-a-reference) requires only Contents write permission. These actions need enforcement beyond token scope. Also, restricting the supplied token does not enforce “pushes only to his repositories” if another credential is supplied; a hostname allowlist cannot establish that guarantee.

4. **Preparation can send before installation asks.** [CONTROL.md:1591](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1591) lets the service fetch a Claude-chosen git address before approval. An address carrying private data can therefore contact an arbitrary destination outside the accepted sandbox developer-site route. Restrict preparation’s sources and redirects, or approve that fetch first. Require inspection and package build scripts to run in the sandbox; the privileged installation step should copy verified artifacts without executing their installation scripts as root.

5. **Added-tool trust and activation remain underspecified.** [CONTROL.md:1603](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1603) says the service proposes classifications but never establishes the trusted decision-maker or evidence for allowing read/change calls freely. Pinning and separate users do not stop a misclassified server sending through its own credentials. Require reviewed behavior or an enforcing adapter; otherwise ask every call. Connectors can change behavior without changing tool names, and startup-only discovery misses changes during a session. Unknown or changed tools must remain unavailable until classified and guarded. Generating exact settings from a root-owned additions record is sound, but activation must wait until the running session demonstrably enforces those settings.

The should-fix items are:

- **Skip-permissions:** retaining `disableBypassPermissionsMode` when qualification fails is correct. The eight rules need explicit coverage of automatic project execution, added-tool activation, executable skill/agent components, and inter-session messaging. Refusing a fetch is safe; “Claude asks him in the session” does not specify a mechanically bound approval and retry path.
- **Judgment calls and risk wording:** dropping `coder`, retaining another-user isolation tests, and reserving hooks/LSP/monitors for owner installation are reasonable. Project deletion and automatic owner-context execution are separate policy concessions, not accepted exfiltration residuals. A managed `CLAUDE.md` expresses instruction policy; it does not enforce it.
- **Brief consequences:** [PLAN.md:228](/Users/pab/AresOS-council-control-layer/docs/control/PLAN.md:228) names the right workstreams but needs the blocking cases assigned explicitly to 18c/base qualification, Mail’s exact-settings boundary, and the add-tool brief. Brief 20 should launch the localhost server and test browser within the same sandbox command/network namespace: Linux sandbox localhost is [private to each command](https://code.claude.com/docs/en/sandboxing# a-command-fails-to-reach-a-server-on-localhost). The clean-browser approach itself is appropriate.
