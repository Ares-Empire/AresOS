# Design re-check 6: drafts 7 and 8 (Chrome results of briefs 17b and 17c, brief 18b's findings)

Reviewer: Codex `gpt-6-astra`, xhigh, read-only, fresh context, 2026-11-07. Reviewed `6b18e55..46ef611`.

Reviewed `6b18e55..46ef611` under `docs/`, the full current section 6, owner scope, both Chrome reports and 17c’s code and retained evidence. No files changed; no runtime tests run.

Four blocking findings:

1. **The guard can end before an honest page sends Claude’s work.** [CONTROL.md:468](../../docs/design/CONTROL.md:468), [CONTROL.md:485](../../docs/design/CONTROL.md:485).

   The named residual violates the owner’s sending/deleting rule. An ordinary offline application can record a deletion in IndexedDB, make no request before the tab closes, then transmit it from another tab or worker. “There was none” establishes only that no send was observed; it does not establish that nothing remains queued.

   This must close before the Chrome build relies on automatic retirement. After an action, retain the guard until an adapter establishes resolution or the owner explicitly ends it. Refusing actions on unqualified sites is another option. Calling guards “short and rare” cannot supply the missing evidence. Holding **every** non-reading owner send while guarded is the right choice, but cannot compensate for ending the guard prematurely.

2. **Fail-then-repeat still has a pause-and-detach race.** [CONTROL.md:421](../../docs/design/CONTROL.md:421), [CONTROL.md:587](../../docs/design/CONTROL.md:587).

   “Nothing is paused inside Chrome” is incorrect. Chrome pauses a matching request before delivering `Fetch.requestPaused`; it remains paused until the client answers. In 17c, `gate()` even awaits header hashing before calling `Fetch.failRequest`. Detaching or updating during that interval can invoke the release behavior demonstrated by 17b. Failing promptly shortens this interval; it does not remove it. See Chrome’s [Fetch protocol](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Fetch.pdl).

   The held in-page calls survived the tested shutdowns, and an already-failed request cannot subsequently escape. Those results do not establish the fallback’s unconditional fail-closed claim. Require a protection that remains effective during this interval, and a deterministic test ending control between interception and acknowledged failure. This is a design dependency, not ordinary porting work for brief 20.

3. **Refusing page-created workers does not cover browser-created replacements.** [CONTROL.md:572](../../docs/design/CONTROL.md:572).

   Blocking `SharedWorker` construction and `serviceWorker.register()` helps. It does not prevent Chrome updating an existing registration on navigation or following background events, nor an explicit `registration.update()`. Chrome documents these [service-worker update triggers](https://developer.chrome.com/docs/workbox/service-worker-lifecycle#when_updates_happen).

   “Keep an unreached worker paused or ended” assumes the very capability still missing: stopping it before execution. Terminating a discovered, already-running worker cannot undo its first send. Auto-attach covers related targets and requires recursive setup; the broader `autoAttachRelated` mechanism is Browser-target-only. Neither establishes universal early coverage through this extension route. See Chrome’s [debugger guidance](https://developer.chrome.com/docs/extensions/reference/api/debugger#attach-to-related-targets) and [Target protocol](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Target.pdl).

   Specify an enforceable barrier covering automatic updates, dormant-worker activation, replacement and restart, including periods without an attached page. Otherwise refuse acting on sites with those unqualified paths **before** Claude leaves work there.

4. **The upload/stream fallback assumes complete request bytes are available.** [CONTROL.md:432](../../docs/design/CONTROL.md:432).

   Sending an unfreezable body through fail-then-repeat does not automatically make it inspectable. Chrome documents omitted oversized `postData` and file bytes omitted by `getRequestPostData` for multipart requests. Therefore the proposed exact-body comparison is not established for the very cases assigned to this fallback. See the [Network protocol](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Network.pdl).

   Require complete immutable bytes through a qualified path; otherwise refuse or require an adapter. Missing bytes must never become an empty-body match.

   Method, full address, immutable body and page-set headers are appropriate bindings for caller-controlled content. Also require the existing document/account guarantees to survive the wait: unchanged request fields can still execute under changed session cookies. Brief 20 must test account changes, mutable headers and competing identical requests. The 17c prototype explicitly skips header matching for in-page allowances, so its successful releases do not prove this stronger contract.

The following should also be fixed:

- **Specify the restart barrier and its handoff.** [CONTROL.md:477](../../docs/design/CONTROL.md:477). Chrome documents that **dynamic** DNR rules persist across sessions and upgrades; session rules do not, and `tabIds` conditions are session-only. Its documentation does not by itself prove this design’s first-request timing. Require a persisted conservative block before accepting the first action, protection after crashes while attached, and tests covering restored tabs, cross-site destinations and worker requests without tabs. Do not remove the sole persisted protection during normal attachment and expect a crash handler to restore it. See [DNR rules and conditions](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest). The restored worker’s zero-arrival result is real, but that fixture activates it after restart/attachment; it does not qualify arbitrary autonomous startup.

- **Compare WebSocket traffic against authorized releases, not merely held messages.** [CONTROL.md:343](../../docs/design/CONTROL.md:343). A bypass could transmit the same bytes as an unapproved queued message. Detection needs connection identity, payload, order and consumed release authorization, including explicitly permitted reading messages. Chrome supplies a sent-message event, so this is a sound **after-the-fact diagnostic**, not prevention. See [Network WebSocket events](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Network.pdl). State that RTC/WebTransport have no equivalent demonstrated payload audit. The hostile-page limitation is otherwise candid; continue refusing input wherever wrapping or observation coverage is unknown. Destination restrictions alone also cannot stop a hostile permitted destination receiving the data.

- **Narrow the “checked” claims.** [CONTROL.md:414](../../docs/design/CONTROL.md:414). All seven transport families were exercised in the main-page fixtures; the frame fixtures exercise fetch, not all seven families in every frame configuration. The report explicitly says XHR drop produces **no error event** in the prototype. Mark the intended XHR behavior as brief-20 work. Keep public-site conclusions provisional: workers/live connections were disabled, observations were brief, and counts covered current main documents. The policy/native-host results, main-page holds, shutdown cases, attribution fixtures and genuine owner controls otherwise match the reports.

- **Recent owner input is only a notification heuristic.** [CONTROL.md:511](../../docs/design/CONTROL.md:511). A delayed shared-worker flush may occur long after the owner’s click. Define what happens outside the “just before” window; it must remain visibly unresolved, never become exempt. Both surfaces should reference one operation, with atomic first-decision handling and worker-event deduplication. Brief 20 can test this. The protected details-page checks are appropriate: Chrome’s [MessageSender documentation](https://developer.chrome.com/docs/extensions/reference/api/runtime#type-MessageSender) supports the URL/frame distinction and explains why popup senders need separate treatment.

- **Carry 18b’s actual safeguards and limits into the summary.** [CONTROL.md:55](../../docs/design/CONTROL.md:55), [CONTROL.md:625](../../docs/design/CONTROL.md:625). Read-only terminal work, no installed plugins and asking on web tools are supported changes. Future filter safety depends on native pinning and socket canaries, not merely requiring the separate helper. Mention launcher refusal of existing plugin installations and exclusion of lower settings sources. Cached plugin execution remains unqualified. Also, [PLAN.md:153](../../docs/control/PLAN.md:153) overstates Bash prompting: `false` restores ordinary permission handling; 18b’s unapproved `sleep 2` still ran. [Anthropic’s setting reference](https://code.claude.com/docs/en/settings-reference#sandbox-autoallowbashifsandboxed) agrees.

- **Make the section-10 choices consistent with the build defaults.** [CONTROL.md:737](../../docs/design/CONTROL.md:737) recommends retaining Claude in Chrome while section 6 mandates blocking it. Keep the conservative default explicit pending the owner’s decision. Machine-wide settings are accurately described; separate coding containers must retain 18b’s explicit isolation, not toolbox/distrobox defaults.
