- **2 — Partly closed, still blocking.** [CONTROL.md:805](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:805) truthfully marks the decision open. However, [CONTROL.md:1463](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1463) incorrectly says the risk requires an offline-only app. An ordinary online app can keep an unsynchronised draft in localStorage, IndexedDB or memory, without any service worker. [Web Storage explicitly supports local documents](https://html.spec.whatwg.org/multipage/webstorage.html).

  Option (a) is enforceable, but remove the unsupported rarity claim and describe that wider exposure. Option (b)’s service-worker-plus-database test misses those cases, so “Nothing is deleted without asking” is false. Define conservative coverage when local storage or action semantics are unknown, or narrow the promise explicitly. Merely having an adapter cannot exempt interactions outside its qualified coverage.

  The new **contenteditable exception**, [CONTROL.md:792](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:792), correctly accommodates ordinary editing, but an editable region can also contain selected cards or attachments whose Delete handler removes an object. Qualify the exemption by supported editing behaviour; test those cases alongside free text editing. This concerns the options’ guarantees, not which option the owner should choose.

- **6 — Partly closed, still blocking.** The CRLSet account and complete-CT-policy requirement are substantially corrected at [CONTROL.md:537](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:537). But [CONTROL.md:1457](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1457) still incorrectly promises that none of the differences weakens a check. If Chrome tightens verification before the checkpoint adopts it, the checkpoint can accept a certificate Chrome rejects. Require a supported-version gate or disclose that security gap.

  Chromium **157.0.8103.38** supports the proposed data sources: [`CertificateRevocation/<version>/crl-set`](https://github.com/chromium/chromium/blob/157.0.8103.38/chrome/browser/component_updater/crl_set_component_installer.cc), and [`PKIMetadata/<version>/`](https://github.com/chromium/chromium/blob/157.0.8103.38/chrome/browser/component_updater/pki_metadata_component_installer_policy.cc), containing [`crs.pb`, `ct_config.pb` and `kp_pinslist.pb`](https://github.com/chromium/chromium/blob/157.0.8103.38/chrome/browser/component_updater/pki_metadata_component_installer.cc). These are under Chrome’s user-data directory, not an individual profile’s `Default` directory.

  The payload files do **not** contain their own verification signatures. Chrome [verifies the CRX before unpacking](https://github.com/chromium/chromium/blob/157.0.8103.38/components/update_client/unpacker.cc); optional verified-content metadata is not guaranteed. Therefore [CONTROL.md:522](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:522) must explicitly identify whether trust rests on Chrome’s verified installation and filesystem protection, or on separately retained, verifiable evidence.

  Brief 20 must prove atomic loading, compatible schemas, Chrome’s built-in floors and version-selection rules, malformed/missing-data handling, and freshness across restarts. File modification time is insufficient: [CRLSet expiry is optional](https://github.com/chromium/chromium/blob/157.0.8103.38/net/cert/crl_set.cc), and [the root-store format has a version rather than a freshness timestamp](https://github.com/chromium/chromium/blob/157.0.8103.38/net/cert/root_store.proto). Successful unchanged-update checks need defined treatment. CT qualification must cover [the 70-day limit, operator history, retired logs, delivery methods, deduplication and applicable log-type rules](https://github.com/chromium/chromium/blob/157.0.8103.38/components/certificate_transparency/chrome_ct_policy_enforcer.cc).

  The new **stale-list exception**, [CONTROL.md:525](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:525), needs a precise recovery contract: which TLS checks remain enforced, how update checks and package downloads qualify, and what authenticates them. A signed downloaded package does not authenticate an outgoing request. Brief 20 must demonstrate recovery from genuinely stale data, failed signatures and interrupted updates, while page/worker imitations remain held.

- **7 — Closed.** [CONTROL.md:798](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:798) and [CONTROL.md:1346](/Users/pab/AresOS-council-control-layer/docs/design/CONTROL.md:1346) now define a compatible signed advance-operation description, bounded by contract, account, targets, effects, sequence and expiry, with durable single consumption.
