## JUDGMENT-CALL

- Apps outside My apps retain ownership of saved names, as well as retaining the names themselves. Rejected lending those names to another app: that could prevent restoring the remembered commands on return. Changing this later needs an explicit reclaim/conflict policy, with no block-world migration.
- If every candidate is invalid (for example a purely numeric/non-Latin name without usable metadata), use `app2`, then the first free numbered variant. The design does not define a valid first candidate in that case. Rejected unusable commands or refusing to add the app. It can be renamed with one command later; existing saved names otherwise stay stable.
- ~~`/open` additionally accepts an exact stable app ID.~~ Replaced in review fixes 1: clicks run `/aresos app open <id>`, and typed `/open` knows no IDs.
- (Review fixes 1) `/apps` lists an app the system no longer lists as "not installed", grey and without a click, rather than leaving it out: he sees why its commands are gone, and it is still one of his apps. Leaving it out is a one-line change.
- (Review fixes 1) Only the AresOS app helper's lists mark programs absent. Windows discovery returns only the shortcuts it found, not the whole file, and on Windows the mod runs an entry's command itself, so there an entry missing from discovery still opens.
- (Review fixes 1) A later registration under one of our names takes the name whole: our node steps aside before Brigadier would merge (a mixin on Brigadier's `CommandNode.addChild`). Rejected: only detecting the merge afterwards, because the later command's own requirement is lost in a merge and could not be given back. The app then gets its next-best name, saved, so it stays `discord2` after a `/reload` even when the other command is gone (names never change by themselves).
- (Review fixes 1) After a failed save of names: retry after 1 s, doubling to at most a minute; the host hears it once per run of failures.
- (Review fixes 1) Host-only AresOS commands are not "restricted" for the client, so a clicked row runs without Minecraft's permission question. The host check still runs, at parse and at execution, for every real source. The alternative, a custom click payload instead of a command, needs its own server handler and was more than this fix.

### What an older mod does with the schema-4 apps file

Read from its code (`AppsConfig.version` in package 34's mod, `main` before this package), not run: it refuses a schema-4 file with "Invalid apps.json; original left intact: Unsupported schemaVersion (expected 3)", leaves the file untouched, starts with no apps, and says "AresOS apps disabled: …" in the chat on join. This mod's move to schema 4 keeps the untouched schema-3 file beside it (`apps.json.schema-3-<id>.bak`). `restoreLegacyApps` accepts only schema-1 and schema-2 backups, so going back to package 34 means copying that schema-3 backup over `apps.json` by hand. (Corrected in review fixes 2.) That backup is the file as it was at the move to schema 4, so copying it back rolls back **everything since that move**, not only names and absent marks: every app added to or removed from My apps and every pin changed since then is undone too. First copy the current `apps.json` aside (for example to `apps.json.schema-4-keep`), so that state is not lost and can be copied back when this mod returns; then copy the schema-3 backup over `apps.json`. This package has no tool that converts a schema-4 file back to schema 3.
