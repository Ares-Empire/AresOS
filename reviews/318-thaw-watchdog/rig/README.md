# Package 318 measurement rig

Copied from package 49b's rig (`reviews/49b-arena-rerun/rig/` and `frames/`), which stay as they were with their records. Package 318 asks why package 49's two cover-freeze trials died by SIGKILL about 200 ms after the thaw (brief: `briefs/318-thaw-watchdog.md`). The hypothesis: OpenAL Soft's `null` backend, which the rig forces with `ALSOFT_DRIVERS=null`, catches up on five frozen minutes of audio in its realtime mixer without blocking, and the kernel's `RLIMIT_RTTIME` watchdog (200 ms, soft = hard) kills the game. No product code or settings ship.

Everything 49b's README describes still holds: `run.sh <name> [KEY=value ...]` takes the shared client-test lock, applies the owner-game and 6 GiB guards, and runs under `mod/dev/env.sh`'s supervisor with the NVIDIA holder, which keeps the card awake for the whole run. The game runs headless in the rig's own labwc/Xwayland and its own scope. `input.py` bounds every input write, `health.py` watches the launcher, compositor and reader with pidfds, and cleanup stops only the rig's own scopes. The frame recorder and the test apps keep their `pkg41` names, and the environment variables keep their `PKG49_` names (they live only in the rig's own processes).

## What changed from 49b, and why

- **Names.** Scopes, `/tmp` and `.work` names are `pkg318-…` (`pkg318-controller`, `pkg318-rig-<pid>.scope`, `pkg318-game-<name>-<pid>.scope`, `.work/pkg318/`), so neither package's guards or records mix with the other's. `scope.py` accepts only a `pkg318-game-…` scope. The frame recorder's properties are `pkg318.ui` and `pkg318.creation_marks`.
- **Left out:** 49b's 18-run `schedule.py`, `verdict.py`, `audit.py`, `finalize.py` and 49's `batch.py`/`table.py`. They run or check 49b's own schedule and report. `observe-return.py` is copied but unused; `thaw.py` does its job.
- **The cover-freeze path is allowed again,** exactly as package 49 ran it: 30 s into a `COVER=300` cover a GC/trim, a `600M swappiness=max` reclaim and a freeze of the game's own scope, then a thaw at the return request. `measure.sh` refuses any other cover action, probe or reclaim amount. 49b's input bounds, health watch, card holder and cleanup stay, and every exit path that finds the game frozen thaws it.
- **`RT=keep|demote`** (default `keep`, `demote` only with `FREEZE=1`). Once the freeze is confirmed (`cgroup.events` frozen 1), `rt.py record` writes `rt-freeze.json`: every `SCHED_FIFO`/`SCHED_RR` thread of the game PID (tid, `comm`, policy, flags, priority) and the whole `/proc/<pid>/limits`. Expected: one `alsoft-mixer` at `SCHED_RR|SCHED_RESET_ON_FORK` priority 1, and "Max realtime timeout 200000 200000 us". In `demote` mode `rt.py demote` then checks that each recorded tid's `Tgid` (from `/proc/<tid>/status`) is the game PID and runs `chrt --reset-on-fork --other --pid 0 <tid>` (`rt-demote.json`). A plain `chrt --other` gets EPERM: rtkit's threads carry `SCHED_RESET_ON_FORK`, and only `CAP_SYS_NICE` may clear it. Doing both while frozen means no thread can end, appear or be promoted between the check and the change.
- **INVALID.** Just before the thaw write `rt.py check` scans every thread again (`rt-prethaw.json`). In `demote` mode a thread still realtime makes the run INVALID: it is thawed and sampled like any other, `invalid.json` and the `invalid` mark are written, and the run stops with exit 3.
- **The thaw watcher (`thaw.py`).** `lifecycle.sh`'s `rig_thaw` starts it and waits for its first sample before the thaw write, on the normal return and in cleanup alike. Every 10 ms it records each recorded thread's (and any `alsoft-*` thread's) `schedstat` CPU time, voluntary and nonvoluntary context switches, state and policy (`thaw-samples.csv`). Every 100 ms it scans all the game's threads for a realtime policy (`thaw-scan.jsonl`). It samples for 3 s (`keep`) or 10 s (`demote`). A pidfd on the game runs until 60 s after the return request. At an exit it reads the zombie's wait status from `/proc/<pid>/stat` (field 52) and compares the exit with the `cleanup_start` mark (`exit.json`). A survivor is held until then: `measure.sh` waits for the watcher before its cleanup, so `exit.json` says `alive`.
- **`cleanup_start`** is the first mark of `finish()`, so "died before any rig cleanup step" can be checked.
- **Run records (`records.py`).** The card's `power/runtime_status` before the freeze, at the freeze, each covered minute, before the thaw and from the watcher (`card-status.jsonl`; reading it doesn't wake the card, package 47). At the end of every run, on every exit path: rtkit's journal lines for the game PID or for no process, every `cardwired` line, and kernel lines about OOM, NVRM or a watchdog (`journal.txt`, no hostname); `cardwire get` (`cardwire.txt`); the game's OpenAL and sound lines (`sound-lines.txt`); and Gradle's exit value as a fallback for the zombie read. The package-318 records are copied to `runs/<name>/` with local paths redacted, also when the game died (a death never reaches `analyze.py`).
- **`scope.py`** also records `write_monotonic_ns`/`written_monotonic_ns` around the `cgroup.freeze` write, to time the death from the thaw write itself.
- **`schedule.py`** runs one of 318's runs per call with fixed settings: `setup` (S0, the `setup-flat` creation; its save becomes `.work/pkg318/AresHub-base`, since 49b's base world went with its worktree) and `trial <name> keep|demote` (`COVER=300 SHOTS=0 RECLAIM=600M FREEZE=1 RT=<mode>`). Which runs happen, and what they mean, is `PLAN.md`'s.

## Writes outside the repo

As in package 49, `memory.reclaim` and `cgroup.freeze` of the game scope this run created, checked by `scope.py:owned_scope`. Package 318 adds scheduling-policy changes on threads of that game's PID, checked by `Tgid`, in `RT=demote` only. Nothing else under `/sys`, `/proc` or `/etc`; the card, journal and `/proc` reads are read-only. The rig never asks rtkit for anything and never changes `kernel.print-fatal-signals`.

## Validation without a game

```
bash -n reviews/318-thaw-watchdog/rig/*.sh reviews/318-thaw-watchdog/frames/build.sh
python3 reviews/318-thaw-watchdog/rig/test_rig.py
python3 reviews/318-thaw-watchdog/rig/test_input.py
python3 reviews/318-thaw-watchdog/rig/test_thaw.py
python3 reviews/318-thaw-watchdog/rig/test_lifecycle.py
```

`test_thaw.py` covers the realtime-thread parsing; the `Tgid` check (a thread of another stand-in is refused before any command); the demotion on stand-in threads that set `SCHED_OTHER|SCHED_RESET_ON_FORK` on themselves (plain `chrt --other` gets EPERM, the rig's command succeeds and keeps the flag); the INVALID check; the watcher stopping at a SIGKILL during sampling with the zombie's signal, marking an exit after `cleanup_start`, sampling a 500 ms non-blocking spin, and holding a survivor to its deadline; and the run records. It never asks for a realtime policy: this account shares rtkit's per-user limits with the owner's session.

`test_lifecycle.py` keeps 49b's three health-failure scenarios and adds thaw on every exit path, with real disposable user scopes and stand-ins that log the freeze/thaw requests instead of writing `cgroup.freeze`: health failure, SIGTERM and a failing command while frozen, the INVALID return, and a normal return. Each needs exactly one thaw after the watcher's first sample, the watcher's verdict on the stand-in game's exit, no process or scope left, and the lock free.
