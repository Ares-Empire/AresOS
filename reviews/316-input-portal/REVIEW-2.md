1. **NIT (a limit to list, and a check for (c))** — `reviews/316-input-portal/KNOWN-LIMITS.md:51`, `os/config/usr/share/aresos/labwc/rc.xml:21`. labwc's own key bindings stay live during a capture. The chord works because labwc takes a bound key before the barrier's surface sees it (`evidence/step3-harness/results.txt`: Escape never reached the receiver). The same is then true for every binding in AresOS's `rc.xml`: Alt+F4, Alt+Tab, the volume and brightness keys. Scenario: Patrik works on the Mac and presses Alt+F4 or Alt+Tab; the Mac never gets it, and labwc closes or switches a window on the laptop, which he isn't looking at. Not tried here: the harness's `rc.xml` binds only the chord. Fix: list it in `KNOWN-LIMITS.md` and in (c)'s list; (c) presses each binding of the real `rc.xml` during a capture and decides which may stay. List upstream's built-in Ctrl+Alt+Escape too (`os/input-portal/src/wayland/state.rs:651`): it still ends a capture, and no test presses it.

2. **NIT** — `os/input-portal/src/wayland/mod.rs:287`, `os/input-portal/src/main.rs:184`. The backend outlives its Wayland thread. When the connection to the compositor ends, the thread logs and stops; the process keeps its bus name and its sessions (`evidence/step3-harness/backend-7.log` shows that state until the harness stops it). Scenario: the backend's Wayland connection ends while the bus lives on (a protocol error on this one client): `CreateSession2` and `Enable` keep succeeding, no barrier is ever placed, and Deskflow looks connected while sharing is dead until someone kills the process. No input can leak, because the compositor drops the grab with the connection. Fix: when the Wayland event stream ends (`os/input-portal/src/portal.rs:1940`), do what bus loss does: close every session and stop, so the next call starts a fresh backend.

3. **NIT** — `os/input-portal/src/portal.rs:630`, `os/input-portal/src/portal.rs:454`. Only `CreateSession` ties the sessions to the frontend connection that made them. The comment there gives the reason (the watch on the frontend's name may not have run yet); the other 14 methods have the same gap. Scenario: the frontend's name changes hands, and before the watch task has closed the old sessions the new owner calls `ConnectToEIS` or `SelectionRead` on an old session's path. It gets that session's file descriptor, while the session's signals still go to the old owner. The new owner must know the path, and the model trusts whoever owns the name, so this is inside the stated limit. Fix: move the comparison into `authorize`: a caller that passes the check but isn't `Inner::frontend` first closes every session.

4. **NIT** — `os/input-portal/src/portal.rs:669`, `os/input-portal/src/portal.rs:1473`. A reused session path can lose its Session object. `at()` answers `false` when an object already stands at the path, and that answer is ignored; a closed session's object is removed only after its `Closed` signal was sent, outside the lock. Scenario: `Close` on a path and `CreateSession2` for the same path right after it: the new session is stored while the old object still stands, then the old object is removed. The new session has no `Close` and lives until its EIS connection or the frontend goes. xdg-desktop-portal's paths carry a random token, so it takes a client that reuses one. Fix: in `emit`, remove the object only if no session with that path exists any more, or replace the object in `create_session` when `at()` says `false`.

5. **NIT (wording)** — `reviews/316-input-portal/KNOWN-LIMITS.md:8`, `:69`, `:113`. "When the real frontend isn't running" is narrower than the truth: xdg-desktop-portal owns its name with replacement allowed, so a program of the user can take the name while the frontend runs (from memory of its source, not checked here). The conclusion stands, and for a stronger reason worth writing down: any labwc client can already take the keyboard with an exclusive overlay layer surface and read the clipboard through `ext-data-control`, so the backend gives such a program nothing new. Lines 69 and 113 describe the labwc abort twice, and the first still says "not known for a real output": make them one entry.
