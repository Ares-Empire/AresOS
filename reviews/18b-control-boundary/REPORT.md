## Q1: which sandbox, how faithfully reproduced, runner changes

**read:** Anthropic names [`@anthropic-ai/sandbox-runtime`](https://code.claude.com/docs/en/sandboxing#how-sandboxing-works) as its open-source sandbox implementation, with bubblewrap on Linux and the optional Unix-socket seccomp helper. This experiment pins Claude Code **2.1.319** and the separately published runtime **0.0.81**, including npm integrity hashes in `package-lock.json`. The runtime source is [tag v0.0.81](https://github.com/anthropics/sandbox-runtime/tree/c40cf14a65d025e3cd27f071f13a73c12b3b1f92); the helper's SHA-256 is `7effeb0f2d94f7b8bbb8d25a9b21fe77416e5f5c7e408cefea5a07f7560ca24a`.

**run:** The native CLI reports `2.1.319 (Claude Code)`; the image uses Node `v22.21.1` and bubblewrap `0.8.0`, on a GitHub Ubuntu 24.04 x86-64 Linux runner. Version output is retained in each mode's `version-*.txt` files.

**read (repository):** Image wiring exposes the single pinned runtime package at `/usr/local/lib/node_modules/@anthropic-ai/sandbox-runtime` through a root-owned symlink. This lets the native CLI find the optional helper through the documented global npm fallback, rather than only making it available to the standalone test's local import. Removing the helper removes that same target for both lookup paths. Its actual selection by native Bash remains part of the later model/image qualification.

**read / assumed:** No documented Claude Code command runs one sandboxed Bash command without a session/model. The native CLI package exposes neither its sandbox settings resolver nor its embedded runtime revision. **Its exact embedded runtime version is unknown; it is not claimed to be 0.0.81.** The permitted closest reproduction uses the published runtime's public `SandboxManager.initialize` and `wrapWithSandbox` APIs, without any model or sign-in. `configure.py` maps the draft's explicit filesystem/network settings and fixed home into that API. Differences: no private Read/Edit rule projection, implicit working-directory/worktree/temp discovery, live policy merging or native-CLI sandbox initialization. Stronger explicit masks cover the intended paths in this experiment. A later actual Claude session must compare `/sandbox` Config with `sandbox.json`.

**run:** Default runner user-namespace restrictions caused `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`. The workflow records `kernel.apparmor_restrict_unprivileged_userns`, temporarily sets it to 0 **only on the disposable runner**, and restores it in an `always()` step. The test container uses Docker `seccomp=unconfined`, `apparmor=unconfined`, `systempaths=unconfined`: without the last, nested proc mounting failed with `Can't mount proc on /newroot/proc: Operation not permitted`. The inner runtime still supplies its own full network, mount, user, PID and proc isolation. No privileged container, host namespace, host home, host input device or Docker socket is exposed. No Mac setting was changed. This is a test envelope, not an AresOS AppArmor deployment recommendation; the image needs its own supported namespace policy.

**run:** Read-only work roots also exposed a mount-planning interaction: with hidden `/home` and an explicitly re-exposed work tree, missing built-in deny targets made bwrap fail creating `.gitconfig`. Image preparation creates harmless mandatory-deny placeholders before sandboxing and the launcher's real canary catches a broken setup. `/tmp/claude` is pre-created with assistant ownership and mode 0700 so the runtime has its normal scratch area. Neither failure was worked around by weakening the inner sandbox.

## Q2: fixed hostile programs and independent observers

**run:** `fixtures.json`, `hostile.py`, `stub.py` and `check.py` cover **128** fixed operations per mode. The service directory is tools:assistant 0750; act/chrome are tools:assistant 0660 and admin is root:root 0600. The listeners drop to the separate service uid after binding. Service state/passwords are tools-owned 0600 under 0700. **run:** Thirty-nine real target files are hashed before and after. `file-integrity.json` records both hashes per path; `stub-new-connections.json` records the listener delta. Completion and exact attack count are required. `WORK_READ_OK` and `TEMP_WRITE_OK` prove useful code actually executed. New work subfolders/config files must remain absent. The observer is outside the sandbox and checks the stub remains alive.

**run:** A hidden-home pathname can accept writes to a disposable tmpfs **shadow**, while the original outside file remains unchanged. This is explicitly tested with `SHADOW_ONLY /home/assistant/.bashrc`. The existing-file attack uses `O_WRONLY|O_APPEND` without `O_CREAT`, so it attempts to modify the actual execution target rather than silently creating an unrelated file. Creation of real work-tree configuration is tested separately, including previously absent subdirectories. The owner never executes the tmpfs shadow. Calling every successful write syscall an escape would be a false conclusion; claiming nothing can be created in the hidden mount would also be false.

**run / risk:** The unfiltered AF_VSOCK connect timed out after socket creation succeeded. That is **not evidence of VSOCK isolation**, because CI has no qualified host endpoint. Unfiltered sessions are therefore forbidden by the tested launcher. The filename mask alone would not close this family.

**read:** The [runtime's Linux implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.81/src/sandbox/linux-sandbox-utils.ts) blocks AF_UNIX and AF_VSOCK creation when its helper is present. It explicitly does not revoke already-open socket descriptors. The launcher closes fds >=3; normal CLI stdio is the owner's terminal/pipes, not a service socket. The missing-helper run really deletes both architecture helpers, leaving the rest of the configuration unchanged; it must print the dependency warning and still run all fixed programs. This tests the documented fallback rather than merely setting `allowAllUnixSockets`.

**read / run:** `failIfUnavailable` does not make an optional seccomp helper mandatory. The launcher adds a pinned helper check and an effective AF_UNIX/AF_VSOCK EPERM canary. No normal central session is allowed to use the unfiltered fallback. An absent or corrupt helper must stop before the CLI target is executed.

## Q4: launcher

**run:** `launcher.c` builds with `gcc -static -O2 -Wall -Wextra -Werror`. It is root-owned, not setuid, requires assistant uid 10001, takes no options, closes descriptors >=3 and calls `execve` with a fixed environment. Isolated Python checks trusted root-owned paths, the pinned helper hash, the plugin registry and the effective runtime canary; only then does it exec the fixed native CLI. No CLI path, config path or command is accepted from the caller.

**run:** Positive controls execute real LD_PRELOAD, Node `--require` and Python `sitecustomize` payloads outside the launcher. Their markers remain absent when the same planted environment is passed through the launcher. The CLI recorder sees only the eight fixed environment entries and `--setting-sources ''`; it never sees planted library/Python/Node paths, credentials, display/bus variables or Claude config/plugin overrides. The corrupt-filter test, preinstalled-plugin test and injected-launcher-option test all require exit 78 before the recorder runs. The absent-filter run requires the same refusal. Recorder substitution happens as root only inside the disposable test container and is restored afterward; it is not an exposed launcher option.

**assumed / not checked:** The image must install the launcher, native CLI, runtime, complete interpreter/dependency tree and policy under root-owned immutable image paths. The draft fixes uid 10001 and `/home/assistant`; those are CI image assumptions to adapt deliberately during image integration. This does not install a launcher on the Mac or qualify the real signed-in central session.

## Q5: separate coding policy environment

**run:** `isolation.sh` starts an assistant container with synthetic credentials, transcripts and an act socket, then a separate uid 10003 coding container with its own root/home and a different read-only `/etc/claude-code/managed-settings.json`. The coding policy is plan mode rather than the assistant's default mode. The coder must see none of the assistant's synthetic credentials/transcripts or any tool socket, must have its own writable transcript/credential location, and `claude mcp list` must show no app MCP. No model or sign-in is used. The additional native CLI probe `--agents '{}' -p ...` reaches the signed-out auth preflight in the coding container, while the assistant policy rejects that flag before auth. This demonstrates distinct policy consumption by Claude Code itself, beyond merely comparing JSON files.

**assumed / design consequence:** This proves an explicitly separated container arrangement, not default toolbox/distrobox integration. Sharing the owner's home, `/run/user`, service sockets, browser profile, SSH agent, container engine socket or host-exec integration would invalidate it. The costs are a separate account and sign-in, duplicate session state, a separately maintained managed policy, explicit work-file transfers/selected coding-project mounts, and loss of automatic desktop/host integration. Docker image layers can be shared, so a second full base download per session is unnecessary. An actual Bazzite toolbox/distrobox configuration remains future image work; a separate Linux uid on the same root filesystem is insufficient for distinct machine-wide policy.

## Risks, PLAN-GAPs, JUDGMENT-CALLs, not checked

- **PLAN-GAP / read:** Exact native-runtime/resolver equivalence cannot be established by the public model-free CLI interface. This is the explicitly permitted closest reproduction, not a full session qualification. **Model-driven gate:** inspect native `/sandbox` Config, then rerun the same programs through actual Bash calls, including failed initialization, restart and dynamic settings changes.
- **PLAN-GAP / read; JUDGMENT-CALL:** Recursive Linux write exclusions do not work. The draft therefore makes the entire shell work tree read-only and allows scratch only in the runtime temp area. Rejected: ineffective recursive globs or enumerating only today's repositories, both of which miss newly created configuration. Reversing this choice requires another confinement design and new hostile runs; file tools remain able to write normal work files under their own permissions. This is a draft owner-decision item, not a silent change to the design files.
- **PLAN-GAP / read; run:** Optional seccomp must not be mistaken for mandatory sandbox availability. A root-owned launcher with a pinned, effective canary closes startup without it. Native-runtime equivalence still needs image qualification; an upstream helper change intentionally requires a pin review and test update.
- **JUDGMENT-CALL / read:** Central terminal internet and coding credentials are absent; all web-tool queries/URLs ask. Rejected: allowing a familiar git/search host and assuming it cannot receive private text. Reversal changes only draft policy/configuration, but requires owner decisions and disclosure tests.
- **PLAN-GAP / run; read:** “No mods” is not literally achieved by the installed-plugin switches. Session initialization still lists the vendor built-ins `cc-plugin-sec-default`, `cc-plugin-agents-md`, `cc-plugin-privacy` and `cc-plugin-plugin-authoring`. [Anthropic documents](https://code.claude.com/docs/en/plugins/mods/overview#mods-built-into-claude-code) that installed-mod switches do not stop built-ins; the guard cannot simply be uninstalled, and other built-ins have individual switches. `privacy` is observed here but not listed in that page's table. These are native vendor code, not a demonstrated route to load Claude-written code, but the image/model qualification must audit them; do not advertise a blanket absence of mods.
- **PLAN-GAP / read; run:** Empty enabledPlugins is not “every plugin off.” Startup refusal for pre-existing installs, no account sync, no allowed marketplace and no sideloaded source are the conservative combination. Do not rely on marketplace policy alone to stop LSP. A future plugin requires explicit review of all its processes and imports.
- **Not checked / assumed:** A VSOCK listener on a real virtualized image, actual `/dev/uinput` event generation, the real display server/native host protocol, Bazzite/SELinux/AppArmor integration, proxy imports/dependency shadowing from brief 18, socket inode aliases planted before launch, inherited socket stdio and kernel exploits. No claim of safety against a malicious owner/root or the owner intentionally executing work files.
- **Needs a model run / read:** File tools (including LSP paths, symlinks, new config files and NotebookEdit), helper/status-line absence, hooks, cached/synced plugins and their LSP/monitors/mods, managed ask persistence under “don't ask again,” bypass/restart attempts, WebFetch/WebSearch redirects and query/URL disclosure, actual environment/settings propagation to subagents, SDK/IDE absence and the browser self-approval/input-injection scenario. The fake mail/site receivers must see zero arrivals in that later test.
- **Open owner decisions:** Work folders, shell write access, search prompting and separate coding sessions remain the design's existing owner questions. No question was asked mid-run.

**run:** Worktree download audit: `.work/` contains **no file over 500 MB**. Only small source/docs/npm metadata and downloaded CI evidence are retained locally. No image layer, native CLI binary, extracted OS image or ISO was downloaded to this worktree. Container/image data exists only on disposable GitHub runners. No files under `os/`, `mod/`, installation/emergency/design/plan/state/handoff paths were changed.
