## Findings

**1. `verify(ref=None)` — SAFE.** `control/aresos_control/chrome/qualification.py:86,96`: `--source-ref` is `ref or 'refs/heads/' + branch`, default `refs/heads/main`. The only product callers are `Qualification.accept` (`:138`, `verifier(path)`, no keyword) and `refresh` (`:143,161`, passes `verifier` through); the adapter calls `refresh(force=...)` only (`control/aresos_control/chrome/adapter.py:230`). No product path passes `ref` or `branch`; forced refresh and daily refresh are unchanged. `ref=''` falls back to main. `test_qualification.py` still asserts `--source-ref refs/heads/main` on the default command.

**2. `qualify.py` guard — SAFE.** `control/chrome/qualify.py:302-331`: repository check first; `notify` and `publish` without `--remote` require `GITHUB_REF == refs/heads/main`; `--ref` is refused for origin (`:330`) before any git call; `--remote` must be an existing local directory and contain no `://` (`:333-335`), resolved to an absolute path, and with a remote set no credential helper is configured (`:236`). `--bundle` is required (`:337`). Binding of `--bundle`: `gh attestation verify <candidate> --bundle` fails if the bundle's subject digest is not the candidate's or its certificate's source ref is not the policy ref, so a bundle for another file or another ref is refused; `publish()` writes `candidate.read_bytes()` only after that (`:247`). First-record path (`:317-320`, `:238-246`): candidate = `origin/main` shipped record + this run's entries; `publish` verifies the fresh bundle, cuts the data branch from `main`, checks `append_only(baseline, held)` and `append_only(held, candidate)`; `held_verifier` runs only when the data branch exists. No unattested append exists. `GITHUB_REF` spoofing: a same-repo PR could set env or edit `qualify.py`, but that actor already has repository write access, and a bundle made in a PR run carries `refs/pull/N/merge` so neither main's later `held_verifier` nor the laptop would trust the result (denial only, fail closed). The guard is a safety rail; the Sigstore identity is the boundary, and it is intact.

**3. `attestation.py` opener — SAFE.** `control/chrome/ci/attestation.py:42-54`: exact-URL match, refuses `Authorization`, refuses plain HTTP; `OpenerDirector()` holds only this handler, so no other scheme has a handler. `minimal_environment` (`:73-86`) clears the environment, so `GH_TOKEN` never reaches `verify()`; the token is used only by `gh api` in the workflow step (`control-chrome-qualification.yml:286`). Never ships: `control/chrome/build.py:8-18` lists the installed tree (aresos_control, generated, settings, packaging, chrome/extension, chrome/packaging, launch.py, requirements.lock, native_host.py, build.py), matching `control/chrome/packaging/README.md:47-49`; `control/chrome/ci/` and `qualify.py` are outside it, and `test_the_recording_opener_never_ships` checks the markers against exactly that list and that the product module names no `Authorization`/`GH_TOKEN`/`GITHUB_TOKEN`/`install_opener`. The committed fixture `42687597384/api-response.json` holds one attestation (`repository_id`, `bundle_url`, `initiator`, `bundle`), no token material.

### NOTEs (optional)

- NOTE `attestation.py:148-155`: the refusal cases catch `except Exception`, so a transient verifier failure (e.g. TUF fetch) would count as a refusal. Asserting `subprocess.CalledProcessError` and that stderr names the source-ref mismatch would make the negative test stricter. Low risk: the positive verify just before uses the same cache dir.
- NOTE `test_qualification.py` workflow test: it inspects `if:` lines only. A new write step with *no* condition (e.g. a bare `git push`/`gh pr create`) would not be caught by this test; `qualify.py`'s guard covers only writes routed through `qualify.py`. Scanning `run:` bodies for `git push`, `gh issue`, `gh pr` outside the allow-listed steps would close that.
- NOTE `control-chrome-qualification.yml:229-241`: PR mode seeds the local bare remote with `main` only, so `publish()`'s "data branch exists → `held_verifier`" branch is never exercised against a real held record in PR mode (prepare's `verify_held` is). Seeding `origin/chrome-qualification` too, when it exists, would cover it.
- NOTE `control-chrome-qualification.yml:230-232`: the PR-mode publish step gets `GH_TOKEN` but `publish --remote` never calls `gh` (no credential helper, `held_verifier` not reached); the env line can go, least privilege.
- NOTE fork PRs: `delivery-attestation` and `qualification-publish` will fail on a PR from a fork (no `id-token`); fail closed, but every fork PR touching `control/**` will be red on this workflow. Acceptable, worth knowing.
- NOTE PR runs now add attestations (on `refs/pull/N/merge`) to the repository's attestation store. Digests are unique per run (`run` field), so they never share a digest with a main-published record; the product's unpaginated `per_page=100` listing (pre-existing, PR #27) is unaffected.
- NOTE `PROGRESS.md:10-11` claims the fixture verifies with real `gh` "on this Mac"; the only `gh` on this Mac's PATH is 2.94.0 (below the product's 2.102.0 floor), so I could not reproduce that locally. The CI log above supplies the same evidence.
