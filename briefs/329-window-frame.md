## What it is

The design is COMPONENTS.md 4.2 (the frame, "What labwc can draw", "What the frame needs from the look setting", A's `themerc` and `rc.xml` lines), 4.4's "For the build", 4.3's ten `snapping.overlay.*` lines, and sections 1 to 3 (the look pack, A's colours and Jersey 10, the grid). Build it as written; this brief adds only what the builder must decide or must not get wrong. The parts:

- The look pack (`/usr/share/aresos/look/`, package 320) gains the frame's 36 cells and its colours by purpose.

- Image checks, unit tests, `docs/design/WINDOWS.md`, and a headless proof in 320's harness.

## Decisions this brief takes

1. **Look A only; the look setting changes nothing yet.** One theme name for every look, `AresOS`, with the same geometry as every later look: a 40 px bar, 48 × 40 px buttons, a 2 px edge, Jersey 10 at 28 pt, corner radius 0. Nothing in this package writes `~/.local/share/themes/AresOS/`, so B (the default) and C show A, which is the fallback rule (4.7) and needs no code. `aresos-settings` and `aresos-indicator` don't change, and there is no `labwc --reconfigure` path: nothing changes the theme while labwc runs. Checked while writing this brief: this laptop's Pango gives Jersey 10 at 28 pt a logical line of exactly 40 px, the bar's height (4.2's "not verified" list; the harness confirms it in labwc).
2. **The generator** lives beside 320's, in `os/look/`. `make_pack.py` adds the 36 cells of 24 × 20 units using `LookA.title_button()` and `labwc_file()` from `reviews/312-component-study/tools/look.py`, which checks the SHA-256 of the repo's `Jersey10-Regular.ttf`. Add two top-level keys to `look.json`:
   - `frame_sprites` maps each labwc PNG filename to `sprites/frame/<filename>`. `aresos-indicator` still loads only the existing `sprites` entries (`Pack.__init__`).
   - `frame_colours` has `active` and `inactive` from `LookA.frame_colours(True/False)`, and `menu`, `switcher` and `snap` from their respective `*_colours()` methods. Keep their field names and add `shadow` to `active` and `inactive` (`#0000008c` and `#0000005a`, from `put_window()`'s black at alpha 140 and 90). Use `#rrggbb` for opaque colours (alpha 255) and `#rrggbbaa` only for alpha below 255, in both the manifest and `themerc`. Store `switcher.outline` and `snap.lines` as ordered arrays of hex strings.
   - `make_labwc_theme.py --pack <folder> --output <folder>` (about 120 lines, Python and Pillow) reads only the pack. It doubles each cell with nearest-neighbour to 48 × 40 px RGBA and writes `themerc` using labwc's keys, the shared geometry (including 24 px and 12 px shadow sizes) and colours from the manifest. B's sync step will run it later on B's pack.
3. **Committed, not generated in the image build.** The build stays a copy of `os/config` (no Pillow in the build), the image check pins the bytes, and reviewers see the files. A unit test regenerates both the pack and the theme and compares `themerc` and `look.json` byte for byte and every PNG by mode, size and RGBA pixels, not file bytes: PNG bytes depend on the Pillow and zlib versions, and CI's Ubuntu ones differ from the laptop's (320's pack test does the same).
4. **Ares-Crown stays in the image, unused, until after R29.** `rc.xml` stops naming it. Removing its files means rewriting release 28's own checks, which read main's Crown folder and its pin (`test_release28.py`'s `ThemeAndRcXmlTest` and the classifier fixture around line 2128; `release_diff.crown_pin()` and `Release28.extra()`), `linux-aresos`'s files, during R29's cut. So its 37 files and their pin stay, and its files stay in git history either way. Afterwards, `linux-aresos` points those tests at R28's recorded source, as B323 did for the lock, and removes the folder; the lead leaves that on the board.
5. **The menus.** labwc's built-in window menu and root menu stay as they are (no `menu.xml`; the layouts package brings one with the right-click layout menu), in A's colours, each row 40 px. Two lines beyond 4.2: `menu.width.min: 200` and `menu.width.max: 400`, because "Always on Top" measures 182 px at 28 pt plus 16 px of padding against labwc's default maximum of 200 px, and a cut row is a visible bug.
6. **The whole `themerc`** is 4.2's block, the two width lines, 4.4's `osd.*` block and 4.3's ten snapping lines, in that order, after a two-line header naming the generator. Join `switcher.outline` for `osd.window-switcher.preview.border.color` and `snap.lines` for both `snapping.overlay.{region,edge}.border.color` keys with commas and no spaces, preserving order and repeats (`#0d0d10,#edca77,#0d0d10` in A). The snapping lines colour the preview for today's drag-to-edge snapping. Keep labwc's defaults for the classic switcher, workspace note, magnifier, ToggleKeybinds mark, menu titles, hover backgrounds and XBM colours.
7. **No Super+Tab list and no cover filters here.** Super+Tab is not "almost nothing": its filter is `skipTaskbar="yes"` on `aresos.cover` and `aresos.black`, which takes away their foreign-toplevel handles, while the shell tells the covers apart by those handles (`COVER_APP_IDS` in `aresos-shell`), and `test_aresos_desktop.py` refuses any `skipTaskbar` in `rc.xml` ("the helper tracks the desktop by its foreign-toplevel handle"). So it needs its own start-up and shutdown check (4.5). It ships with the overview's first ship, together with Alt+Tab's `skipWindowSwitcher` on the same two rules. The cover rules, which the image checks grep byte for byte, stay untouched; Alt+Tab keeps listing a cover in the few seconds it is up, as today.
8. **Bindings.** Scrolling over the bar does nothing: 4.2's `<mouse>` block, starting with `<default />` so every other default stays (today's `rc.xml` has no `<mouse>`, so labwc loads the same defaults; `None` as the only action clears a binding, labwc-actions(5)). Shift+Alt+Tab is added (4.4). No other key or mouse binding changes, and no window rule.
9. **Programs that draw their own bar are unchanged** (Chrome, GNOME apps, frameless Electron; WINDOWS.md): the button order, its GSettings default and every decoration rule stay. So package 31's program list is not rerun; the harness checks a plain Wayland window and a GTK 4 window.

## The bar

Safe the way a good command-line tool or MCP is, not every edge case (decision 24, `docs/design/CONTROL.md`, "The bar"). Fix real harm: a window that can't be moved, closed or resized; a frame that hides content; a key or mouse binding lost; the world's always-below rule or its pointer lock disturbed; anything from the game's files in the repo, the image or the evidence; a change to the owner's running session (no `labwc --reconfigure` on his labwc, nothing written to his `~/.local/share/themes/`, `~/.config/` or `/usr`, the real compositor never touched; everything runs in the harness's container). Low-harm edge cases go into `reviews/329-window-frame/KNOWN-LIMITS.md` with the reason, not into another fix round. Own pixel art only, generated from the study, never drawn by hand or traced.
