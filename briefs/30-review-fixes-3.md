## Step A: the pictures

1. **A picture pass runs only when something changed** (OS lead, defect 1). Today the helper asks for a full pass every 3 seconds for the whole session, and each pass looks up and converts every program's picture again: measured on the laptop with 59 programs, about 228 ms of processor time per pass, 7 to 8 % of one core for as long as he is logged in, on the machine he plays on. Make it work as `Catalogue` does: a pass is asked for only when the catalogue's revision changed, when a cheap stat signature of what the lookup depends on changed (the icon roots, their theme folders and index files, the folders the lookup lists, and the files the last pass resolved), or when the last pass did not finish. Resolved paths are kept with the signature they belong to. The idle check itself stays cheap: say in the report what it costs on the laptop (the unchanged catalogue rescan costs 1.3 ms; stay in that order). Tests: an idle minute of ticks asks for no pass after the first; a new picture file, a replaced picture file and a changed catalogue each ask for exactly one; a pass that was cut short is asked for again.
2. **Breeze's pictures are found** (OS lead, defect 2). `resolve_icon` looks for `<theme>/<N>x<N>/<context>/` and skips SVGs in sized folders. Real Breeze is `breeze/apps/48/utilities-terminal.svg`, described by the theme's `index.theme`. On the laptop 8 programs have Breeze-only pictures and get none, among them Konsole, System Settings and System Monitor; the tests pass because they build an invented layout.
   - Read a theme's `index.theme` (the first icon root that has one for that theme speaks for all roots): its `Directories`, and each directory's `Size`, `Type` and `Scale`. Read it the way every other file here is read: through the checked, pinned descriptor, with a size limit and a limit on the number of directories; a broken or oversized index means the theme falls back to the fixed layout, with one log line. Directories with `Scale` over 1 are left out.
   - A root or theme without an index (his home folder, Flatpak exports) keeps today's fixed layout (`<N>x<N>/<context>/`, `scalable/<context>/`).
   - Order inside a theme, the smallest change to today's rule: PNGs by size, largest first, as today; then SVGs, `scalable` folders first, then sized folders, largest first. Themes stay `hicolor`, then `breeze`.
   - Sizes over 256 (the orchestrator's call on the OS lead's question about Waydroid's 512-pixel picture): a PNG folder over 256 and up to 1024 is used when the theme has nothing of 256 or less for that name, the smallest such first. The converter's own limits stay as they are.
   - The folder and file confinement of review fixes 1 (FIX 5) holds for every new path: nothing is listed or opened outside its icon root or a Flatpak deployment.
   - Tests take their layout from the real theme: a fixture with an `index.theme` you write yourself in Breeze's form (a few directories of each type; do not copy KDE's file) and SVGs at `breeze/apps/48/` and `breeze/apps/64/`; the old invented layout goes. A test for each rule above, and for a hostile index (a directory that points outside the root, an endless list, a huge file).
   - A check for the laptop that is not part of the suite (`os/tests/check_aresos_shell_icons.py` already is such a file): with the real icon folders, read-only and without converting, Konsole, System Settings and System Monitor resolve to Breeze files. In the report give counts only (how many programs resolve before and after); never list the owner's installed programs.
3. **One warning at start when pictures can't be made** (OS lead): when `bwrap`, `magick` or `prlimit` is missing, one WARNING names it and says that programs show without pictures. Today it is logged at DEBUG per picture. A test.
4. **`StartupTest` is self-contained** (OS lead, nit): `os/tests/test_aresos_shell.py`'s `StartupTest` calls `build()` without `environ`, so on the laptop it scans his real application folders and leaves the discovery thread running. Give it a temporary HOME, patch `desktop_directories` as the other `build()` tests do, and stop the thread.

End of step A: `python3 -m unittest discover -s os/tests -p 'test_aresos_shell*.py'` and `-p 'check_aresos_shell_icons.py'` pass on the laptop, each with `TMPDIR="$PWD/.work/30-installed-programs/tmp"`; the same test modules also pass with the registry's three programs reported missing (the orchestrator's `runner_sim` idea: `os.path.isfile` answering no for `/usr/bin/foot`, `/usr/bin/google-chrome` and `/usr/bin/kwrite`), because GitHub's runner has none of them; commit per fix, push, and write `reviews/30-installed-programs/PROGRESS.md` new (the old one is out of date: everything it lists as pending is done).

## Step B: the Flatpak start, the report, the hosted runs

1. **A Flatpak program started for real, once** (OS lead). `flatpak run` moves itself into its own `app-flatpak-…` scope, so the scope the helper made empties at once and the launch rests on the live process and the window's identity. That path was never exercised, and Discord on this laptop is a Flatpak. Extend `os/tests/check_aresos_shell_headless.py` with a third case: KCalc started through its real Flatpak desktop entry (`flatpak run`), in the check's own headless compositor, HOME and socket, as the two existing cases. It passes when the launch reports `focused` with the window `org.kde.kcalc`, stays open while the helper's own scope is empty, and reports `closed` with the return to the stand-in hub when the window closes.
   - The rules of the check stand: only while no Java runs from `~/.lunarclient/` and at least 4 GB are available; `DISPLAY` unset and `WAYLAND_DISPLAY` the check's own, so nothing can appear on his screen; if KCalc already runs in his session, skip the case and say so.
   - Stop only what the check started, by PID or by the scope's exact name, never by a program's name (`flatpak kill org.kde.kcalc` would end his own KCalc too). Afterwards no scope or process of the check's is left.
   - If `flatpak run` cannot be started this way without reaching into his session beyond the user manager's socket the check already links, stop, change nothing, and say exactly what it needs.
   - If the case fails because of the helper (the launch is reported failed or closed while the window is open, or the return never comes), that is a defect of this package: fix it inside the window rules as they are (hints, exact identities, the unowned-window rule), with a unit test that models the scope emptying at once, and say what you changed.
