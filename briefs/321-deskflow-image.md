## Why

## The trust model: what 321 adds

316's model holds (`briefs/316-input-portal.md`, "The trust model"). This package adds:

- **Two facts, both needed.** The allow-list in the image says *which program* may capture (Deskflow's proven ID and nothing else). A switch outside the image says *whether* sharing is on. It is off at first boot and after the update that brings this package: a program of the same user can pose as Deskflow (316's known limit), so nothing may capture until the owner has said so. No reason was found to ship it on. A caller whose ID is empty is refused whatever the list holds.
- **Only the owner turns it on; anything may turn it off.** The switch is one root-owned file, `/etc/aresos/input-portal/sharing` (content `on`; anything else, a missing file, or a file or folder that someone other than root can write means off, checked the way `trust.rs` checks the allow-list; the backend and the helper also treat it as off, and the helper writes nothing, when the file is not a regular file or when it or any folder above it is a symlink, is not root's, or can be written by someone else). Turning it on asks for his password in the password window he already knows (polkit, never kept: `os/config/usr/share/polkit-1/rules.d/00-aresos-maintenance.rules`, rule 2). Turning it off needs no password from the active local session (the owner at the laptop, and so any program running in his session): off is the safe direction.
- **Off closes what is live, and the backend sees Off by itself.** The backend checks the switch wherever input or clipboard would leave: when a session is made, at `Enable`, at each crossing before `Activated`, at each clipboard call, and again after every wait inside a clipboard call, before a descriptor is handed out (today `selection_read` in `portal.rs` checks, waits for the Wayland side, then returns the pipe). While any session exists it also rereads the switch at least every 500 ms, so Off needs no second process (a file watch may make it faster; the timer is the bound). Off means: forwarding stops at once (a flag the input path reads), any capture ends, every session closes, and no new clipboard transfer starts. **One end-to-end deadline, the polling interval included:** within 2 seconds of the switch changing, no further event reaches the client, the capture has ended and the sessions are closed; if the Wayland side has not confirmed the end of the capture within 1 second of the backend seeing Off, the backend exits, and labwc drops the grab with the connection. A new control command, `--revoke`, only makes this immediate; the switch runs it after turning sharing off.
- **Known limit: a clipboard pipe handed out before Off** (the lead, 2026-11-21; into `KNOWN-LIMITS.md` with this reason). Its ends are held outside the backend (`portal.rs`, `wayland/clipboard.rs`), so it can still finish carrying the one item the owner's session asked for while sharing was on. No new transfer starts after Off and Deskflow's session is closed, so nothing further leaves; a revocable relay in both directions would be a new design for that one item.
- **The way out must work against a stuck backend.** `--release` asks the backend over the bus, and the backend answers only after its Wayland side has confirmed that the pointer lock and the keyboard are given back (today `ForceRelease` answers while the teardown is only queued: `portal.rs`, `force_release`). Before it asks, `--release` pins the instance it talks to: the process that owns the backend's bus name, held as a pidfd (the bus's `GetConnectionCredentials` `ProcessFD`; or `pidfd_open` on its PID and a second look that the same connection still owns the name), whose executable is the installed backend and whose user is the caller's. No confirmed answer within 2 seconds: SIGKILL through that pidfd, never by PID or by name (labwc drops the grab with the connection: 316's harness, test 3).
- **During a capture labwc runs two bindings and no others:** the release key and the recovery terminal. A binding that closes a window, starts the window switcher or moves the focus while the owner types for the Mac is a release blocker ("What to build", 6).
- **Deskflow sends only to the Mac it has verified.** The portal can't see the network side, so this is Deskflow's own check: TLS on and client fingerprints checked (`[security]`, `tlsEnabled` and `checkPeerFingerprints`, both on by default; the server then drops a client whose certificate isn't in its trusted-clients list: `src/lib/net/SecureSocket.cpp`, 1.27.0). But it accepts *any* fingerprint in that list, and the user's own settings can turn either check off (`src/lib/deskflow/ServerApp.cpp`, near line 412). So every shipped launch path (the hub's entry and the start hook) makes TLS and peer checking effective whatever the user's settings say, or refuses to start sharing; and the trust list holds only the Mac's verified fingerprint: the laptop test clears it and adds the one the owner compares (laptop test 3). The image ships no Deskflow setting that turns either off. VM test 9 shows a stranger with the right name, a stale trusted entry and peer checking turned off in the user's settings all leave the Mac as the only peer that gets anything.
- **The idle watchdog goes off by default.** Upstream ends a capture after 15 seconds without input. The owner reads on the Mac for longer than that every day; control would fall back to the laptop unseen and his next keys would land in a laptop window. With the release key hardened as above, and 316's teardown for a dead client, the watchdog's default becomes 0 (`ARESOS_INPUT_PORTAL_IDLE_TIMEOUT` still sets it).

6. **Shortcuts during a capture (step 1c; item 8).** During a capture the backend's overlay surface holds the keyboard, but labwc still runs its own bindings first. `Close` acts on the last active window, which stays set under a layer surface, so Alt+F4 typed for the Mac closes a laptop window; Alt+Tab starts the window switcher, which then eats keys. labwc 0.9.6 can't switch its bindings off for a layer surface: it doesn't implement `keyboard-shortcuts-inhibit-unstable-v1` (nothing in `src/server.c`, `src/seat.c` or `src/input/keyboard.c`, nor on upstream's main branch), and `ToggleKeybinds` works per window.
   - **The design: a second patch in 311's stage** (`os/labwc/`, beside `0001-…`), by one of two mechanisms; step 1c (Fable) picks the smaller sound one and writes why in `PROGRESS.md`. *Layer focus:* labwc gates its bindings while the backend's capture surface holds exclusive layer focus (`src/layers.c`), recognised by its layer namespace (`aresos-input-barrier` today, `wayland/state.rs`), so other layer surfaces, such as the laptop home or a future overview, keep their bindings; the backend can't see this patch, so the image check and the harness prove it. *Inhibitor:* labwc offers `keyboard-shortcuts-inhibit-unstable-v1` through wlroots' helper and makes an inhibitor active only for a layer-shell surface that holds the keyboard exclusively, never for an app window, so no app can switch Alt+Tab off; the backend asks for one on its capture surface and reports `Activated` only after labwc's `active` event, so a labwc without the patch can't capture (`wayland-protocols` is already in `Cargo.lock`; add no crate). **Either way:** keyboard and mouse bindings are gated, pending release and repeat actions included (`src/action.c`); labwc handles no window-switcher or menu keys and sends every other key to the surface; only bindings marked `allowWhenInhibited="yes"` (modelled on `allowWhenLocked`) run, and `rc.xml` marks exactly `W-S-Escape` and `W-C-Escape`; VT switching stays.
   - **The two-chord rule stands, so step 1c removes the backend's legacy chord** (Ctrl+Alt+Escape, `is_panic_key` in `wayland/state.rs`; its own comment calls it a convenience, not a safety mechanism). During a capture Ctrl+Alt+Escape goes to the Mac like every other key.
   - **Cost.** A small compositor patch (about a hundred lines for the inhibitor, likely fewer for layer focus) carried until upstream has the like (offer it upstream), a new labwc build with its lock entries (`linux-aresos`), a review of the patch, and one more step, on Fable. Volume, mute and brightness keys go to the Mac during a capture like every other key (the owner's answer, T459).
   - **Gate, in the harness (it runs the stage's labwc):** during a capture Alt+F4 closes nothing, Alt+Tab opens no switcher, a binding held as the capture starts fires no release or repeat action, Ctrl+Alt+Escape reaches the client, the next key after each reaches the client, the chord releases, and `W-C-Escape` releases and opens the terminal; with layer focus, a test layer surface with another namespace keeps its bindings. If the patch doesn't hold within the step, stop and report: the package does not ship with a window-closing or focus-moving binding live in a capture.
   - **The table (step 4).** Press each binding of the real `rc.xml`, Ctrl+Alt+Escape (the backend's former chord), R29's Super key for the search if it is on `main`, and the mouse bindings (Alt+drag, scroll on the desktop). One line each: what the laptop did (windows, focus), whether the capture held, and where the next key landed. Anything but "nothing, held, the client" for an unmarked binding is a release blocker.

## The bar

Safe the way a good command-line tool or MCP is, not every edge case (decision 24, `docs/design/CONTROL.md`, "The bar"). Fix real harm: keystrokes or clipboard reaching a program that shouldn't get them, keys in a log, a capture with no way out, sharing that can't be turned off, a change to the owner's session outside the image. Low-harm edge cases go into `reviews/321-deskflow-image/KNOWN-LIMITS.md` with the reason, not into another fix round. Every reviewer prompt states this bar.
