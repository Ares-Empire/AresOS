Ships as its own release after R29; the release work is `linux-aresos`'s.

## Why

The owner uses Deskflow every day. Under AresOS the laptop is the Deskflow **server**: its mouse and keyboard move over to the Mac, with a shared clipboard. Package 311 made labwc hold a pointer lock on a layer-shell surface (on main, rides R29). Package 316 built the portal backend `aresos-input-portal` in `os/input-portal/` (on main; 72 unit tests, 81 harness checks; nothing in the image uses it). This package puts it into the image, installs Deskflow, and gives the owner the two things he touches: a switch for sharing and a key that always brings the mouse back.

## The trust model: what 321 adds

316's model holds (`briefs/316-input-portal.md`, "The trust model"). This package adds:

- **Two facts, both needed.** The allow-list in the image says *which program* may capture (Deskflow's proven ID and nothing else). A switch outside the image says *whether* sharing is on. It is off at first boot and after the update that brings this package: a program of the same user can pose as Deskflow (316's known limit), so nothing may capture until the owner has said so. No reason was found to ship it on.
- **Only the owner turns it on; anything may turn it off.** The switch is one root-owned file, `/etc/aresos/input-portal/sharing` (content `on`; anything else, a missing file, or a file or folder that someone other than root can write means off, checked the way `trust.rs` checks the allow-list). Turning it on asks for his password in the password window he already knows (polkit, never kept: `os/config/usr/share/polkit-1/rules.d/00-aresos-maintenance.rules`, rule 2). Turning it off needs no password: off is the safe direction.
- **Off closes what is live.** The backend checks the switch wherever input or clipboard would leave: when a session is made, at `Enable`, at each crossing before `Activated`, and at each clipboard call. Off there means: refuse, end any capture, close every session. A new control command, `--revoke`, does the same at once; the switch runs it after turning sharing off. So even if something removes the file behind the backend's back, the next crossing stays local.
- **The way out must work against a stuck backend.** `--release` asks the backend over the bus. If the backend gives no answer within 2 seconds, `--release` ends the process that owns the backend's bus name (labwc drops the grab with the connection: 316's harness, test 3, SIGKILL).
- **The idle watchdog goes off by default.** Upstream ends a capture after 15 seconds without input. The owner reads on the Mac for longer than that every day; control would fall back to the laptop unseen and his next keys would land in a laptop window. With the release key hardened as above, and 316's teardown for a dead client, the watchdog's default becomes 0 (`ARESOS_INPUT_PORTAL_IDLE_TIMEOUT` still sets it).

## What to build

1. **Backend follow-ups (step 1), each with a unit test.** Item 9's five: drop EIS input once emulation has stopped, without losing the first keys of the next capture (REVIEW-3, 1); end the process when the Wayland connection ends (REVIEW-2, 2); compare the caller with the sessions' frontend in `authorize` (REVIEW-3, 2; REVIEW-2, 3); keep a reused session path's object (REVIEW-2, 4); destroy only the portal's own clipboard source on release (REVIEW-3, 3). Plus this brief's three: the switch check and `--revoke`, the 2-second fallback in `--release`, the watchdog default. Rerun the harness (`os/input-portal/harness/run.sh`); add harness checks for the switch (off: a listed ID is refused; turned off during a capture: capture ended, sessions closed, next crossing local, clipboard call refused) and for a stopped backend (SIGSTOP, then the chord frees the input). The harness installs its own switch file inside its container. Update `UPSTREAM.md`'s list of our changes.

2. **Item 1, the output check (step 2), before Deskflow, the routing, the key or the switch's helper and window are built.**
   - **How.** A throwaway check build (never published, so it needs no OK from the owner): a new mode `check_build=deskflow` beside `control` in `os/ci/check-build.sh` and `os-image.yml`. `control` is the pattern: it builds the image, puts a CI-only test layer on top (`os/ci/control/runner.sh layer`), makes a disk and boots its own VM pass. The layer and the pass live in `os/ci/deskflow/`. The VM is `os/ci/vm.py`'s (QEMU q35 with `virtio-vga`), so labwc runs on a real DRM output, `Virtual-1`, that has a list of modes: the case 316's headless harness could not show. Guest commands go over the `org.aresos.ci` channel (`os/ci/overlay/checks.py`), keys over QMP (`os/ci/qmp.py`). For this step the layer needs only the backend from the new build stage (item 3), `wlr-randr`, and 316's listen-only client (`wl-harness outputs`).
   - **A second screen.** `virtio-vga,max_outputs=2`, with head 2 connected and disconnected from the host (QEMU's D-Bus display `SetUIInfo`, or a VNC server on head 1). If that doesn't work within a third of the step, hot-add and remove a second `virtio-gpu-pci` with QMP `device_add` and `device_del`. If neither works, say so: unplug and replug is then a laptop-only check.
   - **The runs.** One boot for each of three states: nobody bound to `zwlr_output_manager_v1`; the listen-only client bound; the backend running (start it with `aresos-input-portal --status`). In each: (a) `wlr-randr --output Virtual-1 --off`, then `--on`, three times at the preferred mode; (b) the same at another mode from the list; (c) the second screen unplugged and replugged three times, and switched off and on while plugged; (d) a VT switch away and back; (e) last, because 316's analysis expects it to abort: a custom mode (`--custom-mode`), then off and on. After each: labwc's PID unchanged, no `Assertion` in its journal, and the backend's log shows the new snapshot.
   - **The gate.** (a) to (d) must keep labwc running in all three states; then the package goes on, and (e)'s result is a known limit ("no custom mode while the backend runs"), reported upstream. If one of (a) to (d) aborts with a client bound, stop after this step and report to the lead; step 3 does not start.
   - **If it aborts, two ways.** *Patch the compositor in 311's stage:* the assertion is in wlroots (`types/wlr_output_management_v1.c`), which the image takes as Fedora's `wlroots0.19` RPM, and 311's stage builds only labwc. So this is a second source-RPM build with its own lock entries and loaded-image pins in `linux-aresos`'s files, carried by every release until Fedora ships a fix, with a compositor-wide review and rehearsal. *The backend stops holding the protocol:* read the screens from `wl_output` and `zxdg_output_manager_v1` (labwc offers both, and every panel uses them), and never bind `zwlr_output_manager_v1`; the harness control already shows labwc survives with nobody bound. **Recommended: the backend.** It is our own code, the harness tests it without a VM, and nothing in `linux-aresos`'s files moves. Cost: one extra step on Fable (it changes 316 step 2's snapshot design): `wayland/heads.rs` replaced, `screens.rs` adapted, the zone unit tests re-aimed, harness test 1 rerun in full, and a fresh review of that diff. It also closes the limit "logical sizes are computed, not asked for". The compositor's fault stays for other clients and is reported upstream.
   - **The laptop part** (the external monitor switched off and on, unplugged and replugged, the lid, suspend) is the first check of the laptop test below and needs the owner's direct OK.

3. **The image (steps 2 and 3).**
   - **Build stage.** `FROM` the exact `BUILDER_IMAGE` of `os/input-portal/toolchain.env` (an image check compares the two), copy only what `build.sh` reads (no `harness/`, no `dev/`), and run `os/input-portal/build.sh <source> /out` as is. It makes its two pinned downloads first and compiles and tests offline, as 311's stage has its inputs fetched and checked before the build. No Rust source or toolchain may reach the final image. Builder check: is the binary the same bytes in two check builds? If so, pin its SHA-256 and let a release build require the pin, as the mod jar's is; if not, record the hash per release and say why (R29's rule for 311's RPM, `STATE.md`).
   - **Installed files**, root-owned: `/usr/libexec/aresos-input-portal` (0755); 0644 each: the D-Bus service in `/usr/share/dbus-1/services/`, `aresos-input.portal` in `/usr/share/xdg-desktop-portal/portals/`, `/usr/share/aresos/input-portal/allowed-apps`, and the `LICENSE` with the notices of the linked crates (if collecting those costs more than a small script, list it as a limit for the lead).
   - **Routing.** `/usr/share/xdg-desktop-portal/AresOS-portals.conf` sends `InputCapture` and `Clipboard` to `aresos-input`. The image has no such file today, so adding one changes how *every* interface is resolved. First record, on an image without the file, which backend the real xdg-desktop-portal picks for each interface under `XDG_CURRENT_DESKTOP=AresOS` (its verbose log); write the file so each keeps that route, one line per interface; show the before and after tables differ only in the two new lines. Never `XDG_DESKTOP_PORTAL_DIR` (upstream's README says why). With only `InputCapture` routed, upstream saw Synergy loop on new sessions: check Deskflow makes one session and keeps it.
   - **Deskflow, native.** Fedora's `deskflow` RPM and what it pulls in, through `os/packages.lock.json` (`check_build=resolve` gives the candidate lock). First thing in step 3: which version Fedora 44 has, and that this build has InputCapture and the clipboard over the portal. If it doesn't, stop and report; a Flatpak or a build of our own is the lead's call.
   - **Its `app_id`, proven.** Through the real frontend, record the ID that reaches `CreateSession2` when Deskflow is opened from the hub. The hub starts apps in a scope `app-aresos-<id>-<launch id>.scope` (`os/config/usr/libexec/aresos-shell`, near line 2280), and the frontend reads a host program's ID from that name unless the program registers one itself; check both Deskflow's window and its core process, and a launch from a terminal (expected: refused, and written down). That exact ID, and nothing else, goes into `allowed-apps`.
   - **Flatpak** (`reviews/316-input-portal/BRIEF-RECHECK.md`, finding 1). Show that a Flatpak with another ID is refused (a sandbox whose `.flatpak-info` names another ID is how the frontend sees one). If the native ID is `org.deskflow.deskflow`, Flathub's Deskflow has the same one. That collision stays the known limit 316's brief accepted (lead, 2026-11-21): sharing is off until the owner turns it on, Flathub's namespace is controlled, and it is the same program. No AresOS desktop entry or hidden RPM entry to avoid it; record it in `KNOWN-LIMITS.md`.
   - **Image checks** (`os/ci/image-checks.sh`, `os/ci/check-image.sh`): each file above with its owner, mode and content; the allow-list holds exactly one ID; `AresOS-portals.conf` routes the two interfaces and names every other one; the service's `Exec=` and the `.portal` file's names agree; the `rc.xml` binding; the two polkit actions against `os/ci/polkit-review.json`; no switch file in the image.

4. **The release key (step 3).** In `rc.xml`, as 316's harness has it (`reviews/316-input-portal/evidence/step3-harness/labwc-rc.xml`): `W-S-Escape` runs `/usr/libexec/aresos-input-portal --release`. `aresos-session` starts labwc inside `dbus-run-session`, so labwc should hold the bus address; prove it on the real session in the VM: labwc's `DBUS_SESSION_BUS_ADDRESS` is the bus the backend's name lives on, the backend (started by the bus's `Exec=`) has `WAYLAND_DISPLAY` and `XDG_CURRENT_DESKTOP`, and the chord pressed on QEMU's keyboard during a real Deskflow capture ends it.

5. **Sharing on and off (step 3; item 7).**
   - **What the owner sees.** In the hub's apps, next to Deskflow, an entry "Mouse and keyboard sharing". It opens a small window: "Sharing is off. Deskflow can't use this laptop's mouse, keyboard or clipboard." with "Turn on" and "Close". "Turn on" brings the password window; after it the window says "Sharing is on. Super+Shift+Escape brings the mouse back at any time." with "Turn off". "Turn off" asks nothing and stops Deskflow's use at once. The choice survives restarts and updates. When Deskflow asks while sharing is off, the backend opens this window once per login, so he meets it where he needs it. The window is a plain dialog from a program the image already has (`kdialog` if it is there; add no package for it); the Minecraft look comes with the other OS pieces (`docs/design/COMPONENTS.md`).
   - **The pieces.** `/usr/bin/aresos-input-sharing` (no argument: the window; `status`, `on`, `off` for the recovery terminal and for agents; `on` always goes through the password window) and its desktop entry. A root helper, `/usr/libexec/aresos-input-sharing-set on|off`, run through `pkexec`: fixed paths, no other input, writes or removes the switch file in one rename, one journal line. Two polkit actions: on is `auth_admin` for the active local session and `no` otherwise; off is `yes` for the active local session. After `off` the program runs `aresos-input-portal --revoke`.
   - **Why this and not less.** A file the user can write could be switched on by any program. A setting inside Deskflow is Deskflow's own word. The password window is how AresOS already asks for the owner's say, and it needs no new design.

6. **Bindings during a capture (step 4; item 8).** Press each binding of the real `rc.xml`, upstream's Ctrl+Alt+Escape, and R29's Super key for the search if it is on `main`. The rule: `W-S-Escape` and `W-C-Escape` (the recovery terminal) must stay live. Any other binding may stay live only if, during a capture, it neither takes the keyboard focus nor closes or switches a window; the volume, mute and brightness keys pass that. For one that fails (expected: Alt+F4, Alt+Tab, and a search that opens on a lone Super, which is Cmd on the Mac and would end the capture): a binding that runs a command gets a guard that does nothing while `--status` reports a capture; a built-in action (Close, NextWindow) that can't be guarded goes to `KNOWN-LIMITS.md` with what it does, and the lead decides whether it is worth a labwc patch.

## Tests

**In the VM** (`check_build=deskflow`; the test layer adds a Deskflow *client* under Xvfb in the guest, a window that records its input there, and `wl-copy`/`wl-paste`). QEMU's tablet is an absolute pointer: add a relative `usb-mouse` over QMP if the crossing or the motion needs one. Typing the password into the polkit window follows 22d's dialog driver (`os/ci/tools_local.py`: wait until the window exists).

1. Item 1's runs (above), before everything else.
2. Sharing off (first boot): Deskflow's session is refused, no crossing captures, the window opens once. On, with the password: one session, kept. A program calling `pkexec … on` without the password gets nothing.
3. Capture with the real Deskflow and the real xdg-desktop-portal: crossing, motion, buttons, scroll and keys reach the client; none reaches a laptop window. Item 4: the frontend gets every signal (the capture works at all, and `Deactivated` arrives), and after 20 clipboard transfers each way the frontend holds no more open file descriptors than before.
4. Item 5: after the chord, the client sees Super and Shift released (no stuck modifier). If they stick, the backend sends the releases before it ends the capture.
5. The release key against a stopped backend; 60 seconds without input and the capture still holds.
6. Item 6: kill the backend while armed; Deskflow's next session starts it again through the bus with the right display, and a crossing captures again. The same after xdg-desktop-portal restarts, and after logout and login.
7. Off during a capture: the pointer is local at once, the client hears the session close, a clipboard copy no longer reaches it; on again needs the password. On and off both survive a reboot.
8. Item 8's table, one line per binding. The Flatpak refusal. A trace-level run: no key, coordinate or clipboard text in any log or journal line, the helper's included.

**On the laptop** (after the final review and the installed release; the owner's direct OK in this session, and he saves his work first: a labwc abort ends the session):

1. Item 1 on real screens, with the backend running and sharing still off: `wlr-randr --off` and `--on` on the external monitor; unplug and replug it three times; the lid; suspend and resume; a VT switch. labwc's PID stays. No custom mode.
2. He finds the switch in the hub and turns it on with his password.
3. The Mac's Deskflow client pointed at the laptop under AresOS (316's brief, "Not in this package", has both addresses to confirm; the Mac's setting is his to change and to change back for Windows).
4. Crossing to the Mac and back: where the cursor lands coming back, with the external monitor and without it.
5. Typing on the Mac, with Cmd shortcuts; then Super+Shift+Escape: the mouse is back and no key is stuck on the Mac.
6. The clipboard both ways (text).
7. Twenty seconds without touching anything while on the Mac: the next key still goes to the Mac.
8. Item 8's keys on the real keyboard: volume, mute, brightness, Alt+Tab, Alt+F4, a lone Super.
9. In the world and in a game: with the game holding the pointer nothing crosses; note what happens in its menus.
10. Turning sharing off while the Mac is connected: the Mac can't be reached, the clipboard is no longer shared, and on again asks for the password. After a restart the choice is as he left it.

## The bar

Safe the way a good command-line tool or MCP is, not every edge case (decision 24, `docs/design/CONTROL.md`, "The bar"). Fix real harm: keystrokes or clipboard reaching a program that shouldn't get them, keys in a log, a capture with no way out, sharing that can't be turned off, a change to the owner's session outside the image. Low-harm edge cases go into `reviews/321-deskflow-image/KNOWN-LIMITS.md` with the reason, not into another fix round. Every reviewer prompt states this bar.

## One question for the owner

Steps 1 to 3 don't wait for it; until he answers, the build is without autostart.

- **Question:** once you have turned sharing on, should the laptop start Deskflow by itself every time you log in, so the Mac just connects? Or do you open Deskflow from your apps when you want it?
- **Advice:** start it by itself while sharing is on. You use it every day; "on" should mean it works after login, and turning sharing off stops it. It costs one more small piece (a start hook in the session, `linux-aresos`'s file, and Deskflow started without its window covering the world), built at the end of step 4.
- **Options:** "Start it by itself" / "I open it myself".
