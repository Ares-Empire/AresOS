terminal and he approves each one by typing his password into the desktop's password window. 22d does that for
**installing new owner tools**, the step every release starts with (a release's reference travels only in the tools
bundle). Tools version 4. The stick and the tty3 console stay as the emergency route, rule for rule.

Owner on record: board #265 (2026-11-14) "I don't really need the tools yet … I'd wait": v3 never goes on the laptop;
**v4 installs over v2** (`851eb742…`). Board #266: step 0's OK. The owner's limit (F1) was put to him in plain words
on 2026-11-14 (the window stops accidents, not a tricked Claude; he may keep the stick for tools instead); nothing

## Decided (the integrator; changeable, shown to the owner at the "try this" stage)

1. **Approval = the password window** (note section 1, option A). No new sudoers rule, polkit action, service or check
   inside the tools. The image's `timestamp_timeout=0` is the enforcement.
2. **The generated line.** `SUDO_ASKPASS=/usr/bin/ksshaskpass /usr/bin/sudo -k -A -p '<label>' bash -c '<script>'`
   (absolute `/usr/bin/sudo`: `~/.local/bin` is first on his PATH). `bootstrap.py` generates every such line,
   `commands.json` holds each one, the guide quotes them, and the tests hold all three equal. The **label** is
   `AresOS owner tools <first 8 hex of the fingerprint>: <action>` and must match none of ksshaskpass 6.7.5's
   remembered-prompt patterns (a unit test lists the 16 patterns and checks every generated label against them; step
   0 saw `Unable to parse phrase` for the test label).
3. **One window per "go"** (F2). One generated line per guide box. The tools-only box is one line: the folder block,
   then the new tools' `check` and `title` in the same root shell, stopping at the first STOP. Other owner commands
   keep one line each, each with its own label.
4. **The window as it looks** (STEP-0): title bar "Enter SSH Credentials" (ksshaskpass's fixed title), the AresOS
   label inside, Password, OK, Cancel. The guide says so exactly. A root-owned AresOS helper with its own title is a
   next-image item, not 22d.
5. **The bundle's identity** (note section 2, anchor b, plus F3, F4, F7):
   - The **announced commit** is the integrator's board note for the owner with the full commit hash and the
     fingerprint. Claude's lines take that hash as their only input.
   - **Claude's lines as `ares`** (fetch, refuse unless the commit is on `origin/main`, `git archive` of that commit
     into a fresh folder at `bootstrap.py`'s path, the payload's own fingerprint equal to the announced one) are
     generated by `bootstrap.py`, chained so any failure stops, pinned in `commands.json` and tested, including the
     refusal for a commit not on `origin/main` and for a dirty or stale checkout. The root line comes from that
     commit, never from the working tree.
   - **His check, part of his rule** (F3): before typing, he compares the 8 characters in the window with line 1 of
     `docs/OWNER-TOOLS.md` on GitHub on his phone. That file is new, short, and exactly: line 1
     `Owner tools version <N>: <first 8 hex>`, line 2 the full fingerprint, then two sentences saying what it is. A
     test holds it equal to the payload, the block's literal and the label.
6. **Records** (note section 3; F8, F9, F10): the tools' records stay root-only and unchanged; the receipt gains the
   source (stick with its volume UUID, or folder) and the caller (login uid, terminal or not). `export` without a stick
   writes its checked copy under `/run` (root-owned folder, readable only by the calling uid), and says plainly that
   the copy is on this laptop, not off it; "SAFE TO REMOVE ARESTOOLS" stays the only proof of an off-laptop copy.
   `export` to a stick whose bundle this laptop installed before (`retired-tools`) is accepted.
7. **The route decision** (note section 2, "What changes in v4"): which block ran decides the route, never whether a
   stick is plugged in. Stick block: today's rules, all of them, unchanged. Folder block: no terminal test, no stick.
   The journal keeps schema `tools-update1` and its fields and adds `source`; before publication v4 writes nothing new
   under `/var/lib/ares` except that key (F8). A folder-started update resumes from either route; a stick-started one
   only from that stick. The first installation (typed serials) refuses on the folder route, whatever the terminal.
8. **After a change of what starts next,** Claude posts the title's lines (systems and boot-menu rows, no serials) to
   the board under topic `aresos`, so they reach his phone (note open question C). A guide rule, no tool change.
9. **A STOP on the routine route** (F12): Claude reports the STOP line to him word for word, runs the folder `export`,
   and tries nothing else; the guide gets a short card for it beside `docs/EMERGENCY.md`'s.
10. **The caller can end** (F15): Claude starts each line in the background and waits for it; if he has not answered
    within 10 minutes, Claude stops that sudo (by the PID it started) so the window closes and nothing runs. The guide
    says so; the rehearsal shows it.
11. **Review 8's follow-ups:** finding 2 (a cleanly stopped `update` leaves its record open) and finding 5 (name
    `layout abandon` after a restart) ride with 22d, in their own step after the trust change is reviewed (F15, F16).
    Finding 8 waits. Finding 3 goes into the record step.
12. **The stick refresh from AresOS** (F11, note question B) is not 22d: package 22e (Opus, small) turns the lead's
    reviewed one-off script (`~/aresos-tools-session/write_stick.py`, review SAFE 2026-11-14) into a generated, tested
    route. Until then the guide names the Windows box. Claude asks for the stick about once per release.
13. **No council.** Step 2's council (online updates) gets the open question of an approval outside the laptop and
    F6 (the laptop's GitHub token can push workflows; the identities in `history.json` are branch refs).

## Rules for every step

- The laptop is the owner's: never run `/var/lib/ares/at` or any owner tool, `sudo`, ostree, bootc or rpm-ostree
  (not even read-only); no disk or boot changes. Tests use fakes. Run only the `os/tests` modules you touch, one at a
  time; never `test_owner_update` locally; never a pattern-less discover. `ARESOS_MODEL_SCOPE=slice` locally.
- Watch any run with `gh run watch <id> --exit-status --interval 60`. Only the integrator dispatches VM runs.
- The repo is public: no personal data, never `--no-verify`. Never merge, never push to main.
- A `JUDGMENT-CALL` goes in the report for the owner; a `PLAN-GAP` stops the step.

## Decisions after review 2 (integrator, 2026-11-15)

Review 2 (`reviews/22d-tools-without-stick/REVIEW-2.md`, Fable, at `4cdd7b28`) found the tools right and asked for
changes around them. All of it is accepted; these replace the matching parts above.

- **Decision 10 is replaced (R1).** Claude never signals the sudo it started. After 10 minutes without an answer it
  stops the password helper: the `ksshaskpass` process whose parent is that sudo (it runs as `ares`). sudo then ends as
  after Cancel (`sudo: no password was provided`, exit 1), and that line is how Claude knows nothing ran. If the helper
  is already gone, he has answered: Claude waits for the line's result and stops nothing. The guide sentence, the
  walk stage and the harness change together; the harness asserts the helper is gone, sudo's message and exit status,
  and that nothing changed.
- **Decision 9 gains a go (R2):** after a STOP Claude copies every STOP line to him word for word, asks for his go, and
  only on his go runs the export line. After a **STOP tools folder** (Claude's own line: no root command ran) there is
  no export and no window. The card says what Claude does with `/run/ares-records`: reads it to help, never copies it
  into the repository, a pull request or the board (disk serials, firmware entries). It also says that the tools'
  "Keep the current administrator session open" line is for the console; on this route nothing is lost (R5).
- **Decision 5's root line comes from the commit (R3):** Claude takes `tools-routine` and `export-routine` with
  `git -C /var/home/ares/AresOS show <commit>:os/owner-tools/commands.json`; the checkout check stays. Pinned in a test.
  The ares line verifies the commit's own `SHA256SUMS` against the pinned fingerprint before it empties the folder (N2),
  so a refusal leaves the folder as it was. The guide says Claude brings the checkout to the commit only by a
  fast-forward pull, never a reset or a checkout over other sessions' work (N7), and that no other session runs an
  owner command meanwhile (N8).
- **His check has an address (R4):** the box prints `github.com/Ares-Empire/AresOS/blob/main/docs/OWNER-TOOLS.md`;
  he keeps it as a bookmark, looks for `main` in it, and never uses a link Claude sends at that moment.

- **The stick falls behind (R6):** one sentence in the routine box and one in "A tools command stopped": after a
  routine install the stick still holds older tools; it still takes records (with the line `media.py` prints for a
  retired bundle, quoted) but cannot bring the current tools until Claude writes it again (package 22e).
- **The prefix (N1, N5):** `/usr/bin/bash` after sudo; the prefix also clears `SSH_ASKPASS_PROMPT`

  window whatever the caller's environment says.
