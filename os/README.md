# AresOS image and private release

This package derives Bazzite's signed `bazzite-nvidia-open` KDE desktop image
and replaces its session with greetd → labwc → foot. The workflow publishes
private GHCR releases and signs their digests with GitHub OIDC. It contains no
Minecraft, Prism, installer or hardware setup. Do not use the CI VM disk as an
installer or as a system containing valuable data.

`Containerfile` pins the base digest. `keys/bazzite.pub` is Universal Blue's public
verification key, copied from the upstream revision recorded in
`manifest/base.json`. CI runs the upstream
[documented verification method](https://github.com/ublue-os/bazzite#verification)
against that digest before building. This authenticates the base container;
the derivative has a separate workflow-identity signature. Neither signature
qualifies hardware Secure Boot.

`packages.lock.json` records the NEVRAs and SHA-256 hashes of added RPMs. A
resolution or content mismatch fails the build. The complete installed RPM list
and unchanged kernel/NVIDIA package subset are generated inside the image under
`/usr/share/aresos/manifest/` and exported by CI. Fedora repository RPM signature
checking remains enabled. The lock was generated by the first successful CI
package resolution; missing pinned RPMs or different content fail the build.
Package 21 re-resolved it with `gh workflow run os-image.yml --ref <branch> -f
check_build=resolve`, which inventories the pinned base and resolves inputs
without building.

`google-chrome.lock.json` pins Google Chrome's exact RPM (NEVRA, URL, SHA-256)
and Google's signing key (`keys/google-linux-signing-key.pub`, SHA-256 and
fingerprint); Chrome is not in Fedora's repositories. The build adds no
repository, removes Google's daily cron job and the imported key, and keeps
Chrome under `/usr/lib/opt/google` (`/opt` is `/var/opt` on bootc), with
`/usr/bin/google-chrome` pointing there and `/opt/google` linked at boot. A new
Chrome arrives only with a new AresOS release; if Google withdraws the pinned
RPM, the build fails until the pin is renewed.

`-f check_build=build` builds the branch image into the runner's local storage
and checks the image itself (`ci/check-image.sh`, `ci/image-checks.sh`,
`ci/polkit-check.js`). That job has read-only permissions and no secrets; it
never pushes, signs or publishes.

The `ares` account is UID 1001 and, since the owner's 2026-11-09 decision
("Like Windows", package 21), a member of `wheel` behind its own password. The
image sets no password, so `sudo` fails until the owner sets one; sudo asks for
it every time and keeps no ticket (`/etc/sudoers.d/aresos-everyday`), and the
build refuses any passwordless sudo rule.
Its image-owned `sysusers.d` declaration also creates it during boot when the
installer's locally modified passwd/group files survive the rebase. The
installer administrator is preserved at UID 1000; neither account is renumbered.
greetd auto-login starts it on VT1. Super+Ctrl+Escape opens another terminal.
Ctrl+Alt+F3 uses labwc's built-in VT switch to an independent getty. A deployment
must provision password-protected administrator `ares-recovery`, UID 1000 and
member of `wheel`, in Bazzite's account creation before switching. The exact
account and private-pull procedure belongs in INSTALL §6; real installer UI
qualification remains a separate gate. The two original VM passes alone set a
random root password in their file-backed disks and test authentication through the unchanged
`login` PAM stack, with both wrong-password rejection and correct-password
acceptance/account validation. It separately asserts a running tty3 getty on
`/dev/tty3` and the recovery VT switch. The current
[verification report](../reviews/06-image-release/REPORT.md) records the exact CI
results and remaining qualification limits. This credential
and the VM disk are never uploaded or committed. The separate switch harness
authenticates the recovery administrator over the stock serial TTY. It also
requires QMP keyboard login on the real tty3 and password-authenticated sudo
after rebase; 06c's final switch-only run passed both assertions on real tty3.
06d adds logout/getty confirmation, deployment inspection before each reboot,
and a bounded rendered-stock-greeter check. The GRUB recovery promotion path
remains explicitly untested in INSTALL's open release gates; a normal rollback
and another stock default boot would not qualify one-time GRUB selection.
06e's full run passed this revised sequence, including the rendered rollback
greeter and another unattended stock boot; it does not qualify GRUB recovery
promotion.
Disposable passwords and hashes are masked before builder output is logged.

The base's desktop packages remain installed to preserve its graphics dependency
set. Display managers, desktop sessions, power agents, XDG autostarts, updater
entry points and automatic maintenance are disabled by `build.sh` and `policy/`.
`ares` cannot invoke the retained updater binaries (`uupd`, `ujust`, `topgrade`,
the Bazzite updater/portal, the stores) or authorize `rpm-ostree`, sysupdate,
`fwupd` or Bazzite actions through polkit, even with its password. Upstream rules
that let `wheel` act without a password ask `ares` for it instead
(`00-aresos-maintenance.rules`; `ci/polkit-check.js` evaluates the built image's
real rules). Flatpak and Homebrew are his apps. This is a disposable prototype with manual image maintenance;
it does not attempt to restrict a recovery administrator deliberately repairing
the system or a user downloading their own programs.

Stock Homebrew lives in shared `/var/home/linuxbrew` and stays owned by the stock
UID 1000 administrator, so a rollback to stock keeps a working Homebrew. Since
package 21 the image-owned `aresos-inherited-homebrew.conf` tmpfiles rule gives
UID 1001 read and execute access to that directory on boot (replacing the deny
entry of earlier images); it preserves other ACL entries, ownership and
contents. `ares` runs brew-installed tools and read-only `brew` commands directly;
`/usr/bin/brew` runs everything else as the prefix owner after `sudo` asks for his
password. The daily PATH (`/etc/profile.d/aresos.sh`) puts `~/.local/bin` first,
then the system, then Homebrew's and Flatpak's command directories when present.
Existing setup/update/upgrade unit masks remain in force. The switch regression
executes the real inherited `brew --version` as its owner on stock, AresOS and
rolled-back stock, and checks the daily access, PATH and the password-gated
install route. No install/update is requested.

The UID 1001 entry remains in shared home state after rollback; it does not
restrict UID 1000. An administrator can remove it with
`sudo setfacl -x u:1001 /var/home/linuxbrew`. No recursive chmod/chown, Homebrew
deletion, credential change or user renumbering is part of this policy.

Power defaults are explicit in `config/etc/systemd/`: all lid cases, idle,
suspend/hibernate keys, reboot key and software long-press actions are ignored.
A short power press requests clean system poweroff. Sleep targets and their
services are masked and all four systemd sleep modes disallowed. UPower's
critical action is `Ignore`, with its required opt-in enabled. There is no game
or power coordinator yet; critical-battery handling must be implemented and
qualified before hardware/battery use.

The workflow uses standard Ubuntu hosted runners and manual dispatch only.
The image job has a 90-minute limit; its dependent stock switch/rollback job
has a 75-minute limit. `ci/toolchain.json` selects an immutable Ubuntu archive snapshot;
`ci/install-tools.sh` isolates APT from the runner's mutable repositories,
selects exact snapshot package versions, and reinstalls Podman, Skopeo, QEMU
and OVMF/SeaBIOS/iPXE firmware from that signed archive. Evidence records exact
versions, archive package hashes, executable/OVMF hashes and APT policy. The
GitHub-managed runner image, kernel/KVM/NBD and preinstalled shared libraries
remain mutable host inputs: hosted runners do not support digest selection or
our own kernel boot. Their image version, kernel/modules and full dpkg inventory
are recorded, with these exceptions explicitly listed in the toolchain manifest.
All container/disk/VM operations run there. It uses rootful Podman
storage directly with the template's pinned bootc-image-builder. Only the tested
release is pushed to private GHCR, using temporary `GITHUB_TOKEN` credentials;
no image archive is uploaded. Only evidence smaller than
180 MB is retained, for three days. No automatic scheduled builds run. The
original package-06 budget was six full dispatches or about 400 runner minutes.
Follow-up 06c permits at most two full runs, rebuilding/publishing only when
the image changes, with checks-only preflight before full runs. Earlier budgets
and results are historical in their reports. Inspect the report
before manually rerunning it. Exhausting the declared run/minute budget or
runner disk capacity is a stop condition; a failed step remains a failed run.
Evidence/report-only commits do not rebuild the large image. The report records
the exact source commit and green run that produced its committed evidence.
For regression work without another image build, manually dispatch
`gh workflow run os-image.yml --ref pkg/06-image-release -f checks_only=true`.
That mode is labelled **OS regressions only (no VM)** and skips the image job;
it runs regressions/syntax checks and queries the real hosted system manager's
unit-file and live unit states. It also verifies package privacy/access and
resolves signed base/official ISO metadata. No image layer, disk or VM is built.
Its green result does not qualify the VM acceptance gate. Ordinary image runs
still require both fresh VM passes.

For a harness-only switch retry, dispatch with
`-f checks_only=false -f switch_from_run=<qualified-run-id>` after checks-only CI.
That mode downloads the earlier release evidence and requires its image job
(including both VM passes and publication) to have succeeded. It checks the
source SHA and refuses any change to runtime configuration, policy, packages,
base, audit or verification key before booting the same published digest.
It cannot qualify a changed release image or overwrite an immutable tag.

The graph audit (`ci/activation_audit.py`), activation-canary prototype and Fedora
container preflight are preserved for the follow-up and are not run by either
workflow mode. Their existing parser/graph regression tests remain enabled.
The graph implementation is not installed in the release or VM image. Any
restored release-container probe must remain diagnostic: a container is not the
boot acceptance environment. Full attempt 1 retained its exact real Fedora
systemctl transcript, parsed probes, version, service status and user journal.

CI requires every suspicious system/user unit to be masked or individually
reviewed, regardless of unit-file state. The scanner reads installed definitions
and drop-ins, template definitions for loaded instances, and real boot-generated
system/user fragments. It also checks unit-file and active/substate snapshots
from both live managers. An unavailable user manager fails the check. A masked
but active, activating, reloading, deactivating or running unreviewed updater
also fails. Allowlisted bookkeeping is individually reviewed, not updater
execution. CI-only canaries prove rejection of an unenabled static updater and
an updater generated at boot, then are removed before the normal-policy audit.
Both have false conditions preventing execution. Effective transient commands,
manager-reported fragment paths/aliases and dependency-graph traversal are the
explicit follow-up residual; current static evidence does not qualify them.
The disk boots with OVMF UEFI and QEMU (KVM when available).
Its checks cover the real user session, blocked updater/sleep units, absence of the
inherited desktop, a recovery key opening another terminal and authenticated
recovery password authentication and an independent tty3 getty. A separate
`localhost/aresos:vm` test layer adds a fixed-check service over a dedicated
virtio-serial port; the release image is checked for absence of that service,
its scripts and credentials, with both image account passwords still locked.
No test modifies the guest PAM policy. The ordinary serial console is a passive
log, never a command/authentication transport. Checks and checksum-protected raw
exports use bounded JSON frames on virtio, isolated from kernel messages and
terminal queries. Release and test-layer OCI manifests/digests are saved separately;
the live bootc status identifies the test image. Before recovery testing, CI exports the raw
`bootc status --json` and runtime updater inventory. A temporary uinput device
injects lid, suspend-key and hibernate-key events; logind must observe them while
the session stays alive and sleep units remain unentered. Direct logind sleep
requests must fail, then QEMU's ACPI power button must reach logind and cleanly
power the guest off. A continuous QMP reader must capture `SHUTDOWN` with
`guest=true, reason=guest-shutdown`, QEMU must exit 0, and the console must show
the poweroff target. A separate CI-only transient unit follows the journal from
a saved cursor, forwards to the passive console, and is configured without
ordinary shutdown dependencies; CI confirms its own readiness record before
pressing the button. Persistence is explicit in the release image. Only the CI
overlay raises logind's log level and the journal's storage level to debug.
After QEMU exits, CI attaches that pass's retained qcow2 overlay through a
read-only NBD device and mounts its Btrfs top level with `ro,nologreplay`.
If the runner kernel rejects the mount, the release image's `btrfs restore`
extracts only the persistent journal from the primary root tree, through the
same read-only device, without ignoring errors or using older trees. The
release image's `journalctl --directory` exports the previous guest boot by its exact boot ID,
including full boot text/JSON, logind JSON, journal verification and file hashes.
When the offline boot is readable, its records must show the pre-button marker, logind's structured short
power-key event, its `SHUTDOWN=power-off` request and successful service teardown,
in that order. Final poweroff.target and guest-initiated QMP shutdown remain
mandatory too; the live follower is retained as diagnostic evidence. Only the
two explicit host-reader limitations together report the logind path as a hardware gate;
it does not claim that logind handled the button. A readable journal's missing
event, wrong boot, invalid journal or unexpected/cleanup failure still fails.
The workflow repeats every guest check in two fresh QEMU
boots using disposable disk overlays and reset firmware variables, saving each
pass separately. Screenshots are QEMU framebuffer captures. The VM has only its
CI-created file disk and ephemeral firmware variables.

Review generated `os-image-evidence` and `os-switch-evidence` before promoting
a build. Download their manifests into `os/manifest/` and session/TTY PNGs into
`reviews/06-image-release/screenshots/` using `gh run download`. Never upload the
image, VM disk, credentials, builder configuration or container storage.
